# Соглашения репозитория control-plane для агента-исполнителя

Этот файл — соглашения прозой; исполнитель читает его сам (`CLAUDE.md` —
ссылка `@AGENTS.md`). Что готовит для задачи демон исполнителя — соседей,
установку, тестовую базу и проверки — описано машиночитаемо в
[`.agents/runner.yaml`](.agents/runner.yaml), формат — в
[`src/control_plane_agent/runner_config.md`](src/control_plane_agent/runner_config.md).
Демон читает оба файла с базовой ревизии задачи: правка на ветке задачи
действует только после ревью и вливания.

Руководство для людей — [`CONTRIBUTING.md`](CONTRIBUTING.md); решения —
[`docs/adr/`](docs/adr/README.md).

## Среда

- Рабочая копия — текущий каталог (`services/control-plane` в раскладке суперпроекта,
  TAI-ADR-0064). Соседи `../../sdk/platform-auth-sdk` и `../memory-service` стоят на ревизиях, закреплённых суперпроектом, и доступны
  **только для чтения**. Правки вне control-plane не делай: сделай свою часть, а
  остальное опиши в отчёте.
- **Контракт другого сервиса не выдумывай.** Если control-plane вызывает
  memory-service, возьми путь, тело и ответ из его кода
  (`../memory-service/src/platform_memory/server/`, модели запросов pydantic) и
  закрепи contract-тестом против этой модели. Фейк, который принимает любое
  тело, не считается проверкой.
- Docker внутри нет: `docker compose …`, `make db-up`, `make test-db-up` и сборка
  образа не сработают. Адрес тестовой PostgreSQL бери из `CP_TEST_DATABASE_URL`
  окружения прогона (узел выдаёт базу по `services.db` из `.agents/runner.yaml`).
  Если инструкции агента задают свой адрес — следуй им. Чужие базы не трогай.

## Команды

Те же цели `make` вызывает CI (`.github/workflows/ci.yml`) и демон перед сдачей
(`checks` в `.agents/runner.yaml`); копий их команд не держи.

| Цель | Что делает |
|---|---|
| `make install` | `uv sync --frozen` — установка по `uv.lock` |
| `make lint` | `ruff check .` и `ruff format --check .` |
| `make typecheck` | `mypy src` |
| `make test` | весь pytest (`testpaths = tests`); аргументы — `make test PYTEST_ARGS="tests/unit -x"` |
| `make check` | `lint`, `typecheck`, `test` подряд — полный прогон, как в CI |
| `make fmt` | `ruff check --fix` и `ruff format` |

- Сначала гоняй только затронутые тесты (`make test PYTEST_ARGS="tests/unit/test_x.py"`),
  полный `make check` — один раз, перед сдачей.
- Одновременно — только один прогон тестов и не в фоне. `make test` держит
  `flock` на `.pytest.lock`: второй прогон в той же рабочей копии сразу выходит
  с кодом 75 — не повторяй его в цикле, дождись первого.
- Прогон молчит дольше нескольких минут — останови его и найди причину, а не
  запускай второй. У каждого теста таймаут 120 с (`pytest-timeout`).
- Миграции Alembic проверяются интеграционными тестами — они входят в
  `make test`; меняешь модели или `migrations/` — полный прогон обязателен.

## Правила

- Архитектурные решения — в ADR (`docs/adr/`, ряд CP). Меняешь контракт API,
  схему БД или поведение, описанное в ADR, — обнови или дополни ADR в том же
  коммите.
- Номер нового ADR — следующий свободный в `docs/adr/` на целевой ветке
  (`origin/<baseBranch>`) на момент коммита: параллельные ветки уже занимали
  один номер.
- Подразделы амендмента ADR помечаются серией `<буква><номер>` (`### Ж1. …`);
  буква — следующая свободная в этом ADR на `origin/<baseBranch>`. Перед сдачей
  амендмента влей актуальный `origin/<baseBranch>` и прогони проверку меток —
  `make test PYTEST_ARGS="tests/unit/test_adr_amendment_labels.py"`: параллельные
  задачи уже занимали одну букву в одном ADR.
- Документация — на русском; комментарии в коде — как в окружающем коде (здесь —
  английские, ruff RUF003 запрещает кириллицу в комментариях); имена API и
  сущностей — на английском.
- Кодовое имя продукта в коде и документах запрещено (white-label, ADR-0022,
  страж `tests/unit/test_branding.py`).
- Не коммить секреты, локальные абсолютные пути, `.env`, артефакты сборки.
- Не трогай `main` и чужие ветки, не пушь и не открывай pull request: демон сам
  коммитит и публикует ветку задачи.
- Не делай того, чего нет в задаче. Найденное попутно — в отчёт, а не в код.

## Перед сдачей (обязательно)

Каждый пункт уже стоил круга ревью; сдача без них — возврат задачи. Пункты
повторяют тип задачи `coding-task`: задачи, закреплённые на его прежней версии,
иначе их не видят.

1. Целевая ветка — `baseBranch` задачи, нет — `main`. Рабочая копия — worktree
   голого зеркала, простой `git fetch` двигает только `FETCH_HEAD`, поэтому:
   `git fetch origin +refs/heads/<baseBranch>:refs/remotes/origin/<baseBranch>`.
   Сливай и сравнивай только с `origin/<baseBranch>`: ушла вперёд —
   `git merge origin/<baseBranch>` и разреши конфликты; проверка —
   `git merge-tree --write-tree origin/<baseBranch> HEAD` без конфликтов.
2. На дереве слияния — `make check`, как в CI: скрытые `no-redef` и `arg-type`
   появляются после слияния параллельных задач. Сборку Docker-образа не делай.
3. Одна голова alembic с учётом целевой ветки: `uv run alembic heads` — ровно
   одна.
4. Доработка после отклонения: каждый сценарий из комментария ревью сначала
   воспроизведи тестом, падающим на прошлой попытке, и только потом исправляй.
5. Граничные случаи новой логики — отдельными тестами: пустое, `null`, неверный
   тип, повтор и идемпотентность, параллельные вызовы, пути файловых операций.
6. Безопасность: невидимый или чужой объект — ответ, неотличимый от
   отсутствующего, если так требует ADR; секреты не попадают в журналы и ответы.

В отчёте — перечень проверок по пунктам 1–6: команда и результат.

## Отчёт

Первой строкой — что сделано, одной фразой. Дальше: изменённые места, какие
тесты прогнаны и с каким результатом, что осталось или требует решения
человека. Ревью идёт через approval, поэтому отчёт должен позволять проверить
работу без повторного исследования.
