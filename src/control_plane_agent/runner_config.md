# Формат `.agents/runner.yaml`, версия 1

Машиночитаемые соглашения репозитория для демона исполнителя
(`control_plane_agent`). Решение — TAI-ADR-0063 суперпроекта, п. 4–6; фича
`universal-runner`, пункт U003.

Каждый репозиторий каталога `workingCopy.repositories`, в который публикуются
ветки задач, несёт три файла:

- `AGENTS.md` — соглашения прозой; исполнитель читает его сам;
- `CLAUDE.md` — одна строка `@AGENTS.md`;
- `.agents/runner.yaml` — этот файл: что демон готовит для задачи.

Схема — [`runner_config.schema.json`](runner_config.schema.json) (JSON Schema
2020-12), разборщик — [`runner_config.py`](runner_config.py)
(`parse_runner_config`).

## Пример

```yaml
version: 1
neighbours: [platform-auth-sdk, memory-service]
setup: uv sync --frozen
services:
  db:
    template: postgres-16
    env:
      CP_TEST_DATABASE_URL: "postgresql+psycopg://{user}:{password}@{host}:{port}/{database}"
checks:
  - {name: lint, run: make lint}
  - {name: types, run: make typecheck}
  - {name: tests, run: make test, services: [db]}
```

## Поля

| Поле | Обязательно | Что это |
|---|---|---|
| `version` | да | Версия формата, целое `1`. Другая версия — ошибка, а не догадка. |
| `neighbours` | нет | Ключи каталога `workingCopy.repositories`, которые ставятся рядом с рабочей копией только для чтения. URL берётся из каталога, ревизия — из суперпроекта на его базовой ревизии; адресов в файле нет. Без повторов. |
| `setup` | нет | Команда установки; демон выполняет её в рабочей копии перед исполнителем (как — ниже). |
| `services` | нет | Тестовые сервисы прогона: `{имя: {template, env}}`, не больше 10. Нет поля или `services: {}` — демон сервисы не запрашивает: узел отвергает запрос без сервисов. |
| `services.<имя>.template` | да | Имя шаблона в `node.yaml` узла. Образ, монтирования и привилегии в файле не задаются: узел выдаёт сервис только из своих шаблонов, незнакомый шаблон — `blocked` с `service_template_unavailable`. |
| `services.<имя>.env` | нет | Переменные окружения прогона с подстановками (ниже). Одна переменная — у одного сервиса; служебные имена запрещены (ниже). |
| `checks` | нет | Проверки перед сдачей, по порядку. |
| `checks[].name` | да | Имя проверки, уникально в файле. |
| `checks[].run` | да | Команда — цель, которую вызывает CI (`make test`), а не копия его команд. |
| `checks[].services` | нет | Имена сервисов из `services`, нужных проверке. |

Имена — строчные латинские буквы, цифры и дефис; ограничения сервисов и шаблонов
совпадают с контрактом узла `fleet` (`ServiceName`, `TemplateName`), соседей — с
ключом репозитория каталога, так что узел не отвергнет прошедший разбор файл:

| Имя | Шаблон | Длина |
|---|---|---|
| ключ соседа | `[a-z0-9][a-z0-9-]*` | 1–63 |
| имя сервиса | `[a-z0-9]`, дальше `[a-z0-9-]`, дефис не последним — имя входит в имя хоста | 1–31 |
| имя шаблона | `[a-z0-9][a-z0-9-]*` | 1–63 |
| имя проверки | `[a-z0-9][a-z0-9._-]*` | 1–63 |
| имя переменной | `[A-Za-z_][A-Za-z0-9_]*` | 1–128 |

Подчёркивание и точка в именах сервисов и шаблонов (`db_main`, `postgres.16`) —
ошибка. Шаблоны схемы кончаются на `(?![\s\S])`, а не на `$`: в Python `$`
пропускает завершающий перевод строки, и `"db\n"` сошло бы за имя.

В `env` запрещены имена, которые задают демон, узел и исполнитель, и имена,
которые меняют, что исполняется, куда уходят запросы исполнителя, каким
сертификатам он верит и чьи учётные данные берёт (`RESERVED_ENV_NAMES` в
`runner_config.py`, `$defs.reservedEnvName` схемы):

| Что | Имена |
|---|---|
| оболочка и путь | `PATH`, `HOME`, `SHELL`, `ENV`, `BASH_ENV` |
| интерпретаторы | `PYTHONPATH`, `PYTHONHOME`, `PYTHONSTARTUP`, `PYTHONUSERBASE`, `NODE_OPTIONS`, `NODE_PATH`, `PERL5OPT`, `RUBYOPT`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS` |
| доверие TLS | `NODE_EXTRA_CA_CERTS`, `NODE_TLS_REJECT_UNAUTHORIZED`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `CURL_HOME` |
| загрузчик | `LD_*`, `DYLD_*` |
| каталоги настроек | `XDG_*` — клиент Control Plane ищет файл учётных данных по `XDG_CONFIG_HOME` |
| git, ssh, менеджеры пакетов | `GIT_*`, `GH_*`, `SSH_*`, `UV_*`, `PIP_*`, `NPM_CONFIG_*` — в любом регистре, как читает npm |
| узел и исполнители | `FLEET_*`, `CLAUDE_*`, `ANTHROPIC_*`, `OPENAI_*`, `CODEX_*`, `OPENCODE_*`, `IAM_*`, `CONTROL_PLANE_*` |
| прокси | `*_PROXY` — суффикс в любом регистре (`http_proxy`, `HTTPS_PROXY`, `no_proxy`) |

Кроме суффикса `_PROXY` и префикса `NPM_CONFIG_`, регистр учитывается: `path`
и `xdg_config_home` — обычные переменные.
Похожие имена разрешены: `NODE_ENV`, `PYTHONUNBUFFERED`, `ENVIRONMENT`.

## Подстановки

В значениях `services.<имя>.env` демон подставляет то, что узел выдал этому
сервису на прогон:

| Подстановка | Значение |
|---|---|
| `{user}` | учётная запись |
| `{password}` | пароль |
| `{host}` | адрес |
| `{port}` | порт |
| `{database}` | имя базы |

`{{` и `}}` — буквальные фигурные скобки. Любая другая подстановка (`{name}`,
`{0}`, `{port:d}`, `{user!r}`) и непарная скобка — ошибка разбора.

Окружение с подставленными значениями демон передаёт процессу исполнителя только
на этот прогон (FR-018 фичи): в чекпоинты, артефакты и журналы оно не попадает.
Подстановку делает `ServiceSpec.render_env`; `ServiceCredentials` не показывает
пароль в `repr`.

## Как исполняются `setup` и `checks`

- Команда — строка для оболочки: демон запускает `sh -c '<команда>'`
  (`SHELL` в `runner_config.py`), поэтому `&&`, `|` и кавычки работают как в
  shell. Списка аргументов формат не принимает.
- Каталог — корень рабочей копии репозитория задачи; соседи лежат рядом с ним.
- В командах ничего не подставляется: фигурные скобки в `setup` и `run`
  буквальные, `{port}` уйдёт в оболочку как есть. Подстановки есть только в
  `services.<имя>.env`.
- Окружение — окружение прогона вместе с `env` выданных сервисов.
- Успех — код выхода 0. `checks` идут по порядку записи в файле.
- `setup` демон выполняет сам в каждом прогоне с рабочей копией (TASK-001273,
  `control_plane_agent/setup_command.py`): после подготовки копии, соседей и
  тестовых сервисов прогона, до запуска исполнителя. Окружение — то же, что у
  проверки (ниже), вместе с `env` сервисов; предел — 1800 с, по нему
  останавливается вся группа процессов. Идёт действием `setup.run` прогона.
  Вывод — в журнал демона, с паролями сервисов, секретами демона и путями
  хоста, скрытыми так же, как в выводе проверок; в чекпоинты, артефакты и
  метаданные он не попадает. Ненулевой код или предел — прогон проваливается
  с `setup_failed`, задача — в `blocked`; в причине — команда, код выхода или
  «timed out» и первая строка вывода со словом `error`/`ERR!` (нет такой —
  последняя непустая). Исполнитель при этом не запускается.
- `setup` выполняется в каждом прогоне, в том числе повторно на той же копии,
  без пропуска по хэшу `runner.yaml` и lock-файлов: с lock-файлом повторная
  установка дешёвая, а хэш не видит того, чего нет в файлах (удалённый
  `.venv`, кэш, очищенный узлом). Поэтому команда должна быть идемпотентной
  и не менять отслеживаемые файлы: что она оставила в копии, коммитится
  вместе с работой исполнителя (ставьте зависимости в игнорируемые каталоги).
- База ветки неизвестна (ветка взята без записи о базе, `merge-base` не
  найден) — `setup` не выполняется, исполнитель ставит зависимости сам, как
  прежде; с включёнными проверками такой прогон раньше останавливается
  `checks_base_unknown`. Нет файла или поля `setup` — поведение прежнее.
  Неверный файл — `runner_config_invalid` до исполнителя, даже если проверки
  выключены: файл читается ради `setup`.
- `checks` демон прогоняет после работы исполнителя, если они включены в
  описании агента (`workingCopy.checks`, фича `universal-runner`, пункт U014):
  все по порядку, одна попытка исправления упавших, результат — в
  `metadata.checks` артефакта `commit`. Окружение проверки — окружение демона
  без зарезервированных имён (`RESERVED_ENV_NAMES`), кроме `PATH`, `HOME`,
  `SHELL`, хранилища сертификатов и прокси; предел — 1800 с на проверку и
  общий бюджет на все проверки сдачи. Что проверки оставили в копии, в коммит
  не идёт. Подробно —
  [`docs/execution-workspace.md`](../../docs/execution-workspace.md), раздел
  «Проверки перед сдачей».

## Как демон читает файл

- Только с базовой ревизии задачи: `git show <base>:.agents/runner.yaml`. Правка
  файла на ветке задачи начинает действовать после ревью и вливания. База — коммит,
  от которого отведена ветка задачи; как демон ставит соседей и что делает с
  неверным файлом (`runner_config_invalid`) — в
  [`docs/execution-workspace.md`](../../docs/execution-workspace.md), раздел
  «Соседи, суперпроект и `runner.yaml`».
- В задаче суперпроекта указатели сабмодулей не трогают — и соседей, и не
  названных в `neighbours`: сдвиг указателя — отдельное действие (скилл сдвига
  сабмодуля), а не часть задачи.
  Указатель, который принесло вливание базы, — базы; свой сдвиг — даже только в
  индексе — проваливает прогон с `neighbour_modified`, а откат к более старому
  указателю базы (вливание базы, затем `commit -a` при старом чекауте) — с
  `neighbour_pointer_regressed`: после вливания базы — `git submodule update`.
- Разбор строгий. Неизвестное поле, повтор ключа YAML (два `db:` в одном
  объекте), ключ слияния YAML (`<<: *base` — он обошёл бы проверку повторов),
  ссылка проверки на необъявленный сервис, повтор имени проверки, незнакомая
  подстановка — ошибки. Неверное имя объясняется правилом словами, а не
  регулярным выражением. Каждая ошибка названа по пути поля (ошибка YAML —
  строкой и столбцом), например:

  ```text
  $.services.db.template: required field is missing
  $.checks[0].timeout: unknown field
  $.services.db.env.DATABASE_URL: unknown placeholder {name}; allowed: {user} {password} {host} {port} {database}
  $.checks[2].services[0]: no service 'cache' in services
  $.services.db.env.LD_PRELOAD: reserved variable name (LD_*)
  $.services.db_main: 'db_main' is not a service name: lowercase latin letters, digits and '-', not starting or ending with '-', 1-31 characters
  $: not valid YAML at line 4, column 3: duplicate key 'db'
  $: not valid YAML at line 5, column 5: merge keys (<<) are not supported; write the keys out
  ```

- `ServiceSpec` проверяет шаблон, имена и значения `env` и сам, при создании:
  код демона, собравший его в обход разборщика, получит `ValueError`, а не
  подстановку в непроверенное значение. `env` хранится копией только для чтения
  (`MappingProxyType`): ни исходный словарь, ни держатель спецификации не
  изменят проверенное.

## Как демон получает сервисы

Демон (`services.py`, фича `universal-runner`, пункт U013) читает `services`
файла с базовой ревизии и до запуска исполнителя спрашивает их у слушателя
`fleet-services` своего узла. Контракт — `fleet_api.models` репозитория fleet
(`docs/node.md`, `openapi/fleet-services.json`); закреплённая копия OpenAPI —
`tests/fixtures/fleet_services_openapi.json`, фейковый слушатель тестов сверяет
с ней каждое тело и каждый ответ.

1. `POST /api/v1/service-requests` с `Authorization: Bearer <токен контейнера>`
   (файл `FLEET_SERVICES_TOKEN_FILE` читается заново на каждый запрос):
   `{agentKey, replica, services: {имя: {template}}, waitSeconds: 600}`. Ничего,
   кроме имени шаблона, в запрос не идёт.
2. `GET .../{requestId}?wait=60` — пока статус `pending`. `404` — слушатель
   перезапустился и потерял запрос: демон спрашивает заново. `429` — повтор
   через секунду, `503` и ошибка сети — через 5 с. Ответ должен назвать свою
   пару `agentKey`/`replica` и ровно запрошенные сервисы.
3. `ready` — демон ждёт, пока каждый сервис примет TCP-соединение (до 60 с),
   подставляет адрес и учётку в `env` и передаёт окружение адаптеру этого
   прогона (ниже). Пароль и токен не попадают ни в журнал, ни в исключение,
   ни в чекпоинт.
4. Пока прогон жив — `POST .../{requestId}/heartbeat` раз в 60 с: каждый держит
   сервисы 300 с, поэтому прогон дольше `idleSeconds` узла базу не теряет.
   `404` на heartbeat — слушатель перезапустился, удержание потеряно; прогон
   продолжается. По концу прогона, каким бы он ни был, — `POST
   .../{requestId}/release`; с него узел считает простой.
5. Своё ожидание демон ограничивает `waitSeconds` + 30 с запаса слушателя +
   один опрос. Вышло время или сервис не принял соединение — `release`
   (до `ready` он отзывает запрос) и `test_services_unavailable`.
6. Ожидание (до ~12 минут) идёт под супервизором прогона, как исполнитель:
   запрос отмены из ядра и конец времени drain (`SIGTERM`) прерывают его,
   запрос отзывается `release`, прогон отменяется (`cancel_requested`,
   `drained`). Сторож «нет прогресса» на ожидании выключен. Когда сервисы
   готовы, демон проверяет, жив ли claim (иначе `lease_lost`, исполнитель не
   запускается), и не вышло ли время drain.
7. `release` ждёт ответа не дольше 10 с (`RELEASE_TIMEOUT_SECONDS`), а не
   75 с long poll: зависший слушатель не держит рабочую копию. Не дождался —
   запись в журнал, прогон этим не проваливается; упавший цикл heartbeat
   `release` не отменяет.

Повторный запрос не идемпотентен. У `POST /api/v1/service-requests` в
контракте fleet нет ключа идемпотентности: если запрос дошёл до слушателя, а
ответ `202` потерялся (обрыв соединения, таймаут), повтор создаёт второй
запрос с новым `requestId`. Демон знает только второй: его он ждёт, держит и
освобождает. Первый остаётся у слушателя без heartbeat и `release` — чем он
кончится и сколько бюджета узла займёт, решают сроки узла (`waitSeconds`
запроса, удержание 300 с без heartbeat), а не демон. То же после `404` на
опрос: слушатель потерял запрос, и демон спрашивает заново.

| Исход | Причина провала прогона | Задача |
|---|---|---|
| нет времени или бюджета, сервис не принял соединение | `test_services_unavailable` | в очередь: прогон провален, claim снят |
| `rejected`, нет шаблона (или `422` на запрос) | `service_template_unavailable` | `blocked` |
| `rejected`, больше `perReplica` | `service_quota_exceeded` | `blocked` |
| нет слушателя, файла токена, исполнитель без `env` | `test_services_not_offered` | `blocked` |
| `401`, `403`, `422 invalid_request`, ответ вне контракта | `test_services_refused` | `blocked` |
| файл не проходит разбор | `runner_config_invalid` | `blocked` |

`FLEET_SERVICES_URL` и `FLEET_SERVICES_TOKEN_FILE` узел задаёт только виду
исполнителя с `services: true`. Раннер без них сервисы не запрашивает, и задача,
чей `runner.yaml` их объявляет, уходит в `blocked`. Раннер, которому тестовые
базы пока даёт хост, запускается с `CONTROL_PLANE_AGENT_SERVICES=host`: тогда
демон ничего не спрашивает и окружения прогона не собирает.

## Окружение прогона в адаптерах

Окружение с подставленными значениями доходит до процесса исполнителя во всех
трёх адаптерах и живёт ровно один прогон (FR-018 фичи `universal-runner`):

- Claude Code и Codex принимают его ключевым аргументом `env` метода `execute`
  и передают только в процесс `claude` / `codex` этого прогона (и его детям —
  MCP-серверу, оболочке). В окружение демона и в адаптер оно не пишется;
  следующий прогон без `env` его не видит. Свои переменные адаптера
  (`CONTROL_PLANE_TASK`, `CONTROL_PLANE_RUN_ID`, `CONTROL_PLANE_BLOCKED_FILE`)
  окружение прогона не перекрывает.
- Отдельная обвязка OpenCode (`control-plane-opencode`) сервисы у узла не
  спрашивает: рабочей копии базы задачи у неё нет. Без источника окружения
  прогона она читает `runner.yaml` репозитория, в котором работает (`HEAD`
  текущего каталога), и если тот объявляет `services`, прогон уходит в
  `blocked` (`test_services_not_offered`, неверный файл —
  `runner_config_invalid`), а не идёт без сервисов. С
  `CONTROL_PLANE_AGENT_SERVICES=host` проверки нет: базы даёт хост.
- OpenCode исполняет инструменты внутри процесса `opencode serve`, а у его
  HTTP API нет окружения на запрос. Поэтому с `CONTROL_PLANE_OPENCODE_BINARY`
  адаптер поднимает свой `opencode serve` на прогон с окружением — на
  loopback, на свободном порту — и останавливает его по концу прогона; прогон
  без окружения идёт на общий сервер (`OPENCODE_SERVER`). Прогон с окружением
  на общем сервере (без `CONTROL_PLANE_OPENCODE_BINARY`) проваливается, а не
  теряет переменные и не отдаёт их следующим прогонам.
- Сервер прогона исполняет оболочку модели, поэтому окружение демона он
  получает без переменных демона, платформы и узла (`CONTROL_PLANE_*` — в том
  числе `CONTROL_PLANE_API_KEY`, — `IAM_*`, `FLEET_*`;
  `DAEMON_ENV_PREFIXES` в `control_plane_opencode/server.py`), а пароль
  `OPENCODE_SERVER_PASSWORD` — только явно заданный адаптеру, не унаследованный.
  Вывод сервера (stdout, stderr) пишется в журнал адаптера построчно.
- Каждый адаптер повторно отбрасывает запрещённые и неверные имена и значения
  с символом NUL (`run_environment` в `runner_config.py`) — защита в глубину на
  случай окружения, собранного в обход разборщика, или подстановки, принёсшей
  NUL: такое значение стоит одной переменной, а не падения запуска
  исполнителя. Отброшенные имена пишутся в журнал предупреждением, значения —
  никогда.

## Проверить файл локально

Разборщик зависит только от `pyyaml` и `jsonschema`, поэтому файл проверяется из
любого репозитория, не только из окружения control-plane. Нужна копия
control-plane (любой клон; путь к ней ниже — `<control-plane>`):

```bash
uv run --no-project --with pyyaml --with jsonschema \
  python <control-plane>/src/control_plane_agent/runner_config.py .agents/runner.yaml
```

В окружении control-plane то же самое — `uv run python -m
control_plane_agent.runner_config .agents/runner.yaml`. Без аргумента берётся
`.agents/runner.yaml` текущего каталога.

Команда молчит и выходит с 0, если файл верен; печатает ошибки по путям полей в
stderr и выходит с 1, если нет; не читается файл — 2. Traceback не печатается.
