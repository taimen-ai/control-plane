# ADR-0061: Исходы approval объявляет тип задачи — обобщённый исполнитель в ядре

Статус: Accepted (2026-09-23), шаг 1 TAI-ADR-0041; редакция 2 (2026-09-23) — по
ревью TASK-000282: authorizer в worker'е, собственные повторы исполнителя, `deferred`
под claim, обязательные выражения, системный исполнитель ядра; редакция 3
(2026-09-23, TASK-000312) — шаг 2 TAI-ADR-0041: `invokeSkill` исполняется через
`skill_invocation` (M2.1), реакция `onFailure`, `customFields` и `|truncate:N` в
выражениях, порядок `invokeSkill` до закрытия задачи, `code-review` больше не сеет ядро;
редакция 4 (2026-09-23, TASK-000326, по ревью TASK-000315) — задача закрывается **по
итогу** вызова (реакции `onSuccess`/`onFailure`), а не рядом с `invokeSkill`;
проверки по реестру при публикации (`name@version` для `external_write`, не в
`rejected`); литеральный статус у `transition` своей задачи; срок ожидания
невзятого вызова; требования к `field_schema` `code-review` v4; амендмент
2026-09-25 (TASK-000378) — `ensureWork.customFields` и `requestApproval`, работа
после завершения задачи (`completionSchema`) вместо ревью, заведённого демоном;
амендмент 2 2026-09-25 (TASK-000375) — предусловия `approve` (`preconditions`,
шаг 3 TAI-ADR-0041, п.7); амендмент 3 2026-09-30 (TASK-001071) — перевод задачи
на другую версию типа не обгоняет неисполненный исход; амендмент 4 2026-10-01
(TASK-001237, из приёмки S033 №12) — адресат гейта ролью пакета `role:<slug>`

Контекст: TAI-ADR-0041 (Accepted 2026-09-23, суперпроект) — исходы approval
объявляются типом задачи; ADR-0018 (gate-approval); ADR-0048 (иммутабельная
версия типа задачи); ADR-0052, амендмент 2026-09-23 (ревью человеком через
gate-approval); ADR-0056 (Skill contract, `invokeSkill`); ADR-0047 (external
references).

## Контекст

С амендментом ADR-0052 вердикт ревью — это решение человека по gate-approval на
задаче `code-review`. Но после решения ничего не происходит: reject не
превращается в работу для кодера, approve не закрывает ревью. Человек
заводит задачу на правки руками, вписывает в неё ветку и замечания, закрывает
ревью — ровно та ручная склейка, от которой ADR-0052 уводил на стороне
кодера.

Решение владельца (TAI-ADR-0041): **ядро не знает доменных действий**.
«Слить ветку», «опубликовать релиз» — это не операции Control Plane. Ядро
исполняет любой тип задачи обобщённо: тип объявляет, что делать после
решения, ядро исполняет объявленное закрытым словарём действий над своими
сущностями. Доменное (merge) приходит позже как вызов Skill из интеграции
(`integrations/selfdev`), а не как код в ядре.

## Решение

### 1. `task_types.approval_schema` — часть иммутабельной версии

```json
{"gates": {"default": {"outcomes": {
  "approved": [{"completeTask": {}}],
  "rejected": [{"ensureWork": {"type": "coding-task", "key": "…", "title": "…"}},
               {"completeTask": {}}]
}}}}
```

JSONB-колонка версии типа, `{}` по умолчанию («исходов нет» — поведение до
этого ADR). Триггер неизменяемости `task_types` покрывает и её: поменять исходы
— значит выпустить следующую версию (ADR-0048). Задача помнит версию, с которой
создана, поэтому уже открытое ревью исполняет те исходы, что были объявлены при
его создании.

Ключ гейта — имя; сейчас у approval нет имени гейта, поэтому допустим и
исполняется только `default`. Другое имя отклоняется при публикации
(`invalid_approval_schema`): такой гейт никогда бы не сработал, а исходы,
которые молча не исполняются, хуже отказа. Имена откроются, когда approval
получит имя гейта. Исходы — `approved` и `rejected`; каждый — список
действий, исполняемых **по порядку**. Действие — объект с одним ключом (имя
действия) и объектом входов.

Валидация — при публикации версии (`POST /task-types`), не при решении:
закрытый словарь действий, закрытый набор входов у каждого, корректные
выражения, известные типы связей; `transition` своей задачи (без `task`) в
литеральный статус проверяется по lifecycle этой же версии. Нарушение —
`422 invalid_approval_schema` с путём до места ошибки. Документ проходит тот же
guard размера и secret scan, что прочие JSON-документы типа.

### 2. Словарь действий (шаги 1–2)

| Действие | Входы | Что делает |
|---|---|---|
| `ensureWork` | `type`, `key`, `title` (обязательные); `description`, `assignee`, `priority`, `workspace`, `relation {<тип связи>: ref}`, `customFields {поле: строка}`, `requestApproval {assignee, comment?}` (амендмент 2026-09-25) | Создаёт задачу типа `type`, если задачи с этим `key` ещё нет; связывает новую задачу `relation` (например, `spawned_by` → ревью). `workspace` по умолчанию — workspace задачи approval'а; и явный, и умолчательный проверяются как право решившего `tasks.write` на **этот workspace** (п.5) |
| `completeTask` | `task?` (по умолчанию задача approval'а) | Обычный `:complete`: ребро в `completionStatus` должно быть объявлено, gate не должен держать задачу. Уже завершённая — не ошибка (`alreadyCompleted`) |
| `comment` | `body`, `task?` | Комментарий в тред задачи от имени решившего |
| `transition` | `status`, `task?` | Обычный `PATCH status` — только по объявленному ребру lifecycle; уже в статусе — не ошибка. Для задачи approval'а (`task` не задан или `$.task.id`/`$.task.publicId`) `status` — только литерал из её lifecycle: закрывает ли переход задачу, должно быть известно при публикации (п.10) |
| `invokeSkill` | `skill` (литерал `name@version` или `name`), `inputs?`, `expect?`, `onSuccess?`, `onFailure?` | Ставит в очередь `skill_invocation` (ADR-0056) тем же путём, что `POST /skills/{ref}:invoke`; см. п.10 |

`key` у `ensureWork` — ключ «ensure» в пределах tenant'а: автор схемы сам
выбирает область (в `code-review` v3 — `review-fix:$.approval.id`, одна задача
на правки на каждое решение). Ключ глобален в tenant'е, поэтому найденная по нему
задача отдаётся как результат, только если решивший может её прочитать
(`tasks.read` по ресурсу `task:<id>`); иначе действие падает `not_found` — ровно
так, как если бы задачи не было, без её id в ошибке.

### 3. Выражения входов — ограниченный JSON-path, без кода

Строковый вход может ссылаться на контекст решения:

- `$.task.<f>` — задача approval'а; `$.spawnedBy.<f>` — задача, от которой она
  порождена связью `spawned_by` (самое раннее такое ребро);
  `f ∈ {id, publicId, title, description, assigneeId, workspaceId, status, priority}`;
- `$.task|spawnedBy.customFields.<key>` — поле `custom_fields` задачи (шаг 2);
- `$.approval.<f>`, `f ∈ {id, comment, decidedBy, decidedAt, outcome}`;
- `$.task|spawnedBy.artifact[<type>].metadata.<field>` — поле metadata самого
  свежего артефакта этого типа на задаче;
- `$.invocation.<id|skill|status>`, `$.invocation.output.<field>`,
  `$.invocation.error.<code|message>` — вызов скилла, на итог которого реагирует
  действие; допустимо **только** внутри `onSuccess`/`onFailure` своего `invokeSkill` (п.10),
  в любом другом месте отклоняется при публикации.

Единственный фильтр — `|truncate:N` (1 ≤ N ≤ 100 000) после выражения (и после `!`,
если оно есть): текст длиннее N символов обрезается до N, последний символ —
«…». Нужен, чтобы копия описания исходной задачи не росла в цепочках
правки → ревью → правки (`$.spawnedBy.description|truncate:4000`). Больше
ничего: ни вызовов, ни индексов, ни других фильтров, ни корней вне списка.
Строка, целиком состоящая из одного выражения, даёт значение как есть (в том
числе `null` — например, отсутствующий `assignee`); любая другая строка —
шаблон, в котором каждое выражение заменяется своим текстом, `null` — пустой
строкой. Контекст снимается один раз перед первым действием исхода.

**Обязательное выражение** — с суффиксом `!` (`$.spawnedBy.assigneeId!`,
`$.x.y!|truncate:N`). Если
оно разрешилось в `null` или пустую строку — и целиком, и внутри шаблона, —
действие не исполняется, исход падает с кодом `unresolved_expression` (в
`details.expression` — само выражение). Иначе незаполненный контекст молча
превращался в задачу без исполнителя (runner с `ONLY_ASSIGNED` её не возьмёт),
заголовок «Правки по ревью : » и исход `executed`. Суффикс, а не отдельный
список обязательных входов: обязательность — свойство ссылки, а не входа
целиком (ветка — одно выражение внутри шаблона `description`).

Что выражения читают, решивший должен мочь прочитать: `tasks.read` на каждую
задачу, на которую ссылаются `$.task`/`$.spawnedBy`, и `artifacts.read`, если
есть ссылки на артефакты. Проверка — тем же `authorize()` (в режиме `policy` —
по ресурсу `task:<id>`) при каждом исполнении; отказ — `forbidden` у первого
невыполненного действия. Иначе исход переносил бы в новую задачу то, чего
решивший никогда не видел.

### 4. Исполнитель — в worker'е, по состоянию approval'а, а не по outbox

`decide_approval` для **gate**-approval'а на задаче, тип которой объявляет
непустой список действий для этого решения, ставит
`approvals.outcome_status = 'pending'`, `outcome_next_attempt_at = now` и
сохраняет **снимок полномочий решившего** (`decision_authority`: permissions,
credential, IAM subject; у решения из канала — права binding человека,
CP-ADR-0070) — в той же транзакции, что и решение. Для прочих
approval'ов `outcome_status` остаётся `NULL`, и ничего не меняется. Обычный
(не gate) approval совещательный: тип задачи не может знать, о чём был
произвольный approval, лишь упоминающий задачу.

Worker каждый цикл выбирает approval'ы с `outcome_status ∈ {pending, deferred}`
и наступившим `outcome_next_attempt_at` (частичный индекс
`ix_approvals_outcome_due`) и исполняет каждый **в своей транзакции**, беря
approval `FOR UPDATE SKIP LOCKED` — несколько worker'ов не мешают друг другу.
Outbox исполнитель больше не трогает: доставка `approval.*` вниз по течению и
исполнение исхода не зависят друг от друга (раньше сбой исхода отправлял в
dead-letter и доставку события решения). Отдельного журнала событий
«approval.decided» нет: это пара уже существующих событий; `causationId`
событий исхода — id события решения.

Состояния исхода: `pending → executed | failed | deferred`, `deferred →
executed | failed | deferred`, `failed → pending` только через replay.

**Неожиданная ошибка** (не доменная: `IntegrityError`, `KeyError`, обрыв БД)
откатывает транзакцию этой попытки целиком, затем в новой транзакции
засчитывается на самом approval'е: `outcome_attempts += 1`,
`outcome_last_error`, `outcome_next_attempt_at` — с тем же backoff, что у
outbox (`CP_OUTBOX_BACKOFF_*`). По достижении `CP_OUTBOX_MAX_ATTEMPTS` исход
становится `failed` с кодом `outcome_attempts_exhausted` у первого
невыполненного действия (`cause: internal_error`, `message` — последняя
ошибка, `details.attempts`), событием `approval.outcome_failed` и задачей на
разбор (п.7) — исход больше не может молча висеть в `pending`.

**Ожидание скилла.** Реакции `onSuccess`/`onFailure` (п.10) ждут, пока не
завершатся **все** вызовы исхода: пока хоть один `pending`/`running`, исход —
`deferred` с причиной `skill_pending` (в событии `approval.outcome_deferred` —
`reason: skill_pending`, `details.invocationId`) и проверяется снова через тот
же интервал `CP_APPROVAL_OUTCOME_DEFER_SECONDS`; попытки не засчитываются.
Ожидание ограничено: вызов, который `CP_APPROVAL_OUTCOME_SKILL_WAIT_SECONDS`
(по умолчанию 86 400 — сутки) после последнего движения (`updated_at`, а при
backoff — `available_at`) всё ещё `pending`, то есть его никто не взял,
исполнитель отменяет полномочием решившего (это его вызов; `POST
/skill-invocations/{id}:cancel`, `error.code: cancelled`, `error.message:
approval_outcome_skill_wait_expired`). Отмена — итог «не как ожидалось»: идут
реакции `onFailure`. Это — только при живом основании: утраченное основание
исполнитель проверяет раньше срока, на каждом проходе (п.10, «Основание
утрачено без claim»). Строку вызова исполнитель предварительно блокирует и
отменяет только `pending`: claim, успевший раньше, выигрывает, и `running`-вызов
ограничивают его lease и дедлайн попытки (ADR-0056), а не этот срок.

**Claim на цели.** Если `completeTask` или `transition` упирается в живой
claim на задаче (`task_claimed`) — это не сбой, а «ещё рано»: типичный
сценарий — человек по MCP взял ревью (claim → run) и решает gate изнутри
своего run'а. Действие откатывается, исход становится `deferred`
(`approval.outcome_deferred` — один раз, при переходе), попытка не
засчитывается, `outcome_next_attempt_at = now + CP_APPROVAL_OUTCOME_DEFER_SECONDS`
(15 с). Когда claim снят или истёк, следующая проверка продолжает с того же
действия; если держатель сам завершил задачу, `completeTask` отвечает
`alreadyCompleted`. Действия до ожидающего (например, `ensureWork` задачи на
правки) уже исполнены и не ждут claim'а. Завершать «с учётом claim'а
решившего» не стали: под claim'ом обычно идёт run, и завершение поверх него
было бы `run_in_progress` — отложенное действие покрывает оба случая одинаково.

### 5. Полномочия — решившего (TAI-ADR-0041 п.4)

Каждое действие идёт через обычную команду ядра с `AuthContext`,
восстановленным из снимка полномочий решившего. Право проверяет тот же
`authorize()`, что и в API; действие, на которое у решившего нет права, не
исполняется, исход падает с кодом `forbidden` (исходный код отказа — в
`cause`). Автор созданной задачи, комментария, перехода — решивший.

Снимок, а не «текущие права principal'а»: права живут в credential (API key
или IAM binding), у principal'а их может быть несколько. Worker'у не
предъявить credential, поэтому решает то, что credential мог в момент
решения.

**Authorizer в worker'е — тот же, что в API.** Worker при старте собирает
authorizer из тех же настроек (`build_authorizer`, `CP_AUTHZ_MODE`,
`CP_IAM_CLIENT_*`, `CP_POLICY_*`) и ставит его процессу. В режиме `policy`
для снимка с IAM subject решает PDP — по ресурсу (`workspace:<id>` при
создании задачи, `task:<id>` при записи в задачу), `on_behalf_of` — IAM
subject решившего; снимок без IAM subject (legacy API key) проверяется по
плоским permissions, как и в API. Поэтому исполнение в worker'е и replay через
API отвечают одинаково. Незаконченная конфигурация PDP роняет старт worker'а,
как и API.

**Credential должен быть жив.** При каждом исполнении (и при replay)
проверяется, что credential снимка ещё действует: API key не отозван и не
истёк, IAM binding `active` и не отозван, оба принадлежат решившему, а сам
principal `active`. Проверяется собственное состояние ядра (строки `api_keys`
и `iam_principal_bindings`, локальная политика отзыва ADR-0053): токен или PAT,
отозванный только в самом IAM, здесь не виден — чтобы исходы перестали
действовать, отзывается или отключается binding (в режиме `policy` каждое
действие дополнительно решает PDP). Иначе — `forbidden` с `cause: credential_inactive` у
первого невыполненного действия. Replay решившим подставляет его текущий
credential (он заведомо жив); replay admin'ом оставляет снимок — и проверку.

**`ensureWork.workspace`** не расширяет права: создание задачи проверяет
`tasks.write` решившего на целевой workspace (в `policy` — по ресурсу
workspace), будь он явным входом или workspace задачи approval'а. Поэтому
вход оставлен, а не убран: тип вправе класть правки туда, где жила исходная
задача (`$.spawnedBy.workspaceId`), но только если решивший сам мог бы
создать там задачу.

### 6. Идемпотентность

Ключ — `(approval.id, индекс действия)`: таблица `approval_outcome_actions`
(unique), строка на выполненное или упавшее действие с evidence (`result`) или
ошибкой (`error`) и числом попыток. Исполнитель берёт approval `FOR UPDATE` и
работает только при `outcome_status ∈ {pending, deferred}`: повторная попытка
или повторная доставка события решения — no-op; действие с `executed`-строкой
не исполняется повторно никогда. Строка пишется в той же транзакции, что и
эффект действия.

### 7. Сбой, события, replay

Каждое действие исполняется под своим savepoint. Сбой действия:

- его частичные записи откатываются; оставшиеся действия исхода **не
  выполняются**; решение **не откатывается** (approval остаётся
  `approved`/`rejected`, gate открыт);
- `outcome_status = 'failed'`, событие `approval.outcome_failed` c
  `failedAction {index, action, code, cause, message, details}` и evidence
  выполненных действий;
- решившему заводится задача на разбор (системный тип, исполнитель —
  решивший, `related_to` → задача approval'а, ключ ensure —
  `approval-outcome-failure:<approval.id>`; при повторном сбое — комментарий в
  неё же). Её автор — **системный исполнитель ядра**: service-principal
  tenant'а (`kind=service`, `metadata.system = control-plane-core`), который
  создаётся при первой надобности, без API key и IAM binding (войти им нельзя,
  он только атрибутирует записи ядра). Полномочие сужено до `tasks.write` и без
  IAM subject: типичный сбой — как раз то, что у решившего нет права писать, а
  сбой не должен остаться незамеченным; и писать от имени решившего то, что
  решивший не делал, ядро не должно.

Успех — `outcome_status = 'executed'` и событие `approval.outcome_executed` с
evidence по каждому действию (`taskId`/`publicId` созданной задачи, флаги
`alreadyCompleted` и т.п.). Актор событий — решивший, `causationId` —
событие решения.

`POST /approvals/{id}:replay-outcome` — для `failed` и для **зависшего**
`pending` (были неудачные попытки, `outcome_attempts > 0`, или worker не трогал
исход ≥ 10 минут); иначе `409 outcome_not_replayable` (свежий `pending` и
`deferred` ведёт worker). Replay обнуляет счётчик попыток, переводит исход в
`pending` и синхронно продолжает с первого невыполненного действия. Replay
может решивший — тогда полномочием становится его **текущий** credential
(обычное лечение `forbidden` — выдать право и повторить), или admin — тогда
остаётся снимок решения. Состояние видно в `GET /approvals/{id}/outcome`
(`outcomeStatus`, `attempts`, `lastError`, `nextAttemptAt`, действия; у реакции
реакции — `reactsTo`, индекс её `invokeSkill`, и `when`: `onSuccess` | `onFailure`)
и в `ApprovalOut.outcomeStatus`.

### 8. Происхождение работы (до Work Graph M1.1)

У задачи пока нет первоклассного origin. `ensureWork` помечает созданную задачу
external reference'ом в собственном пространстве ядра:
`externalSystem = control-plane`, `externalType = approval-outcome`,
`externalId = <key>`, metadata `{origin: approval, approvalId, actionIndex}`.
Та же ссылка — ключ «ensure»: задача с этим ключом второй раз не создаётся.
Когда M1.1 даст origin, его заполнят из этих ссылок.

### 9. Данные: `code-review` v3

Миграция `e3b8c1a6d9f4` добавляет каждому tenant'у, у которого есть тип
`code-review`, следующую версию — те же поля и lifecycle плюс исходы:

- `rejected` → `ensureWork` `coding-task` «Правки по ревью
  `$.spawnedBy.publicId!`: `$.spawnedBy.title`» (описание: комментарий
  решения, инструкция продолжить ветку
  `$.spawnedBy.artifact[commit].metadata.branch!`, описание исходной задачи;
  исполнитель — `$.spawnedBy.assigneeId!`, приоритет и workspace — исходной
  задачи; `spawned_by` → `$.task.id!`; ключ `review-fix:$.approval.id`), затем
  `completeTask`. Исходная задача, её исполнитель, опубликованная ветка и

  (`unresolved_expression`) и задачу на разбор, а не безхозную задачу на
  правки;
- `approved` → `completeTask`. Merge — шаг 2 (п.11), через `invokeSkill
  git.merge@1` из `integrations/selfdev`; в ядре его нет.

Тенанту без `code-review` миграция ничего не добавляет: тип — данные tenant'а.
Решившему ревью теперь нужно `artifacts.read` (ветка берётся из артефакта
`commit`, п.3).
Демон runner'а (ADR-0052, режим `human`) заводит ревью по **ключу** типа без
версии, а ключ резолвится в самую свежую active-версию — новые ревью
автоматически получают v3, перенастраивать демон не нужно.

### 10. `invokeSkill` (шаг 2) — вызов скилла через M2.1

```json
{"invokeSkill": {
  "skill": "git.merge@1",
  "inputs": {"repository": "$.task.customFields.repository!",
             "branch": "$.task.customFields.branch!",
             "commit": "$.task.customFields.commit!",
             "target": "$.task.customFields.targetBranch!"},
  "expect": {"merged": true},
  "onSuccess": [{"completeTask": {}}],
  "onFailure": [{"ensureWork": {"type": "coding-task", "key": "merge-fix:$.approval.id",
                                "title": "…$.invocation.output.reason$.invocation.error.code",
                                "assignee": "$.spawnedBy.assigneeId!", "…": "…"}}]
}}
```

**Ссылка на скилл** — литерал `name@version` (закреплённая версия) или `name`
(самая свежая active-версия, ADR-0021). Выражения в ссылке запрещены. **Входы**
— объект `inputs` (строки с выражениями, числа, булевы, вложенные объекты);
прежнее имя `input` больше не принимается.

**Проверки по реестру при публикации.** Грамматика не знает побочных эффектов
скилла, реестр знает; поэтому `POST /task-types` для каждого `invokeSkill`
смотрит в реестр tenant'а (`422 invalid_approval_schema`, `details.reason`):

- `not_found` — нет ни одной версии с этим именем (для `name@version` — этой
  версии). Тип, который вызывает незарегистрированный скилл, не публикуется;
  значит, скилл регистрируется **до** типа (в `deploy/bootstrap.py` — так же);
- `external_write_not_pinned` — у имени есть версия с `sideEffects:
  external_write`, а ссылка без версии. Версия типа иммутабельна — скилл, через
  который она пишет наружу, тоже должен быть неизменным. Та же проверка
  повторяется при исполнении: если незакреплённое имя к моменту решения
  резолвится в `external_write`-версию, действие падает
  `invalid_action_input` (`input: skill`), вызова нет;
- `external_write_on_rejected` — `external_write`-скилл в исходе `rejected`:
  основанием внешней записи служит только **одобренный** gate (ADR-0056 §4), при
  исполнении такой вызов всё равно был бы отклонён.

**Исполнение.** Действие вызывает ту же команду, что `POST
/skills/{ref}:invoke`, с `AuthContext` решившего: право `skills.invoke`,
`tasks.write` на задачу approval'а, `requiredPermissions` скилла — всё решившего;
`taskId` — задача approval'а, `approvalId` — решённый approval. Для скилла с
`sideEffects: external_write` этот approval и есть основание (ADR-0056 §4:
gate, `approved`, та же открытая задача, одно основание на версию скилла).
`idempotencyKey` — `approval-outcome:<approval.id>:<индекс действия>`: повтор
или replay возвращает тот же вызов, второго внешнего действия не будет. Отказ
команды (нет права, нет скилла, входы не по контракту, основание не годится)
— обычный сбой действия (п.7) с её кодом.

**Семантика.** Действие выполнено, когда вызов **поставлен в очередь**
(evidence: `invocationId`, `skill` в виде `name@version`, `status`, `created`,
`authorizationBasis`). Итог вызова — события самого `skill_invocation`
(`skill.invocation_succeeded|failed|cancelled`, артефакт `skill_result`), и на
него реагируют реакции.

**Реакции на итог — `onSuccess` и `onFailure`.** Два списка действий того же
словаря, кроме `invokeSkill` (вложенных вызовов нет: одна ступень, иначе исход
стал бы деревом). Реакции исполняются **после всех действий исхода**, в том же
плоском списке с устойчивыми индексами (после `n` основных действий; на каждый
`invokeSkill` — сначала его `onSuccess`, затем `onFailure`), и ждут (`deferred`,
`skill_pending`), пока не завершатся **все** вызовы исхода (п.4): реакция может
закрыть задачу, а ещё не взятый вызов на закрытой задаче claim отменил бы. Затем:

- вызов `succeeded` и каждое поле `expect` в output **строго** равно своему
  литералу (`true` ≠ `1`) — исполняются реакции `onSuccess`;
- иначе (`failed`, `cancelled` — в том числе по сроку ожидания, п.4 — или
  `succeeded`, но не как в `expect`: например, `git.merge` вернул `merged: false`
  с `reason: conflict | branch_moved`) — исполняются реакции `onFailure`.

Реакции другой ветки записываются `executed` с `result: {skipped: true,
invocationId}` и не исполняются.

**Основание утрачено — ни одной ветки.** Вызов, который claim отменил, потому
что основание утрачено (`error.code: basis_revoked` с `task_terminal` — задачу
approval'а закрыли, или `approval_withdrawn` — approval отозван), не исполняет
ни `onSuccess`, ни `onFailure`: обе ветки записываются `executed` с `result:
{skipped: true, reason: basis_revoked, cause: <task_terminal|approval_withdrawn>,
invocationId}`, исход завершается `executed` (событие
`approval.outcome_executed` выдаётся, `outcome_failed` — нет). Сам исход
закрыть задачу до конца вызова не может (правило ниже), значит, её закрыл
кто-то другой — типично человек вручную закрыл ревью, пока `git.merge` стоял
в очереди. Внешнее действие никто не пытался выполнить, а решение перестало
быть основанием: `onFailure` завёл бы ложную задачу «влить не удалось:
basis_revoked», `onSuccess` — отчитался бы об успехе, которого не было.
Остальные отмены — `basis_revoked` с `skill_disabled` (основание в силе, не
стало скилла), отмена по сроку ожидания (п.4), ручная отмена — по-прежнему итог
«не как ожидалось» и идут в `onFailure`: там вызов не случился, а решение
остаётся в силе, и кто-то должен узнать, что действие не выполнено. Отдельную
реакцию `onCancelled` не вводили: различать «основание утрачено» можно только
одним способом — ничего не делать, а прочие отмены типу незачем отделять от
сбоя.

**Основание утрачено без claim.** Отмена при claim закрывает гонку, только
если исполнитель Skills есть и берёт вызов. Если его нет (или он не берёт
этот вызов), `pending`-вызов остался бы в очереди, исход — `deferred`, а
через `CP_APPROVAL_OUTCOME_SKILL_WAIT_SECONDS` отмена по сроку (п.4) увела бы
в `onFailure` с ложной задачей «влить не удалось: cancelled», хотя основания
давно нет. Поэтому исполнитель исхода на каждом проходе по `pending`-вызову
проверяет основание тем же правилом, что claim (`_claim_obstacle`), и при
`task_terminal` или `approval_withdrawn` отменяет вызов сам — с тем же
`error.code: basis_revoked` и причиной в `error.message`
(`skill.invocation_cancelled` с этим `code`); дальше — ветка выше: обе реакции
skipped, исход `executed`. Проверка идёт раньше срока: истёкшее ожидание при
утраченном основании — тоже `basis_revoked`, а не `onFailure`. Прочие
препятствия claim (`skill_disabled`, `approval_required`) этот проход не
трогает: их по-прежнему решают claim и срок ожидания.

*Порядок проверок, блокировка, аудит (ревью TASK-000346).*

- **Основание — раньше версии.** Проход исхода проверяет только основание
  (`lost_basis`: задача терминальна, approval не `approved`), состояние версии
  скилла в эту проверку не входит. Выключенный `git.merge@1` на закрытом ревью
  — `basis_revoked` с `task_terminal`, а не `skill_disabled`, пропущенный
  проходом и потом превращённый сроком ожидания в ложную задачу на разбор.
  Тот же порядок причин — в claim (`_claim_obstacle`): утраченное основание
  называется раньше выключенной версии, иначе исполнитель, взявший вызов
  раньше прохода, отменил бы его с `skill_disabled` и увёл исход в
  `onFailure`. Решение claim при этом не изменилось: отменить, придержать или
  выдать — как прежде (выключенная версия по-прежнему отменяет вызов, чьё
  основание лишь придержано `approval_required`); меняется только причина в
  `error.message`, когда отменить можно по двум сразу.
- **Блокировка — по необходимости.** Проход читает `pending`-вызов,
  основание и срок **без** блокировки строки; если отменять нечего, строка
  остаётся свободной, и параллельный claim (`FOR UPDATE SKIP LOCKED`) берёт
  вызов, а не пропускает его. Только когда основание утрачено или срок истёк,
  строка берётся `FOR UPDATE` с условием `status = pending`, и под блокировкой
  статус, основание (задача и approval перечитываются из БД, а не из сессии)
  и срок проверяются заново. Гарантия прежняя: вызов, который claim успел
  взять (`running`), проход не трогает, а claim, пришедший позже блокировки,
  ждёт отмены и вызова уже не видит.
- **Кто отменил.** `error.details` отменённого вызова и payload
  `skill.invocation_cancelled` несут `cancelledBy` (principal, от чьего имени
  записана отмена) и `initiator`: `principal` — отмена по запросу (`POST
  /skill-invocations/{id}:cancel`), `system` — ядро само (утраченное основание
  при claim или в проходе исхода, истёкший срок ожидания исхода). У системной
  отмены исхода `cancelledBy` — решивший (полномочия исхода — его, п.5), но
  решение отменить принимал не он; без `initiator` аудит их не различал. Поле
  добавлено, прежние (`cancelledBy`, `wasRunning`, `code`, `reason`) не
  переименованы; в payload события `cancelledBy` тоже новое.

Исполняемые реакции идут по порядку, с
полномочиями решившего, с доступом к `$.invocation.…`; их сбой — обычный сбой
исхода (п.7), с replay.

`expect` — объект «поле output → литерал» (строка без выражений, число,
булево, `null`); без `expect` успехом считается любой `succeeded`. Почему так, а
не «ядро знает `merged`»: ответ по контракту (`merged: false`) — не ошибка
вызова, а ядро не знает смысла полей output; какое значение означает успех,
объявляет тип задачи.

**Задача закрывается по итогу вызова.** Основание `external_write`
действительно, пока задача approval'а открыта, и M2.2 перепроверяет его при
claim: вызов на закрытой задаче отменяется (`basis_revoked`, `task_terminal`),
эту гарантию шаг 2 сохраняет. Исполнитель Skills может взять вызов через
минуты — поэтому закрыть задачу в том же исходе «сразу после постановки в
очередь» значит отменить собственный вызов: merge не случился бы никогда, а
`onFailure` заводил бы ложную задачу «влить не удалось: task_terminal». Отсюда
правило публикации (`422 invalid_approval_schema`) для основного списка исхода:

- `invokeSkill` не может стоять **после** действия, которое закрывает задачу
  approval'а («invokeSkill must come before …»);
- действие, которое закрывает задачу approval'а, не может стоять **после**
  `invokeSkill` («… may not have run yet; close it in onSuccess/onFailure»).

То есть исход, который вызывает скилл, закрывает свою задачу только в
реакциях: в `onSuccess` и, если так решит тип, в `onFailure`. «Закрывает
задачу» — `completeTask` без `task` (или с `$.task.id`/`$.task.publicId`) либо
`transition` своей задачи в статус терминальной категории её lifecycle; статус
такого `transition` обязан быть литералом (п.2), иначе закрытие не распознать
при публикации. `completeTask`/`transition` **другой** задачи (например,
`$.spawnedBy.id`) правилом не ограничены.

### 11. `code-review` v4 — данные суперпроекта, не ядра

Ядро больше не сеет версий `code-review`: константа `CODE_REVIEW_APPROVAL_SCHEMA`
в миграции `e3b8c1a6d9f4` остаётся историей (миграция уже применена), новых
миграций с доменным текстом нет, в `src/` нет git-специфичного кода. Версия v4
публикуется суперпроектом (`deploy/bootstrap.py`) через обычный `POST
/task-types` — он принимает `approvalSchema` целиком и валидирует его тем же
парсером (`parse_approval_schema`) и теми же проверками по реестру (п.10), что
любую версию типа; `git.merge@1` регистрируется раньше типа. Форма v4:

- `approved` → `invokeSkill git.merge@1` с `expect {merged: true}`,
  `onSuccess: [completeTask]`, `onFailure` → `ensureWork` задачи на разбор
  исполнителю исходной задачи (`merge-fix:$.approval.id`). Ревью при неудаче
  **остаётся открытым**: merge не случился, и его закрытие решает человек;
- `rejected` → как v3, с `$.spawnedBy.description|truncate:4000`, затем
  `completeTask` (скилла в этом исходе нет, правило п.10 не мешает).

**`field_schema` v4.** Данные для входов `git.merge` кладёт демон кодера
(ADR-0052): при заведении ревью — в `customFields` ревью `repository` (URL
push-remote без учётных данных; локальный путь не публикуется), `branch`,
`commit`, `targetBranch` (база ветки — ветка, от которой пул режет копии); то
же — в metadata артефакта `commit`. v3 копирует `field_schema` v2, которую
публиковал суперпроект; из ядра её не видно (у исполнителя этой задачи нет
`task_types.read` на staging). Требование к v4: `field_schema` **должна
пускать** эти четыре поля — объявить их (`type: string`) в `properties`, и если
в схеме `additionalProperties: false`, иначе `POST /tasks` ревью с ними даёт
`422 custom_fields_invalid`. Чтобы до v4 (или при такой схеме) демон не
перестал заводить ревью совсем, он при `custom_fields_invalid` повторяет
создание **без** `customFields` и пишет предупреждение в лог: ревью появится,
а её merge упадёт видимо (`unresolved_expression`, задача на разбор решившему)
вместо merge по догадке. Решившему ревью нужны ещё `skills.invoke` (и права,
которые объявляет скилл).

## Последствия

- Цикл «ревью → правки → ревью» замыкается без человека между решением и
  следующей задачей; человек только решает approval и пишет причину.
- Ядро по-прежнему не знает ни `merge`, ни `review`: всё специфичное — данные
  типа задачи.
- Действия исхода атрибутированы решившему и ограничены его правами: gate
  нельзя использовать, чтобы сделать руками ядра то, что решивший сделать не
  мог.
- Downgrade миграции lossy: колонка, состояние исходов и журнал действий
  удаляются; добавленные версии `code-review` остаются копиями предыдущих
  (удалять версию запрещает триггер, на неё могут ссылаться задачи).

## Ограничения

- Допустим и исполняется только гейт `default`; именованные гейты — когда у
  approval появится имя гейта.
- `invokeSkill` ставит вызов в очередь; исполняет его исполнитель Skills (M2.2).
  Вызов, который никто не берёт, держит реакции в `deferred` не дольше
  `CP_APPROVAL_OUTCOME_SKILL_WAIT_SECONDS` (п.4), потом отменяется и идут
  реакции `onFailure`; с утраченным основанием он снимается на ближайшем
  проходе исхода (`basis_revoked`, п.10); без реакций исход завершается сразу после постановки в
  очередь.
- Реакция узнаёт об итоге вызова опросом (раз в `CP_APPROVAL_OUTCOME_DEFER_SECONDS`),
  а не по событию завершения вызова.
- Реакции — одна ступень: `onSuccess`/`onFailure` не вызывают скиллов. Реакции
  всех вызовов исхода ждут самого долгого из них.
- Контекст `$.…` снимается один раз на исполнение (и на каждый replay).
- Набор прав решившего берётся **снимком на момент решения** (п.5): если после
  решения права в IAM binding урезали, в режиме `local` исход этого не видит до
  нового решения (replay решившим подставляет текущий credential, но replay
  доступен только упавшему или зависшему исходу).
  Отзыв/отключение binding'а видны сразу (проверка credential'а), в режиме
  `policy` каждое действие решает PDP по текущему состоянию.
- `deferred` по claim не ограничен по времени: его держит только живой claim, а
  claim истекает по TTL или вместе с сессией.

Основание: TAI-ADR-0047, «Порядок реализации» п.2 — цикл spec-driven как цепочка
шагов без потерь; TASK-000378. Семантика существующих исходов approval не
меняется: всё ниже — новые необязательные входы и новый необязательный раздел
версии типа.

### Проблема

(а) `ensureWork` не умел задать поля создаваемой задаче: шаг пакета sdd
(`feature-design` → `feature-tasks`) передавал slug фичи, ветку и репозиторий
только текстом в `description`, и следующий шаг не мог сослаться на них через
`$.task.customFields.…`. (б) «После успешного `coding-task` с опубликованной
веткой завести ревью» было зашито в демоне раннера (ADR-0052,
`control_plane_agent/review.py`): тип задачи этого не объявлял, и задача,
завершённая другим исполнителем (харнесс человека, исход approval), цепочку не
получала.

### А1. `ensureWork.customFields`

Необязательный вход `customFields: {имяПоля: строка}`. Имя поля —
`[A-Za-z_][A-Za-z0-9_]*`, не больше 32 полей; значение — та же строка
грамматики п.3: одно выражение (сырое значение), шаблон, `!`, `|truncate:N`.

- **При публикации** проверяется только форма (объект, имена, строки,
  выражения) — `422 invalid_approval_schema`. Целевой тип может быть задан
  выражением, поэтому его `field_schema` при публикации неизвестна.
- **При исполнении** значения рендерятся; значение, разрешившееся в `null` или
  `""`, **опускается** (не записывается пустым): обязательное по схеме поле тогда
  упадёт как отсутствующее, а `!` в выражении роняет раньше —
  `unresolved_expression`. Результат проверяется по `field_schema` той версии
  целевого типа, под которой задача создаётся (новейшая активная по ключу), тем
  же кодом, что `POST /tasks`: **`custom_fields_invalid`**. Это обычный отказ
  действия (п.7): записи действия откатываются, исход `failed`, остальные
  действия остаются `not_executed` и выполняются replay'ем после исправления
  (например, новой версии целевого типа) — ничего не теряется.
- **Идемпотентность**: `ensureWork` находит задачу по `key` и возвращает её
  (`created: false`) **без перезаписи полей** — «ensure», не upsert.
- Разрешено везде, где разрешён `ensureWork`: в исходах, в реакциях
  `onSuccess`/`onFailure` (с `$.invocation.output.…`) и в работе после
  завершения (А3).
- В evidence действия — только **имена** заданных полей (`customFields: [..]`),
  не значения: журнал читают шире, чем задачу (ADR-0015).

### А2. `ensureWork.requestApproval`

Необязательный вход `requestApproval: {assignee, comment?}` — gate-approval на
**только что созданной** задаче, назначенный `assignee` (id principal'а, строка
грамматики п.3). Тот же командный путь, что `POST /approvals` с `gate: true`,
с полномочиями того, кто исполняет действие (`approvals.manage`), в той же
savepoint, что создание задачи: не удалось запросить approval — не создана и
задача. На найденной по `key` задаче второй approval не открывается. Это то,
что демон делает для человеческого ревью (ADR-0052, амендмент 2026-09-23), —
теперь выразимо декларацией. В результате действия — `approvalId`.

### А3. `task_types.completion_schema` — работа после завершения

Новая колонка версии типа (миграция `a4c7e2f9b1d3` на `ffbbd22726d3`, триггер
неизменяемости пересоздан с ней, как в `ffbbd22726d3`), в API —
`completionSchema`, `{}` — ничего (поведение до амендмента). Отдельный документ,
а не ключ внутри `approvalSchema`: у завершения нет решения и гейта, а
`approvalSchema` описывает именно исходы гейта.

```json
{"onComplete": {
  "when": ["$.task.artifact[commit].metadata.published",
           "$.task.artifact[commit].metadata.branch"],
  "actions": [
    {"ensureWork": {"type": "code-review", "key": "code-review:$.task.id",
      "title": "Ревью $.task.publicId: $.task.title",
      "assignee": "<reviewer>", "relation": {"spawned_by": "$.task.id"},
      "customFields": {"branch": "$.task.artifact[commit].metadata.branch!",
                       "commit": "$.task.artifact[commit].metadata.commit!"},
      "requestApproval": {"assignee": "<reviewer>",
                          "comment": "Code review $.task.publicId"}}},
    {"comment": {"body": "Ревью заведено"}}]}}
```

- **Словарь** — `ensureWork` (с `customFields`, `relation`, `requestApproval`) и
  `comment`; `completeTask`, `transition`, `invokeSkill` после завершения
  недоступны. **Корни** выражений — `$.task` (завершённая задача, включая
  `customFields` и `artifact[<type>]`) и `$.spawnedBy`; `$.approval` и
  `$.invocation` — нет: за завершением нет ни решения, ни вызова.
- **`when`** — непустой список (до 8) выражений `$.task…`/`$.spawnedBy…` без
  `|truncate`; работа заводится, только если **все** разрешились во что-то (не
  `null`, `""`, `false`). Не выполнено — ничего не заводится и не
  записывается. Без `when` — на каждое завершение. Отдельного корня `$.run` нет:
  условие «опубликован коммит» читается как новейший артефакт `commit` задачи
  (`$.task.artifact[commit].metadata.…`) — раннер пишет его до `:succeed`.
- **Ошибки публикации** — `422 invalid_completion_schema` с путём.

**Когда срабатывает — при переходе задачи в `terminal_success`, а не при успехе
run.** Единственная точка такого перехода — `finish_locked_task`: и
`POST /tasks/{ref}:complete`, и `POST /runs/{id}:succeed` (с
`completeTask: true`), и `completeTask` исхода approval проходят через неё
(`PATCH status` в терминальный успех запрещён, ADR-0048). Успех run без
завершения задачи (`completeTask: false`) — не конец работы, а задача,
закрытая человеком без run, — конец. Цель амендмента — чтобы цепочку получал
**любой** исполнитель, поэтому триггер — завершение задачи.

**Исполнение — синхронно, в транзакции завершения, с полномочиями
завершившего.** В отличие от исходов approval (worker, п.4), здесь нечего
ждать: claim своей задачи освобождается тем же завершением, решения и вызовов
нет. Полномочия — `AuthContext` того, кто завершил задачу (раннер своим ключом,
человек своим, для `completeTask` исхода — решивший approval), через тот же
authorizer; что читают выражения, завершивший должен уметь читать (`tasks.read`,
`artifacts.read` — как у решившего, п.5). Каждое действие — в своей savepoint.

**Однократность и сбой.** Таблица `task_completion_work` — одна строка на
задачу (уникальный `task_id`): `executed` или `failed`, по каждому объявленному
индексу — что сделано (evidence), кто завершил, число попыток. Строка
`executed` больше не исполняется: повторное завершение (переоткрыли и закрыли
снова) не заводит второй работы; `ensureWork` к тому же идемпотентен по `key`.
Отказ действия (`DomainError`) откатывает его записи, остальные действия не
выполняются, **завершение задачи остаётся в силе** — то, что тип заводит после
завершения, не может его отменить. Сбой записывается (строка `failed`, событие
`task.completion_work_failed` с `failedAction` и evidence) и сообщается
комментарием на завершённой задаче от системного principal'а ядра (как failure
work в п.7, но не отдельной задачей: завершивший — обычно раннер, задача ему
ушла бы в очередь агенту). Следующее завершение той же задачи продолжает с
первого невыполненного индекса. Успех — событие `task.completion_work_executed`
(`actorId` — завершивший, `actions` — evidence). Происхождение заведённой работы
(п.8, CP-ADR-0062) — `{"kind": "process", "ref": "completion:<taskId>"}`,
отметка `approval-outcome` с `metadata = {"origin": "completion", "taskId",
"actionIndex"}`. Неожиданная (не доменная) ошибка не глушится: завершение
отвечает 500 и откатывается целиком, клиент повторяет.

### А4. Демон раннера

Сторона кодера авто-ревью (ADR-0052) смотрит на версию типа завершённой задачи
(ту же, что демон уже читает для `execution`, кешируется по `typeId` —
версии неизменяемы): если в ней непустой `completionSchema`, демон ревью
**не заводит** — ядро уже сделало это в транзакции `:succeed`, второе было бы
дублем. Тип без раздела — прежнее поведение (обратная совместимость до перевода
пакетов). Тип, который раннер прочитать не может, — тоже прежнее поведение:
пропущенное ревью хуже дубля, который человек видит и закрывает. Код
`review.py` остаётся до перевода пакетов.

Путь авто-ревью демона удалён в declarative-cycle C006 (TASK-000645,
2026-09-27; ADR-0052 → Superseded): ревью и вливание — критерии приёмки типа
задачи (ADR-0067, амендмент 2026-09-27), и проверка `completionSchema` демону
больше не нужна.

### А5. Не входит

Перевод пакетов суперпроекта (core `coding-task`, selfdev `code-review-merge`,
sdd `feature-tasks`) на новые поля — харнесс владельца после вливания; Worker
Profile; чтение `task_completion_work` через API (пока — события и строка в БД);
явный replay работы после завершения (пока — повторное завершение задачи или
вручную по комментарию).

## Амендмент 2 2026-09-25: предусловия `approve` (TASK-000375)

Основание: TAI-ADR-0041 п.7 и «Порядок реализации» п.3 — сверка ADR с кодом
(`adr.conformance_check`) нашла, что `approval_precondition_failed` в ядре нет.
Наблюдения внешних систем уже приходят в ядро (ADR-0057, M1.2a), язык условий
уже есть у правил (ADR-0063), поэтому предусловия собираются из них, без нового
механизма. Семантика исходов не меняется.

### П1. `preconditions` гейта

Гейт `approval_schema` — объект с `outcomes` и/или `preconditions` (хотя бы
одним из них; гейт только с предусловиями допустим и исходов не запускает):

```json
{"gates": {"default": {
  "preconditions": {"approved": [
    {"observation": {"kind": "ci.status", "source": "ci", "task": "$.spawnedBy.id!"},
     "condition": {"eq": [{"var": "observation.data.conclusion"}, "success"]},
     "reason": "CI задачи $.spawnedBy.publicId не зелёный"}
  ]},
  "outcomes": {"approved": [...], "rejected": [...]}
}}}
```

- Предусловия бывают **только у `approved`**: отклонить можно всегда, иначе
  человек не смог бы отказать, пока, например, CI красный. `rejected` —
  `422 invalid_approval_schema`. Не больше 10 на исход.
- `observation` выбирает **самое свежее** наблюдение `observation.recorded`
  по `observedAt` (без него — по времени записи; при равенстве — позднее
  записанное): `kind` (обязательно, литерал), `source` (литерал), `task` —
  ровно одно выражение `$.task.id` или `$.spawnedBy.id` (с `!` или без),
  наблюдение привязано к этой задаче (`taskId`); `externalRef` — шаблон
  `externalRef.id` наблюдаемого объекта (например,
  `$.spawnedBy.artifact[commit].metadata.branch!`). Без `task` и `externalRef`
  — наблюдения о самой задаче approval'а. Поздно пришедшее более старое
  наблюдение свежее не перекрывает.
- `condition` — выражение языка правил ADR-0063 (`and`/`or`/`not`, сравнения,
  `in`, `exists`) с единственным корнем `observation` (payload наблюдения и
  его `id`: `observation.data.<…>`, `observation.source`,
  `observation.externalRef.id`…). Без `condition` достаточно, что наблюдение
  есть.
- `reason` — обязательный шаблон причины для решающего (до 1000 символов).
- Выражения в `task`/`externalRef`/`reason` — только корни `$.task` и
  `$.spawnedBy`: до решения `$.approval` читать нечего. Всё проверяется при
  публикации версии (`422 invalid_approval_schema`).

### П2. Проверка при `approve`

`decide_approval` для gate-approval'а перед записью решения читает
предусловия `approved` версии типа задачи и проверяет каждое. Если хотя бы одно
не выполнено — `409 approval_precondition_failed`: сообщение с причиной первого,
`details.failed[]` — все невыполненные с `index`, `kind`, `cause`
(`no_observation`, `condition_false`, `condition_error` — условие споткнулось о
тип значения, `unresolved_reference` — `task`/`externalRef` ни на что не
указывает), `reason` и `observationId` прочитанного наблюдения. Решение **не
записывается**: approval остаётся `pending`, события нет, исход не
запускается. Отказ по отсутствию данных — осознанный: ядро не одобряет то, о чём
ничего не знает.

Выражения, выбирающие наблюдение, и причина читаются **от имени решающего**
тем же путём, что входы исходов (п.3: `tasks.read` на `$.task`/`$.spawnedBy`,
`artifacts.read` для ссылок на артефакты). Само наблюдение ищет ядро: решающий
видит только вывод «выполнено / нет» и id наблюдения, а права на наблюдения
выдаёт тот, кто публикует тип (`task_types.manage`).

### П3. Ограничения

- Читается только горячий журнал: наблюдение, ушедшее в архив (ADR-0038),
  считается отсутствующим — предусловие не выполнено.
- Поиск идёт по событиям tenant'а с `entity_type = observation` без
  отдельного индекса по `kind`; при росте числа наблюдений понадобится индекс
  или проекция.
- Предусловия проверяются в момент решения; после успешного `approve` ядро их
  не перепроверяет (исход не откатывается, как и при сбое действия).
- Human Harness пока не показывает предусловия рядом с кнопками решения —
  видна только ошибка `409`.

## Амендмент 3 2026-09-30: перевод задачи на другую версию типа (TASK-001071)

Исполнитель читает `approval_schema` из версии типа, которую задача несёт **в
момент исполнения** (`declared_actions`), а не из версии на момент создания
approval. С появлением перевода задачи на другую версию типа (ADR-0048,
амендмент 2026-09-30) это значило бы, что решение, принятое под одними
исходами, исполняется по другим. Поэтому перевод отклоняется
(`409 approval_pending`), пока у задачи есть gate-approval в `pending` или
решённый с `outcomeStatus` `pending|deferred`. После исполнения (`executed`)
или провала (`failed`) исхода перевод разрешён; `:replay-outcome` провалившегося
исхода после перевода исполняет исходы новой версии — оператор, переводящий
задачу с `failed`-исходом, решает это сознательно.

## Амендмент 4 2026-10-01: адресат гейта — роль пакета `role:<slug>` (TASK-001237)

### Проблема

Приёмка S033 (TASK-000957, №12): внешний автор пакета «заявки на закупку» не
смог адресовать гейт ролью, которую пакет объявляет сам. `requestApproval.assignee`
(А2) принимал только id principal'а, `approverRole` критерия приёмки
(ADR-0067) и `request_decision` правила (ADR-0063) — только UUID роли. Id
принадлежат одной установке, поэтому пакет нёс переменную установки вида `role`
(`${FINANCE_DIRECTOR_ROLE_ID}`). Тест типа задачи к тому же не мог сказать,
кому решать нельзя: шаг `approve` знал только того, кто решает.

### Р1. `role:<slug>` в адресате гейта

Строка **`role:<slug>`** (slug роли по схеме каталога,
`^[a-z0-9][a-z0-9-]{0,62}$`) принимается наравне с прежними значениями в полях:

- `ensureWork.requestApproval.assignee` — в исходах `approvalSchema`, реакциях
  `onSuccess`/`onFailure` и в `completionSchema` (А2, А3); gate получает
  `requiredRoleId` вместо `assignedPrincipalId`;
- `spec.approverRole` критериев приёмки `human` и `llm_judge` (у типа задачи и
  у самой задачи);
- `action.fields.approverRole` правила с `request_decision`.

Id роли (UUID) принимается по-прежнему. Значение — строка грамматики поля:
шаблон (`role:$.task.customFields.approver`, `role:{{payload.data.role}}`)
разрешается после рендеринга.

### Р2. Разрешение при публикации и при открытии гейта

- **Публикация** версии типа (`POST /task-types`, `packages:apply`, проба
  плана и тест пакета) и правила (`POST /rules`, `PUT /rules/{id}`):
  литеральная ссылка должна называть роль, которая есть у tenant'а — в любом
  workspace или на уровне tenant'а. Нет — **`422 unknown_role`**,
  `details: {field, role}`; `field` — путь поля
  (`completionSchema.onComplete.actions[0].ensureWork.requestApproval.assignee`,
  `acceptance[0].spec.approverRole`, `action.fields.approverRole`), в плане
  пакета — указатель находки
  (`/spec/completionSchema/onComplete/actions/0/ensureWork/requestApproval/assignee`).
  Ссылка с неверным slug (`role:`, `role:Purchase`) — тот же `unknown_role`.
  Ссылку при публикации и при открытии гейта разбирает одна функция ядра
  (`role_reference_slug`, та же грамматика, что у `approverRole` критерия):
  ничего вокруг slug не обрезается, `role: buyer`, `role:buyer ` и шаблон,
  отрендеренный в slug с пробелом, — `unknown_role` (TASK-001277).
  `approverRole` критерия, который не UUID и не `role:<slug>`, — по-прежнему
  `invalid_acceptance_spec`. Шаблон при публикации не проверяется.
- **Открытие гейта**: slug разрешается в области задачи, на которой гейт,
  как требование роли задачи (ADR-0010): роль workspace задачи или ближайшего
  предка раньше роли уровня tenant'а. Approval хранит id найденной роли
  (`requiredRoleId`), саму ссылку ядро не хранит. Роли нет — `unknown_role`:
  действие исхода или работы после завершения проваливается и откатывает
  свою работу (п.7, А3), правило — ошибка команды (ADR-0063 п.5), критерий —
  ошибка открытия проверки.

Роль пакета публикует установщик раньше типов (вспомогательные объекты плана,
CP-ADR-0074 И1), поэтому проба плана и тест пакета видят её.

### Р3. Право решающего в тесте типа задачи

Шаг `approve` теста `subject: taskType` (CP-ADR-0074 З1) получает
необязательное `expectRefused: <код>` — как у шага `approve` теста процесса.
Решает тот же код ядра, что живое решение, поэтому гейт ролью решает только её
держатель (`given.principals`), чужой получает `not_eligible`:

```yaml
given: {principals: {approvers: [sam]}}
steps:
  - complete: {}
  - approve: {decision: approved, by: bob, expectRefused: not_eligible}
  - approve: {decision: approved, by: sam}
  - expect: {status: {category: terminal_success}}
```

Ожидаемый отказ не решает гейт, тест идёт дальше. Решение принято, а отказ
ожидался, или отказ с другим кодом — провал шага (`expected` — код,
`actual` — фактический или `null`). Если гейта нет, `expectRefused` — провал
