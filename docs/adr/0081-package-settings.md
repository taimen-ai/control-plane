## Контекст

У вертикального пакета есть параметры поведения, которые меняет администратор
организации, а не автор пакета и не оператор установки: порог согласования,
срок проверки. Сейчас они зашиты в объекты пакета или вынесены в переменные
установки, а те меняются только новым планом установки. TAI-ADR-0067 решил:
пакет **объявляет** настройки в манифесте (`spec.settings {schema,
uischema?}`), ядро **хранит** одно значение на пакет в организации и отдаёт
его объектам пакета, консоль **рисует** форму по описанию, без кода под пакет.

Что ядро должно и чего не должно:

- хранить схему настроек по ревизии пакета, значения с версией и историей,
  проверять значения по схеме и отдавать действующие значения объектам пакета;
- держать решение шага процесса воспроизводимым: replay прежнего дела после
  смены значения даёт прежнее решение;
- **не знать смысла** настроек (нейтральность, ст. II конституции, FR-017):
  ни имени поля, ни единицы, ни предметной области в коде ядра нет;
- **не хранить секретов**: секреты — подключения и секреты агентов по имени
  (CP-ADR-0079), в настройках их нет никогда.

## Решение

### 1. Объявление: подмножество JSON Schema и раскладка формы

`Package.spec.settings` манифеста (`package.yaml`, схема — package-sdk,
закреплённая копия в ядре — G003):

```yaml
spec:
  settings:
    schema:            # JSON Schema, корень — object
      type: object
      required: [approverRole]
      properties:
        approvalThreshold: {type: number, minimum: 0, default: 100000}
        reviewDueWorkdays: {type: integer, minimum: 1, maximum: 20, default: 2}
        approverRole:      {type: string, x-ref: role}
    uischema:          # необязательно; п.2
      type: VerticalLayout
      elements:
        - type: Group
          label: invoice-payment.settings.groups.approval
          elements:
            - {type: Control, scope: "#/properties/approvalThreshold"}
            - {type: Control, scope: "#/properties/approverRole"}
        - {type: Control, scope: "#/properties/reviewDueWorkdays"}
```

Имена полей примера — данные пакета-пилота, а не ядра.

**Разрешённое подмножество** (как у данных процесса): `type` (`object`,
`string`, `integer`, `number`, `boolean`, `array`), `properties`, `required`,
`enum`, `minimum`, `maximum`, `minLength`, `maxLength`, `pattern`, `format`
(`date`, `uri`, `email`, `uuid`), `items`, `minItems`, `maxItems`, `default`,
`x-ref`. Корень — `object`; вложенность объектов ≤ 3; свойств ≤ 100 **на
каждый объект**; `$ref`, `allOf/anyOf/oneOf/not`, `if/then/else`,
`patternProperties`, `additionalProperties: true` и прочее — вне
подмножества. Неизвестное свойство в значениях отвергается всегда
(`additionalProperties: false` подразумевается на каждом объекте).

**`title` и `description` в схеме пакета** вне подмножества: схема манифеста
package-sdk их не допускает, ядро отвергает их при плане
(`settings_schema_unsupported`). В ответе `GET …/settings` (п.4) они есть —
их ставит **только ядро** подстановкой строк словаря.

**`x-ref`** — значение-ссылка на объект платформы. Только у `type: string`
(или `items` массива строк). Значение по видам ссылки:

| `x-ref` | Значение |
|---|---|
| `role` | id роли организации |
| `principal` | id principal'а |
| `workspace` | id workspace (только id, не slug) |
| `taskType` | ключ типа задачи |
| `calendar` | ключ календаря |

Ключевое слово нейтрально по решению 2026-10-03 (white-label: имени продукта
нет в контрактах; ADR-0022, страж `tests/unit/test_branding.py`) — как с
профилем CEL в ADR-0075 п.1. TAI-ADR-0067 и plan фичи на ветке
суперпроекта `feature/package-settings` уже на `x-ref`. На переходе остаются
схема манифеста package-sdk (TASK-001329) и консоль: пока их правки не
влиты, там стоит прежнее имя с кодовым именем продукта, и ядро его не
принимает.

**Значения по умолчанию.** У каждого **необязательного** поля есть `default`,
и он проходит схему поля (как в схеме package-sdk): пакет работает сразу
после установки без единого сохранения (сценарий 3, SC-005). У обязательного
поля (`required`) `default` допустим, но не нужен: пока его не сохранили,
действующего значения нет (п.4, `effective`), и объект пакета обязан это
учитывать (`has(settings.<поле>)` в CEL). Ссылке на роль, principal или
workspace `default` дать нельзя по сути — id у каждой организации свой;
такое поле объявляют обязательным.

**Признаки секрета в схеме** отвергаются: `writeOnly: true`,
`format: password`, имя свойства по списку `_SECRET_KEY_HINTS`
(`domain/project.py`: `password`, `secret`, `token`, `apikey`, `privatekey`,
`credential`, `authorization`, `clientsecret` и их написания), строка
`default`/`enum` с материалом секрета (`secret_material`,
`domain/redaction.py`).

**Подписи** — ключи словаря пакета (CP-ADR-0080 п.2). Ключи выводятся из
пути поля (`<путь>` — имена свойств через точку от корня схемы, `<пакет>` —
ключ пакета):

| Строка | Ключ словаря | Обязателен |
|---|---|---|
| имя пакета (`title` ответа) | `<пакет>.title` | да, если пакет объявляет `settings` |
| подпись поля (`title` свойства) | `<пакет>.settings.<путь>` | да, у каждого свойства |
| пояснение поля (`description` свойства) | `<пакет>.settings.<путь>.help` | нет |
| заголовок группы (`label` у `Group`) | `<пакет>.settings.groups.<id>`, `<id>` выбирает автор | да |
| `label` у `Control`, `text` у `Label` | любой ключ словаря пакета | да |

Обязательный ключ должен быть в словаре каждого объявленного языка пакета
(FR-004).

Проверка ядра при плане (п.7) повторяет проверку `package-sdk check` (G008) с
теми же кодами; находки — в форме находок плана (`code`, `severity`, `path`,
`file`, `line`, `message`, `hint`). Коды объявления — `path` от
`/spec/settings`:

| Код | Когда |
|---|---|
| `settings_schema_unsupported` | конструкция вне подмножества (в том числе `title`/`description`), корень не `object`, пределы глубины или числа свойств объекта, `x-ref` неизвестного вида (не из таблицы выше), `x-ref` не у строки и не у `items` массива строк |
| `settings_default_missing` | у необязательного поля нет `default` |
| `settings_default_invalid` | `default` не проходит схему поля |
| `settings_secret_field` | признак секрета в схеме (выше) |
| `settings_uischema_unsupported` | `uischema` вне подмножества п.2 |
| `settings_label_missing` | обязательного ключа подписи нет в словаре языка (в сообщении — язык и ключ) |

Коды ссылок — у объектов пакета, которые читают настройки (п.6: процессы,
правила, виды); `path` — путь выражения в объекте (`/spec/...` файла
объекта), в сообщении — путь `settings.<путь>`:

| Код | Когда |
|---|---|
| `settings_ref_unknown` | ссылка `settings.<путь>` на поле, которого нет в схеме настроек пакета объекта (в том числе у объекта, пакет которого настроек не объявляет) |
| `settings_ref_type` | ссылка `settings.<путь>` на объявленное поле, тип которого не подходит месту выражения (число в условии, объект в шаблоне строки и т. п.) |

### 2. `uischema` — закрытое подмножество JSON Forms

`uischema` — контракт между пакетом, ядром и консолью: консоль рисует ровно
это подмножество JSON Forms на компонентах дизайн-системы, ядро отвергает
остальное при плане (`settings_uischema_unsupported` с путём от
`/spec/settings/uischema`). Расширение набора — амендмент этого ADR.

Элементы:

| `type` | Поля | Что |
|---|---|---|
| `VerticalLayout` | `elements` | элементы столбцом |
| `HorizontalLayout` | `elements` | элементы в строку |
| `Group` | `label`, `elements` | рамка с заголовком; `label` обязателен |
| `Control` | `scope`, `label?` | поле формы |
| `Label` | `text` | строка текста |

У любого элемента — необязательное `rule`. Других полей у элементов нет:
`options`, `i18n`, `Categorization`/`Category`, `ListWithDetail`, свои
рендереры — вне подмножества.

- **`scope`** — JSON Pointer в форме JSON Forms: `#/properties/<имя>`,
  вложенное — `#/properties/<a>/properties/<b>`. Он указывает на
  существующее свойство схемы; указатель внутрь `items` массива и на корень
  — вне подмножества. Одно свойство — не более одного `Control`.
- **`label`**, **`text`** — ключи словаря пакета, не текст (п.1). У `Group`
  ключ — вида `<пакет>.settings.groups.<id>`. `Control` без `label`
  подписан `title` своего свойства (п.1).
- **`rule`** — `{effect, condition}`: `effect` — `SHOW`, `HIDE`, `ENABLE`
  или `DISABLE`; `condition` — только условие по схеме: `{scope, schema,
  failWhenUndefined?}`, где `scope` — указатель на свойство (как у
  `Control`), а `schema` — подмножество п.1 без `x-ref` и `default` (обычно
  `const`, `enum`, `minimum`/`maximum`; `const` разрешён только здесь).
  Составные условия (`OR`, `AND`, `LEAF`) — вне подмножества.
- **Корень** — `VerticalLayout`, `HorizontalLayout` или `Group`; вложенность
  ≤ 5; элементов всего ≤ 200.
- Нет `uischema` — консоль строит `VerticalLayout` из `Control` по порядку
  свойств схемы (вложенный объект — `Group` с подписью поля).
- Свойство схемы без `Control` в заданной `uischema` — предупреждение плана
  `settings_uischema_uncovered`: значение действует, но в форме его не
  поменять.

`rule` только меняет вид формы: скрытое или выключенное поле сохраняется и
проверяется, как любое другое, и `PUT` (п.4) правил `uischema` не исполняет.

### 3. Данные: три таблицы

Одна цепочка alembic (G004). Все таблицы — с `tenant_id`; изоляция tenant'а,
как у остальных таблиц ядра, — фильтром `tenant_id` в каждом запросе (RLS в
ядре нет). Две оси независимы: **ревизия схемы** меняется
только применением пакета, **версия значений** — только `PUT` (п.4).

**`package_settings_schemas`** — схема по ревизии, только вставка:

| Колонка | Что |
|---|---|
| `id` | uuid |
| `tenant_id`, `package_key` | пакет |
| `revision` | int, 1, 2, … в пределах `(tenant_id, package_key)`; новая — когда меняется хэш |
| `package_version` | версия пакета, которая её поставила |
| `schema`, `uischema` | jsonb, как в манифесте (ключи подписей, без подставленных строк); `uischema` — `null`, если не задана |
| `schema_hash` | `sha256` канонического JSON `{schema, uischema}` (`canonical_hash`) |
| `active` | bool; ровно одна активная ревизия на пакет (частичный уникальный индекс) или ни одной |
| `plan_hash`, `applied_by`, `applied_at` | применение, которое её записало |

Уникально `(tenant_id, package_key, revision)`. Строки рядом с
`package_dictionaries` (CP-ADR-0080) — то же «что относится к пакету целиком,
по ревизии». В `package_objects` схема не идёт: у настроек нет вида и ключа
объекта, `ck_package_objects_kind_known` не меняется. Схема ревизии
неизменяема: `default` ревизии R — опора replay (п.6).

**`package_settings`** — текущее значение, одна строка на пакет; появляется
при первом `PUT`:

| Колонка | Что |
|---|---|
| `tenant_id`, `package_key` | первичный ключ |
| `values` | jsonb — **сохранённые** значения (только то, что задал человек) |
| `version` | int ≥ 1, номер последней версии в истории |
| `schema_revision` | ревизия схемы, по которой значения проверены при сохранении |
| `updated_by`, `updated_at` | автор и время |

Строки нет — версия 0: ничего не сохраняли, `values = {}`.

**`package_settings_versions`** — история сохранений, только вставка:

| Колонка | Что |
|---|---|
| `tenant_id`, `package_key`, `version` | первичный ключ; `version` — 1, 2, … без пропусков |
| `values` | сохранённые значения версии |
| `schema_revision` | ревизия схемы, по которой они проверены |
| `changed_paths` | text[] — JSON Pointer полей, у которых сохранённое значение отличается от прошлой версии (поле добавлено, изменено или убрано — то есть вернулось к `default`) |
| `updated_by`, `updated_at` | автор и время |

Версия появляется **только от `PUT`**. Установка пакета и смена схемы версию
не трогают и строк истории не пишут. Строки истории не удаляются и не
изменяются, в том числе когда пакет перестаёт объявлять настройки.

**Действующие значения** (`effective`) пары «версия N, ревизия R» —
сохранённые значения версии N (при N = 0 — `{}`) поверх `default` схемы
ревизии R, по пути поля: вложенные объекты сливаются по полям, массив —
целиком; сохранённое поле, которого нет в схеме R, не входит. Обе строки
неизменяемы, поэтому пара однозначно называет значения, которые видел объект
пакета, — это опора replay (п.6).

### 4. API

Все маршруты — уровень tenant. `{key}` — ключ пакета (`package_objects.
package_key`, `package.yaml → metadata.name`). Неизвестные параметры запроса —
`400` по ADR-0058. Ошибки — в общем конверте ядра `{"error": {code,
message, details, requestId}}`. OpenAPI — в G004.

**Пакет установлен**, если у tenant'а есть строка `package_objects` с этим
`package_key` или ревизия `package_settings_schemas` этого пакета. Иначе —
`404 package_not_installed`. Пакет установлен, но активной ревизии схемы нет
(настроек не объявляет или перестал объявлять) — `404
settings_not_declared` на все маршруты `…/{key}/settings…`.

**Язык строк** — `?locale=<тег>`. Строка ищется в словаре запрошенного языка,
затем его базового (`ru-RU` → `ru`, без учёта регистра), затем
`defaultLocale` пакета; нет нигде — подставляется сам ключ. Нет `?locale=` —
`defaultLocale`. Порядок тот же, что у видов (CP-ADR-0080 §5).

**`GET /api/v1/package-settings?locale=`** (`packages.settings.read`) —
перечень пакетов с настройками:

```json
{
  "items": [
    {"package": "invoice-payment", "title": "Оплата счетов", "packageVersion": "1.3.0",
     "version": 3, "updatedBy": "8f1c…", "updatedAt": "2026-10-03T09:00:00Z"}
  ]
}
```

Только пакеты, у которых есть активная ревизия `package_settings_schemas`,
по `package` по возрастанию; постраничности нет (пакетов в организации —
единицы). `title` — строка `<пакет>.title`; `packageVersion` — версия пакета
активной ревизии; `version: 0`, `updatedBy: null`, `updatedAt: null` —
ничего не сохраняли.

**`GET /api/v1/packages/{key}/settings?locale=`** (`packages.settings.read`).
Ответ `PackageSettingsOut`, заголовок `ETag: "package-settings-<version>"`
(`api/etag.py`):

```json
{
  "package": "invoice-payment",
  "title": "Оплата счетов",
  "packageVersion": "1.3.0",
  "schema": {
    "type": "object",
    "required": ["approverRole"],
    "properties": {
      "approvalThreshold": {"type": "number", "minimum": 0, "default": 100000,
        "title": "Порог согласования", "description": "Сумма, выше которой нужен второй подписант"},
      "reviewDueWorkdays": {"type": "integer", "minimum": 1, "maximum": 20, "default": 2,
        "title": "Срок проверки, рабочих дней"},
      "approverRole": {"type": "string", "x-ref": "role", "title": "Роль согласующего"}
    }
  },
  "uischema": {"type": "VerticalLayout", "elements": [
    {"type": "Group", "label": "Согласование", "elements": [
      {"type": "Control", "scope": "#/properties/approvalThreshold"},
      {"type": "Control", "scope": "#/properties/approverRole"}]},
    {"type": "Control", "scope": "#/properties/reviewDueWorkdays"}]},
  "values": {"approvalThreshold": 150000, "approverRole": "5b2e…"},
  "effective": {"approvalThreshold": 150000, "reviewDueWorkdays": 2, "approverRole": "5b2e…"},
  "version": 3,
  "schemaHash": "sha256:…",
  "updatedBy": "8f1c…",
  "updatedAt": "2026-10-03T09:00:00Z",
  "canManage": true
}
```

- `title` — имя пакета, строка `<пакет>.title`.
- `packageVersion` — версия пакета активной ревизии схемы; `schemaHash` —
  её `schema_hash`.
- `schema`, `uischema` — активной ревизии, **со строками, подставленными
  прямо в описание**, как у видов (CP-ADR-0080 §5): `title` свойства ←
  `<пакет>.settings.<путь>`, `description` ← `<пакет>.settings.<путь>.help`
  (нет ключа ни в одном словаре — `description` нет), `label` у `Group` и
  `Control` и `text` у `Label` ← строка своего ключа. Отдельной карты строк
  в ответе нет. `uischema` — `null`, если автор её не задал: консоль строит
  раскладку по умолчанию сама (п.2).
- `values` — **сохранённые** значения (то, что задал человек) версии
  `version`, только поля активной схемы; `{}` при `version: 0`.
- `effective` — действующие значения (п.3): `values` поверх `default`
  активной ревизии. Обязательного поля без `default`, которое не сохраняли,
  в `effective` нет.
- `version` — номер последней версии; `0` и `updatedBy: null`,
  `updatedAt: null` — ничего не сохраняли, `ETag: "package-settings-0"`.
- `canManage` — есть ли у вызывающего право `packages.settings.manage`.

**`PUT /api/v1/packages/{key}/settings`** (`packages.settings.manage`),
`If-Match: "package-settings-<version>"` обязателен (как у правил и
workspace, `api/etag.py`; до первого сохранения — `"package-settings-0"`).
Тело — сохранённые значения **целиком**:

```json
{"values": {"approvalThreshold": 150000, "approverRole": "5b2e…"}}
```

Поле, которого нет в теле, возвращается к `default`. Других полей в теле
нет. Откат к прежней версии — `PUT` значений этой версии из истории.

Порядок проверки — от дешёвого к содержательному; первая сработавшая отвечает:

1. `If-Match` нет — `428 if_match_required`; не той формы — `400
   invalid_if_match`.
2. Пакет не установлен — `404 package_not_installed`; активной ревизии нет —
   `404 settings_not_declared`.
3. Материал секрета в любой строке тела, **включая имена членов** объектов —
   `422 secret_material_rejected`, `details.errors: [{path}]`: `path` — JSON
   Pointer строки (`/note`), для имени члена — путь объекта, в котором он
   стоит (`/` — корень `values`). **Значения в ответе нет**; поля `field` и
   `match` (вид найденного материала, без самого материала) допустимы только
   в дополнение к `path`. Тот же код и тот же поиск, что у `settings`
   подключения (CP-ADR-0079 п.4). Проверка идёт до схемы: значение не
   попадает ни в базу, ни в журнал, ни в эхо ошибки схемы.
4. Значения не по схеме активной ревизии — `422 settings_invalid`,
   `details.errors: [{path, code, message?}]` — все нарушения сразу; `path` —
   JSON Pointer поля (`/approvalThreshold`), `code` — ключевое слово JSON
   Schema (`type`, `minimum`, `enum`, `required`, `additionalProperties`, …),
   `message` — пояснение без значения.
5. `x-ref` на объект, которого нет в организации (роль, principal, workspace,
   календарь, тип задачи tenant'а) или который выведен из оборота, — `422
   unknown_ref`, `details.errors: [{path, ref}]`, `ref` — вид ссылки.
6. `If-Match` не совпал с текущей версией — `409 version_conflict`,
   `details.currentVersion`. Проверка — под блокировкой (`SELECT … FOR
   UPDATE` строки `package_settings`; до первого сохранения — вставка с
   конфликтом по первичному ключу), поэтому из двух одновременных `PUT` с
   одной версией проходит ровно один.

**Сравнение с сохранённым.** Тело совпадает с текущими сохранёнными
значениями (канонический JSON, сравнение `values` целиком) — `200` с текущим
состоянием, новой версии и события нет. Так и с пустым телом: `{"values":
{}}` при `version: 0` или при сохранённом `{}` ничего не создаёт, а при
непустом сохранённом — новая версия, все поля возвращаются к `default`.
Иначе в одной транзакции: строка `package_settings`, строка истории,
событие (п.5). Ответ — `200 PackageSettingsOut` нового состояния с новым
`ETag`.

**`GET /api/v1/packages/{key}/settings/versions?limit=&cursor=`**
(`packages.settings.read`) — история сохранений, новые первыми:

```json
{
  "items": [
    {"version": 3, "values": {"approvalThreshold": 150000, "approverRole": "5b2e…"},
     "changedPaths": ["/approvalThreshold"], "updatedBy": "8f1c…",
     "updatedAt": "2026-10-03T09:00:00Z"}
  ],
  "nextCursor": null
}
```

`limit` — 1…100, по умолчанию 50; вне пределов — `422 invalid_limit`, как у
прочих списков ядра (`clamp_limit`, `docs/api.md`). `cursor` —
непрозрачный, по `version`. Версии 0 в истории нет. `values` — сохранённые
значения версии, как они были записаны: по ним консоль показывает diff и
предлагает откат. Это не секреты (п.1, п.4.3), поэтому чтение истории даёт
то же право, что и чтение текущих значений.

### 5. Права и событие

| Право | Ресурс | Что даёт |
|---|---|---|
| `packages.settings.read` | tenant | `GET /package-settings`, `GET …/settings`, `GET …/settings/versions` |
| `packages.settings.manage` | tenant | `PUT …/settings` (чтение — отдельным правом); `canManage` в ответе |

Права независимы от `packages.plan` (FR-009): ставить код пакета и менять его
пороги — разные роли. Имена — в `Permission` и `authz/catalog.yaml`.
Объектам пакета права не нужны: процесс, правило, вид, агент и скилл читают
настройки **своего** пакета по связи `package_objects` (п.6, п.8), а чужих не
читают ничем.

**`package.settings_changed`** (сущность `package`, v1) — при каждой новой
версии, то есть при каждом `PUT`, который её создал:

```json
{
  "package": "invoice-payment",
  "version": 3,
  "previousVersion": 2,
  "schemaRevision": 2,
  "changedPaths": ["/approvalThreshold"],
  "actorId": "8f1c…"
}
```

**Значений в событии нет** (FR-010): ни прежних, ни новых, ни `default`. Кто
хочет значения — читает `GET …/settings/versions` по праву. Применение
пакета с новой ревизией схемы этого события не порождает.

### 6. `settings` в процессах, правилах и видах

**Чей пакет.** Объект знает свой пакет по `package_objects.package_key` (кинд
и ключ объекта). У объекта без связи — созданного вручную — имени `settings`
нет: ссылка на `settings` в нём отвергается при публикации кодом
`settings_ref_unknown` с путём выражения (в сообщении — «объект не из
пакета»).

**Коды находок.** Ссылки `settings.*` в процессах, правилах и видах
проверяются по схеме активной ревизии (при плане — по схеме из присланных
файлов пакета) одинаково у ядра и у `package-sdk check` (G008): поле не
объявлено — `settings_ref_unknown`, тип поля не подходит месту выражения —
`settings_ref_type` (п.1, коды ссылок); `path` — путь выражения в объекте.
При плане это находки плана (severity `error`), при публикации объекта
через API вне плана — те же коды отказа публикации с тем же путём. Прочие
ошибки выражения — прежние коды профиля и объекта (`expression_type_error`,
`invalid_rule`, `undeclared_path` для `data`); необъявленное поле или
неподходящий тип в ссылке `settings.*` ими не отмечаются.

**Процессы.** В профиле CEL `cp/1` (ADR-0075 п.2) — переменная `settings`,
тип — из схемы активной ревизии настроек пакета процесса по тем же правилам
перевода JSON Schema, что у `data` (`x-ref` — `string`). Добавление
переменной профиль не меняет: определения, где её нет, вычисляются как
прежде. Публикация версии процесса проверяет пути `settings.*` по схеме:
необъявленный путь — `settings_ref_unknown`, неподходящий тип —
`settings_ref_type`, с путём выражения.

Значения читаются **один раз на транзакцию шага** — действующие значения
(п.3) текущей версии `package_settings` и активной ревизии схемы (та же
транзакция, что пишет запись журнала). Смена значения действует на следующее
вычисление без плана и без новой версии процесса (SC-001); дело, уже
прошедшее шаг, не меняется.

**Версия в журнале.** Если версия определения процесса ссылается на
`settings` хоть в одном выражении (статически, по разбору при публикации), то
каждая запись журнала экземпляра `process_instance_events`, которую пишет
движок, несёт пару `settings_version` и `settings_schema_revision` (новые
колонки, int, `null` у остальных) — версию значений (в том числе `0`) и
ревизию схемы, которые видел шаг. В API журнала — `settingsVersion` и
`settingsSchemaRevision` записи. Процессы без `settings` журнал не меняют.

**Правило replay.** Replay (ADR-0074 п.10, `:replay`, пробный прогон
`given.fromInstance`, план с поведенческим diff) подаёт шагу записи
действующие значения пары записи (п.3): сохранённое версии
`settings_version` из `package_settings_versions` поверх `default` ревизии
`settings_schema_revision` из `package_settings_schemas`, а не текущие.
Решение прежнего дела после смены значения или схемы воспроизводится
(FR-013, SC-002). Ревизия семантики движка (`ENGINE_REVISION`) **не
меняется**: прежние журналы `settings` не читают, их решения не меняются.
Запись, версии или ревизии которой нет в базе, — расхождение replay
`{kind: "settings", journalSeq, recorded: {version, schemaRevision}}`, а не
подстановка текущих значений. Миграция экземпляра (`migrate`) на версию
процесса, читающую `settings`, начинает писать пару со следующей записи.

**Правила вывода работы.** В контексте оценки — корень `settings` наряду с
`trigger`, `payload`, `goal`, `task` (ADR-0063): в условиях
`{"var": "settings.<путь>"}`, в шаблонах `{{settings.<путь>}}`. Правило знает
пакет по `package_objects` вида `WorkRule`. Значения читаются один раз на
оценку; пара — в `evidence` оценки (`rule_evaluations.evidence`) отдельным
элементом `{"kind": "settings", "package": "<key>", "version": <n>,
"schemaRevision": <r>}`. Проверка правила при публикации отвергает путь
`settings.*`, которого нет в схеме (`settings_ref_unknown`), и поле
неподходящего типа (`settings_ref_type`), с путём условия или шаблона.

**Виды.** В выражениях вида (`View`, CP-ADR-0080; запрос под вид —
TASK-001299) — переменная `settings` с типами из схемы пакета вида; проверка
при плане — по тем же правилам, что у `data`, но с кодами ссылок настроек:
`settings_ref_unknown` вместо `undeclared_path`, `settings_ref_type` вместо
`expression_type_error`, с путём выражения вида.
Реализуется после вливания TASK-001299 (G005).

**Песочница тестов пакета** (`POST /packages:test`, ADR-0074 п.10 и З1–З8):
`given.settings` — сохранённые значения на начало сценария, шаг `settings:
{...}` — смена посреди сценария; оба проверяются по схеме пакета из
присланных файлов (как п.4, коды — `settings_invalid`, `unknown_ref`,
`secret_material_rejected`) и пишут версии во временную историю песочницы.
Нет `given.settings` — версия 0, действуют значения по умолчанию. Формы
шагов — `test.schema.json` package-sdk (G002).

### 7. Раздел `settings` плана пакета

`POST /packages:plan` сравнивает `spec.settings` из файлов пакета с активной
ревизией и отдаёт `settings` в `PackagePlanOut` (`null`, если пакет настроек
не объявлял и не объявляет):

```json
"settings": {
  "schemaRevision": {"before": 1, "after": 2},
  "added":        [{"path": "/reviewDueWorkdays", "default": 2}],
  "removed":      [{"path": "/legacyLimit", "saved": true}],
  "incompatible": [{"path": "/approvalThreshold", "code": "maximum"}],
  "uischemaChanged": true
}
```

- `schemaRevision.after` — `null`, если хэш не меняется (ревизия та же), или
  если пакет перестаёт объявлять настройки;
- `added` — новое поле и его `default` (у обязательного поля без `default` —
  без него);
- `removed` — поле ушло из схемы; `saved` — было ли у него сохранённое
  значение. Сохранённое значение удалённого поля остаётся в истории и в
  строке `package_settings`, но в `values` и `effective` ответа не
  попадает;
- `incompatible` — сохранённое значение (а не `default`) не проходит схему
  новой ревизии: путь и ключевое слово, без значения. Каждый элемент — ещё и
  находка плана `settings_incompatible` (severity `error`, `path` —
  `/spec/settings/schema/...` поля); `apply` такого плана — `422
  invalid_package`. Автоматической миграции значений нет (TAI-ADR-0067,
  открытый вопрос): администратор правит значение `PUT`, затем план
  строится заново.

Раздел входит в `planHash` (как `processes`), активная ревизия схемы и версия
значений — в `catalogEtag`: значение, сохранённое между `plan` и `apply`,
даёт `409 plan_stale`.

`POST /packages:apply` в той же транзакции записывает новую ревизию схемы
(`active`, прежняя — `active = false`). Версия значений, история и событие
`package.settings_changed` при этом не меняются: действующие значения
следующего шага — те же сохранённые поверх `default` новой ревизии (п.3).
Пакет перестал объявлять настройки — активной ревизии нет: объекты пакета
больше не читают `settings`, маршруты отвечают `404 settings_not_declared`,
история сохраняется. Объект пакета, который в той же установке ещё ссылается
на `settings`, — находка `settings_ref_unknown` этого объекта (п.6).

Удаления пакета из установки в ядре нет (у пакета нет записи, кроме связей
его объектов); пакет без объектов и без ревизии — `404
package_not_installed`, история при этом остаётся в базе.

### 8. Агент и скилл

**`GET /agents/me`** — поле `packageSettings` в ответе:

```json
"packageSettings": {"package": "invoice-payment", "version": 3, "schemaRevision": 2, "values": {"...": 0}}
```

— `values` — действующие значения (п.3) пакета **описания агента**
(`package_objects` вида `Agent`); `null`, если агент не из пакета или
пакет настроек не объявляет. Отдельного маршрута и права нет: `GET
/agents/me` уже отдаёт агенту его описание. Настройки чужого пакета агенту
не доступны ничем.

**Вызов скилла.** Ответ `POST /skill-invocations:claim` (ADR-0056) несёт
рядом с `skill` поле `settings` той же формы `{package, version,
schemaRevision, values} | null` — действующие значения пакета **скилла**
(`package_objects` вида `Skill` по имени скилла), прочитанные при выдаче
вызова. Значение закрепляется за попыткой вызова: повтор попытки получает
значения на момент своей выдачи. В skill-sdk — `ctx.settings` (G007). Скилл
не из пакета — `null`.

### 9. Нейтральность

Ядро хранит, проверяет по схеме и отдаёт значения; смысла полей не знает
(FR-017). Доказательства (G004): тест нейтральности на двух пакетах не из
разработки ядра (`invoice-payment` и тестовый пакет) одним кодом и страж: в
`src/` ядра нет имён полей пилота.

## Последствия

- Администратор меняет параметр пакета без новой версии пакета и без плана;
  смена действует на следующее вычисление шага, правила или вида.
- Журнал экземпляра процесса, читающего `settings`, получает колонки
  `settings_version` и `settings_schema_revision`; replay таких дел зависит
  от истории настроек и ревизий схемы — их строки не удаляются.
- `version` значений означает ровно «сколько раз сохраняли»: консоль и
  `If-Match` не ломаются от обновления пакета.
- План пакета не даёт поставить версию, с которой сохранённое значение
  несовместимо; администратор сначала правит значение.
- Консоль строит форму по `GET …/settings` одним компонентом для настроек
  пакета и `settings` подключения (CP-ADR-0079), только по подмножеству п.2,
  без своего словаря: строки уже в описании.
- Схема манифеста package-sdk получает `spec.settings` с ключевым словом
  `x-ref` (G002, переход — TASK-001329), закреплённая копия в ядре — G003;
  консоль переходит на `x-ref` парной правкой. TAI-ADR-0067 и plan фичи
  уже на `x-ref`.

## Не принято

- **Ключевое слово ссылки с кодовым именем продукта** (прежнее имя в
  первой редакции TAI-ADR-0067 и plan): кодовое имя в контрактах запрещено (ADR-0022,
  ADR-0040, решение 2026-10-03). Принято нейтральное `x-ref`.
- **`412` на устаревший `If-Match`**: в ядре конфликт версии — `409
  version_conflict` у всех ресурсов с версией (workspace, правила, роли,
  скиллы), как и в plan; консоль и клиенты обрабатывают его одинаково.
- **Новая версия значений при установке и смене схемы**: `version` API
  менялась бы без действия администратора и сбивала бы `If-Match` консоли.
  Опора replay — пара «версия значений, ревизия схемы» (п.3, п.6).
- **Отдельный откат (`restoreFrom`)**: откат — `PUT` значений выбранной
  версии истории, с той же проверкой и тем же событием.
- **Карта строк рядом со схемой** (`messages`) и `title`/`description` в
  схеме пакета: строки подставляет ядро, как у видов (CP-ADR-0080 §5).
- **Схема в `package_objects`**: у настроек нет вида и ключа объекта.
- **Отдельный вид каталога `Settings`**: лишняя сущность (ст. VIII).
- **Копия значений в данные экземпляра при старте**: значение «замерзает» на
  всё дело, смена порога не действует на ещё не вычисленные шаги.
- **Подстановка значений в определение при публикации**: это переменная
  установки, а не настройка.
- **Секретные поля с шифрованием**: второе хранилище секретов.
- **Сброс несовместимого значения к `default` при обновлении**: администратор
  теряет решение без следа.
- **Настройки уровня workspace, личные, чтение чужих настроек пакетом,
  `x-migrate`** — открытые вопросы TAI-ADR-0067, не в этой фиче.

## Conformance

- G004: unit схемы (подмножество, `title`/`description` отвергнуты, секреты,
  `default` у необязательных полей, предел свойств на объект, совместимость
  двух ревизий, подмножество `uischema` — по случаю на каждый элемент и
  запрет, коды находок п.1); integration — перечень пакетов (только с
  активной ревизией, `version: 0` без сохранений), форма ответа `GET` по
  примерам `docs/settings.md` консоли (подставленные строки, `values` и
  `effective`, `canManage`, порядок языков), сохранение, отказ по каждому коду
  п.4 (`secret_material_rejected` без значения, путь члена — путь объекта),
  `404 settings_not_declared`, пустой и повторный `PUT` без новой версии,
  гонка двух `PUT` с одной версией (в том числе первых, с
  `"package-settings-0"`: проходит один, второй — `409 version_conflict`),
  история с `limit`/`cursor`, права `read`/`manage`, событие без значений,
  установка и смена схемы не меняют `version`, план с тремя видами изменения
  схемы, секрет не сохраняется и не попадает в журнал событий; одна голова

## Амендмент 2026-10-03 (G005, TASK-001316): `settings` в процессах, правилах и видах

Реализация п.6 там, где решение выше оставляло выбор, и хвосты ревью G004.
Контракт API с консолью (п.4) не меняется.

### Б1. Тип переменной и как различаются ошибки

- Тип `settings` — схема активной ревизии (при плане — из файлов пакета) по
  правилам перевода `data`, но **каждое поле допускает отсутствие**: `required`
  при переводе снимается. Обязательное поле без `default`, которое не
  сохраняли, читается как отсутствующее (`has(settings.<поле>)` — `false`), а
  не как нулевое значение protobuf. `x-ref` — строка.
- Выражение компилируется с типизированной `settings`; ошибка типов — повод
  скомпилировать его ещё раз с `settings` без типа (`map(string, dyn)`).
  Проходит — виновата ссылка: путь, которого нет в схеме, —
  `settings_ref_unknown`, иначе `settings_ref_type`. Не проходит и так —
  прежний код профиля. Так же различается и несоответствие месту выражения
  (тип ключа, условия, поля `data`, формата колонки вида).
- Объект без пакета и пакет без настроек: `settings` есть в окружении как
  нетипизированная, любое чтение — `settings_ref_unknown` (в сообщении —
  «объект не из пакета» или «пакет не объявляет настроек»).
- `catch … as: settings` в процессе по-прежнему допустим: внутри ветки имя
  означает ошибку, ссылкой на настройки не считается и в журнал пару не
  приносит.
- Общий код ссылок — `domain/settings_refs.py`; процесс, правило и вид
  проверяются им одинаково при плане, применении и публикации вне плана.
  Применение проверяет объекты по схеме, которую оно же записывает, а не по
  прежней активной ревизии.

### Б2. Процессы: время чтения, журнал, replay

- Версия процесса компилируется под пару «версия определения, ревизия
  схемы» (кэш воркера по обоим); версия, в спецификации которой слова
  `settings` нет вовсе, пакет не ищет — у прежних процессов запросов не
  прибавилось.
- Шаг (`take`) читает действующие значения один раз — до первого входа,
  включая повторы `intent_failed` того же шага. Маршрутизация события
  (`where` и `key` старта и `correlate`) читает текущие значения отдельно, но
  решение старта движок принимает заново во входе, со значениями записи.
- В API журнала пара — в `data` записи входа (`kind: input`):
  `settingsVersion`, `settingsSchemaRevision`; у процесса без `settings`
  `data` прежняя. Колонки журнала связаны проверкой
  `ck_process_instance_events_settings_pair` (обе `null` или обе заданы,
  версия ≥ 0).
- Replay собственной версии экземпляра типизирует шаг ревизией записи;
  версия, которая с той ревизией проверку не проходит, остаётся со своими
  типами. Replay кандидата (`:replay`, поведенческий diff плана) сохраняет
  типы кандидата, значения записи — из истории. Расхождение `settings`
  останавливает replay экземпляра.
- `given.fromInstance` пробного прогона копирует состояние, журнал не
  воспроизводит: настроек он не касается.

### Б3. Правила

- `settings` — корень наряду с `trigger`, `payload`, `goal`, `task` везде,
  где они читаются (условие, `interpretation.inputs`, шаблоны и `where`/
  `forEach` действия).
- Тип по месту чтения: `lt/le/gt/ge` — число или строка; `eq/ne` — скаляр
  или массив; левый операнд `in` — скаляр, правый и `forEach` — массив;
  подстановка внутри текста — скаляр; шаблон, который целиком один
  плейсхолдер, и `exists` — любой. Поле ошибки — `details.field` условия или
  шаблона (`condition.gt[1].var`), как у прочих ошибок правил; в находке плана
  — путь `/spec/...`.
- Элемент `{kind: "settings", package, version, schemaRevision}` пишется в
  `rule_evaluations.evidence` и приходит в `rule.evaluated`; в `evidence` и
  `origin` заведённой работы он не попадает — задача ссылается на факты, а
  не на прочитанные настройки. Оценка, продолженная после ответа скилла,
  читает значения версии из своего `evidence` по истории.

### Б4. Виды

- Значения читаются один раз на запрос `:query`; в переводе CEL в SQL
  `settings` — константа запроса, как `param`. Путь колонки `settings.<поле>`
  допустим и проверяется по схеме (`settings_ref_unknown` вместо
  `undeclared_path`).

### Б5. Песочница тестов пакета

- Тест процесса: `given.settings` — версия 1, шаг `settings` — следующая
  (те же значения версии не дают); проверка — как у `PUT`, с теми же кодами в
  сообщении сбоя теста и без значений; `x-ref` проверяется по организации
  стенда до прогона. Нет объявления в файлах пакета — тест останавливается
  `settings_not_declared`. Процесс каталога, который вызывает пакет, читает
  текущие значения своего пакета.
- Тест правила (`ruleGiven.settings`): в откатываемой транзакции правила
  пакета связываются с пакетом, схема из файлов становится активной
  ревизией, `given.settings` (нет — `{}`) — новой сохранённой версией. Это
  делается, только если `given.settings` задан или правило пакета упоминает
  `settings`: иначе стенд не трогается.
- `POST /packages:test` показывает находки объявления настроек, как план.

### Б6. Хвосты ревью G004

- Время в ответах настроек — с `Z`, как в остальных ответах ядра.
- Язык строк выбирается общим `choose_locale` видов (CP-ADR-0080 §5): строка
  ищется в выбранном языке, затем в `defaultLocale`; базовый язык между ними
  не просматривается, как у видов.
- **Подписи у свойств объектов внутри `items` массива** не требуются и не
  подставляются: `Control` на них не указывает (п.2), форма показывает массив
  целиком; ключи `<пакет>.settings.<путь>` для них не выводятся. Расширение —
  амендмент вместе с подмножеством `uischema`.

## Амендмент 2026-10-03 (TASK-001378): срок шага выражением

TAI-ADR-0067 §4 задаёт для срока шага форму
`due: {workdays: {expr: settings.reviewDueWorkdays}, warnBefore: {workhours: 4}}`.
До амендмента `workdays` и `workhours` срока (CP-ADR-0078 §1) были только
числами, и настройка пакета попадала в срок лишь через `{at: "cal.addWorkdays(...)"}`.
У этой формы нет `warnBefore`, а приостановка не сдвигает срок от данных
(CP-ADR-0078 §4): событие `process.sla_warning` пропадало, срок после паузы
не сдвигался. Амендмент добавляет выражение туда, где стояло число; прочие
формы `due` не меняются.

### Г1. Форма

```yaml
due: {workdays: {expr: settings.reviewDueWorkdays}, warnBefore: {workhours: 4}}
due: {workhours: {expr: "settings.reviewHours * 2"}, calendar: ru}
due: {workdays: 5, warnBefore: {workdays: {expr: settings.warnDays}}}
```

- `workdays` и `workhours` — и самого срока, и его `warnBefore` — принимают
  число, как прежде, или объект `{expr: <CEL>}` без других членов. В схеме
  каталога (`processDue`, `workingSpan`) это `workdayAmount` и
  `workhourAmount`: `oneOf` из прежнего числа (`workdayCount`,
  `workhourCount`) и `workingAmountExpr`.
- В выражении доступны те же переменные, что в других выражениях шага:
  `data`, `instance`, `settings` пакета процесса (§6) и прочие.
- Пути находок и выражения — `…/due/workdays/expr`,
  `…/due/warnBefore/workhours/expr`.

### Г2. Проверка определения

- Выражение должно давать целое (`int`/`uint`, `dyn` проходит), иначе
  `expression_type_error` по пути выражения. Чтение поля `settings`
  проверяется как в любом другом выражении процесса (§6, Б1): поле,
  которого нет в схеме, — `settings_ref_unknown`; поле другого типа
  (`number`, `string`) — `settings_ref_type`.
- Требования к календарю (CP-ADR-0078 §1: `sla_calendar_missing`,
  `sla_calendar_without_hours`, `unknown_calendar`) — те же, что у числа.

### Г3. Вычисление

- Выражение вычисляется один раз, при входе в шаг (для `spec.due` — при
  старте экземпляра), значениями этого входа: настройки — версии, которую
  записывает запись журнала (Б2).
- Результат — неотрицательное целое не больше предела числа той же единицы
  в схеме (1000 рабочих дней, 10000 рабочих часов); `double` без дробной
  части (число из нетипизированного JSON) считается целым. Ноль допустим:
  срок `workdays: 0` — момент входа (с часами — начало ближайшего рабочего
  интервала). Иначе — `null`, строка, `bool`, дробь, отрицательное или
  слишком большое — ошибка выражения `expression_error` с путём выражения
  в `detail`. Как любая ошибка вычисления срока (CP-ADR-0078 §3), она даёт
  `process.sla_failed` и запись срока `failed`; экземпляр и шаг продолжаются
  без срока.
- Рецепт таймера хранит вычисленное число (`n`/`hours`) и путь выражения
  (`from`). Дальше срок — это срок от числа: порог `warnBefore` и событие
  `process.sla_warning`, остаток при приостановке и сдвиг при возобновлении
  (CP-ADR-0078 §4), пересчёт по новой версии календаря. Настройки,
  сохранённые после входа в шаг, уже посчитанный срок не двигают.
- Пересчёт сроков при миграции экземпляра на новую версию (CP-ADR-0074 §11)
  считает срок по определению новой версии от `openedAt`, как и срок
  `{at}`, поэтому выражение вычисляется заново значениями момента миграции.

### Г4. Журнал и replay

- Решение `timer_set` таймеров срока, рецепт которых содержит вычисленное
  выражением число, несёт `computed`: `{<путь выражения>: <число>}`. Для
  таймеров со сроком-числом поле не пишется, и журналы, записанные до
  амендмента, воспроизводятся как прежде.
- Replay сверяет `computed` вместе с остальным решением: другое значение
  настроек на replay даёт расхождение `decision` на этой записи.
- Песочница тестов пакета считает срок так же: `given.settings` и шаг
  `settings` до входа в шаг меняют срок, после входа — нет.
