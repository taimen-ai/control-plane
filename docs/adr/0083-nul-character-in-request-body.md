# ADR-0083: Символ NUL в теле запроса — 422 на границе API, а не 500 от PostgreSQL

Статус: Accepted (2026-10-04, TASK-001351). Найдено ревью TASK-001334.

Связано: [ADR-0058](0058-reject-unknown-query-parameters.md) (строгая
query-строка, тот же приём — общий слой вместо проверок по маршрутам),
[ADR-0081](0081-package-settings.md) §4.3 и
[ADR-0082](0082-principal-profile-and-workspace-visibility.md) §1.4 (форма
ошибок полей: `details.errors[{path, code}]`, JSON Pointer, без значения);
единый конверт ошибок — `docs/api.md`, «Формат ошибок».

## Контекст

PostgreSQL не хранит `U+0000`: ни в `text`, ни в `jsonb` (`\u0000`). JSON
передаёт этот символ экранированием `\u0000`, pydantic и FastAPI его
пропускают, и строка доходит до базы: `INSERT` падает с `DataError`, клиент
получает `500 internal_error`. Так было с `displayName` в `POST /principals`,
строками профиля, заголовками задач, комментариями, `customFields` — ядро NUL
нигде не обрабатывало. Ошибка клиента выглядела как сбой сервера и писала
стектрейс в журнал.

Проверка по маршрутам или по полям схем не держит вложенные JSON-поля
(`customFields`, `metadata`, параметры пакетов, профиль) и забывается в новом
маршруте — ровно как список «ограничивающих» параметров в ADR-0058.

## Решение

1. Одна проверка на всё приложение — ASGI middleware
   `NulCharacterGuardMiddleware` (`control_plane.api.nul_guard`). Она
   проверяет тело запросов `POST`, `PUT`, `PATCH`, `DELETE` с JSON-типом
   содержимого (`application/json`, `application/*+json`) или без заголовка
   `Content-Type` (маршруты, читающие сырое тело, разбирают его как JSON и без
   заголовка — `PATCH /principals/{id}`).
2. Строка с NUL в любом месте тела — значение на любой глубине или имя члена
   объекта — `422 validation_error`, конверт ошибок полей платформы:
   `details.errors[{path, code: "nul_character", message}]`. `path` — JSON
   Pointer в тело (`/` — корень); у имени члена своего пути нет, указывается
   объект, в котором оно стоит. Значение и само имя в ответ не попадают.
   Ошибок — не больше 20, в порядке документа.
3. Проверка идёт до маршрутизации, аутентификации и обращения к базе: запрос
   с NUL не доходит ни до команды, ни до журнала. Поэтому без учётных данных
   такой запрос получает `422`, а не `401` — ответ говорит только о форме
   тела, ничего о данных.
4. Тело без `\u0000` и без байта `0x00` пропускается без разбора: другим
   способом JSON символ NUL не несёт (сырой управляющий символ в строке — не
   JSON). Тело, которое не разбирается как JSON, остаётся маршруту: он отвечает
   своей ошибкой контракта (`400 invalid_request` и т. п.).
5. Middleware — самая внутренняя: тело буферизуется после
   `BodySizeLimitMiddleware`, превышение предела при чтении — `413
   request_too_large`, как раньше.
6. Исключение — `PUT /api/v1/artifact-contents`: содержимое артефакта любого
   типа, в том числе `application/json`, потоком уходит в хранилище
   содержимого, а не в PostgreSQL (CP-ADR-0072), и не буферизуется.

## Где NUL ещё может попасть в базу мимо проверки

Проверка закрывает тело HTTP-запроса. Вне её остаются (отдельные задачи):

- **query-строка и сегменты пути** — закрыты амендментом, А1 (до
  него `GET /tasks?status=a%00` давал `500`: значение уходило параметром в
  SQL);
- **данные, которые ядро получает не из тела запроса**: ответы внешних систем
  в процессах и вызовах подключений (CP-ADR-0074, CP-ADR-0079), результаты
  Skill (CP-ADR-0056), ответы памяти, которые ядро записывает в события и
  пакет контекста (CP-ADR-0059, CP-ADR-0064), внутренние события worker'а;
- **импорт пакетов** приходит телом `POST /packages:*` и проверкой покрыт;
  метаданные артефактов — телом `POST /artifacts`, тоже покрыты; байты
  содержимого артефакта (п. 6) в PostgreSQL не пишутся.

## Последствия

- Клиент получает `422` с путём к полю вместо `500`; журнал сервера не
  засоряется стектрейсами чужих ошибок.
- Новый маршрут и новое JSON-поле защищены без регистрации.
- Тело запроса с JSON-типом буферизуется ещё раз до маршрута; разбирается
  повторно только тело, содержащее `\u0000` или байт `0x00`.
- `nul_character` — новый `code` в `details.errors[]` у `validation_error`.
- Файл пакета с NUL в `content` (`POST /packages:test`, `:plan`, `:apply`)
  раньше доходил до разбора YAML и давал проблему `invalid_yaml` по файлу
  (TASK-001231); теперь — `422 validation_error` с путём
  `/package/files/<i>/content`, до разбора.

## Амендмент 2026-10-04 (TASK-001395): параметры запроса, транскрипт исполнителя

Хвосты ревью TASK-001351. Решение п. 1–6 не меняется; ниже — что добавлено к
нему. Опечатка в п. 6 (маршрут загрузки — `PUT`, а не `POST`) исправлена на
месте.

### А1. Query-строка и параметры пути

Строка с NUL в параметре запроса или пути — тот же `422 validation_error`,
что и для тела: `details.errors[{path, code: "nul_character", message}]`, где
`path` — `query.<имя>` или `path.<имя>` (имя параметра из шаблона маршрута,
как в OpenAPI: `GET /api/v1/tasks/a%00` — `path.task_ref`).

1. Проверка — router-level зависимость `reject_nul_in_parameters`
   (`control_plane.api.nul_guard`) на всём `/api/v1`, рядом с
   `reject_unknown_query_params` (CP-ADR-0058) и тем же приёмом: имена
   параметров пути известны только после маршрутизации, поэтому middleware из
   п. 1 их не видит. Зависимости роутера решаются раньше зависимостей
   маршрута — запрос с NUL не доходит ни до аутентификации, ни до базы, как и
   по п. 3: без учётных данных — `422`, а не `401`.
2. Проверяется значение каждого параметра пути (строкой, до преобразования
   типа) и каждого параметра query-строки после percent-декодирования
   (`%00`). NUL в параметре типа `int`, `uuid`, даты — тоже `nul_character`,
   а не `400 invalid_request` разбора.
3. Порядок ошибок — порядок в URL: сначала путь, затем query-строка;
   повторённый параметр назван один раз; ошибок — не больше 20. Значение в
   ответ не попадает. Имя параметра с NUL не повторяется — указывается просто
   `query`, как объект для имени члена в теле (п. 2).
4. Неизвестный параметр отклоняется раньше (`400 invalid_request`,
   CP-ADR-0058): `?bogus=%00` — это непонятый параметр, а не NUL в известном.
5. WebSocket `GET /api/v1/events/ws` не затронут, как и в CP-ADR-0058: он
   отвечает кодами закрытия, а не конвертом ошибки.

### А2. Транскрипт исполнителя

Транскрипт прогона (CP-ADR-0051) — JSON-тело `POST /artifacts`, и NUL в нём
давал `422` по п. 2: инструмент, выведший бинарные данные, лишал прогон всего
транскрипта. Исполнитель (`control_plane_agent.trace`) заменяет `U+0000` на
`U+FFFD` в каждой строке транскрипта — тексте, входе и выходе инструментов,
итоге, именах инструментов, идентификаторах вызовов, модели и сессии — и в
`run action` вызова инструмента, до редакции путей и секретов и до обрезки.
Сервер своего правила не меняет: NUL в теле — по-прежнему `422`.

### А3. Буфер тела

Склеенная копия тела живёт только внутри разбора (`_find_nul`); пока
выполняется маршрут, middleware держит лишь сообщения ASGI для повторной
отдачи — одной копией тела меньше на запрос.
