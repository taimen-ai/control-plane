# ADR-0080: Экраны пакетов описанием — вид `View`, словари пакета и `GET /views`

Статус: Accepted (2026-10-03), этапы 1, 2 (амендмент А1–А8, `POST /views/{key}:query`) и 6
(амендмент Б1–Б6, источники `tasks` и `knowledge`) решения суперпроекта TAI-ADR-0066
«Экраны вертикальных пакетов описанием» (принято владельцем 2026-10-03;
разделы «Решения владельца», 1, 1а, 2, 3, 7.1). Задача TASK-001298. Связано:
[ADR-0074](0074-process-engine-in-core.md) §11 (план и установка пакета по
хэшу, `package_objects`), [ADR-0075](0075-cel-expression-profile.md)
(профиль CEL `cp/1`), [ADR-0068](0068-event-filters-catalog-versions.md)
(каталог событий), [ADR-0058](0058-reject-unknown-query-parameters.md).

## Контекст

Вертикальному пакету нужны свои экраны: список экземпляров процесса,
карточка экземпляра, очередь задач типа. Консоль не должна знать предметных
областей пакетов, а пакет — нести код интерфейса. TAI-ADR-0066 решил: экран
пакета — **описание** (вид объекта каталога `View`), консоль рисует его
набором блоков; ядро хранит, проверяет и отдаёт описания, а данные под вид —
отдельным запросом (этап 2, `POST /views/{key}:query`). Все строки экрана —
ключи словарей пакета на объявленных языках.

## Решение

### 1. Виды `View` и `Component`, формат — схема ядра

Формат обоих видов — `src/control_plane/domain/view.schema.json`
(`$defs.viewSpec`, `$defs.componentSpec`). Источник — ядро: package-sdk держит
побайтную копию и проверяет ею файлы автора, как схемой тестов пакета.
Ключ вида и компонента — как у процесса: `^[a-z0-9][a-z0-9_-]{0,62}$`.
Форма — та, которой пишут примеры TAI-ADR-0066 (разделы 1 и 7.1): оба вида и
компонент решения ставятся как есть (`tests/fixtures/views/tenders`,
`tests/unit/test_views_blocks.py`).

`spec` вида:

| Поле | Что |
|---|---|
| `blocks` | версия набора блоков, `1` (необязательно; в ответе всегда) |
| `title`, `description?` | ключи словаря |
| `nav? {group?, icon?, order?}` | пункт меню консоли; `group` — **закрытый список групп меню** `work \| knowledge \| packages` (не ключ словаря), нет — `packages`; иное значение — `invalid_view` |
| `audience? {roles: [slug…]}` | роли организации, держателю одной из которых вид виден; нет поля — виден всем, кто читает источник |
| `source` | ровно одно из `{process, filter?}`, `{process, instance: param.<name>}`, `{tasks: {type}}`, `{knowledge: {kinds}}` |
| `params? {name: {type, required?}}` | типы `string, integer, number, boolean, date, datetime, uuid`; в выражениях — `param.<name>`. Параметр, который называет `source.instance`, может быть не объявлен: он подразумевается `{type: uuid, required: true}` (карточка TAI-ADR-0066 п.1 пишется без `params`); объявленный — `uuid` или `string` |
| `layout` | 1…50 блоков набора версии 1 |

Блок называется ключом `block:`. Блоки версии 1 (закрытый набор):

| Блок | Поля |
|---|---|
| `table`, `list` | `columns`, `open?`, `filters?` (пути), `sort? [{field, dir?}]`, `pageSize?` |
| `board` | `columns: stages` — колонка на этап процесса, в его порядке; `card {title, subtitle?, fields?, badge?}`: `title`, `subtitle`, `badge` — пути источника (`data.*`, `stage`, `status`, `slaState`), `fields` — колонки, подпись у них необязательна; `open?`, `filters?` |
| `header` | `title` — путь источника, `status?` — путь (`stage`, `status`, `slaState`, `data.*`), `actions?: steps` — открытые шаги экземпляра как действия |
| `fields` | `section?` (ключ словаря), `items` — колонки |
| `timeline`, `steps` | — |
| `artifacts` | `types?` — ключи типов артефактов; нет поля — все |
| `related` | `knowledge {kind, key}` — запись базы знаний, от которой идёт блок: вид онтологии и выражение CEL её ключа (`string`); `include? {relations: [имя…] \| "*", direction?: out \| in \| both, limit? 1…200}` — какие связи записи показать; форма — `include` запроса `POST /knowledge/entities:query` ([ADR-0060](0060-knowledge-snapshots-through-control-plane.md) С1) |
| `metrics` | `items: [{title, value, format?, key?}]`, `title` — ключ словаря, `value` — агрегат |
| `chart` | `chart: bar \| line \| donut`, `groupBy` (путь), `value` (агрегат), `label?`, `format?` |
| `invoke` | `label`, `skill: <name>@<version>`, `input? {name: CEL}` — вызов скилла (ADR-0056); результат консоль показывает по **схеме выхода** скилла |
| `component` | `component: <key>`, `with? {param: CEL}` — компонент пакета и значения его параметров |

У всех, кроме `header` и `component`, — `title?` (ключ словаря); у `fields` —
ещё `section?`. Колонка (`columns`, `items` блока `fields`, `card.fields`) —
`{label?, field | value, format?, key?}`: `field` — путь источника, `value` —
выражение CEL (путь — тоже выражение: `value: data.procurement.number`); ровно
одно. **Подпись не написана** — это ключ словаря `<пакет>.fields.<путь>`
(TAI-ADR-0066 п.1а): путь — `field` без `data.` или единственное поле, которое
читает `value` (`decimal(data.procurement.maxPrice.amount)` →
`tenders.fields.procurement.maxPrice.amount`; параметры не в счёт, а без поля
источника — единственный параметр без `param.`); `value` не из одного поля
пишет подпись сам (`missing_label`). `key` — ключ колонки в ответе и в данных
под вид (§9); не написан — тот же путь, у показателя `metrics` — последнее
слово его `title` (`tenders.board.inProgress` → `inProgress`), иначе номер в
списке. `open: {view, id?, params?}` — переход на вид: `id` — выражение CEL
идентификатора записи (`id: id`, `string`), `params` — выражения параметров.

Контекст выражений источника `process`: `data` по схеме данных процесса,
`instance.{id,key,version,startedAt,clock}`, `stage.<id>.{active,completed}`,
`param` по `params` и поля экземпляра, по которым фильтрует
`GET /process-instances`: `id`, `status` (`running | suspended | completed |
failed | cancelled`) и `slaState` (CP-ADR-0078 §6) — строки. Функция
`decimal()` профиля (амендмент 2026-10-03
[ADR-0075](0075-cel-expression-profile.md)) переводит сумму, записанную
строкой, в число: `sum(decimal(data.procurement.maxPrice.amount))`.

`invoke` вызывает скилл маршрутом `POST /api/v1/skills/{ref}:invoke` с правом
вызывающего (`skills.invoke`): видимость вида права вызова не даёт, а
кнопку без права консоль может не показывать. `input` вычисляется консолью
над записью блока; ядро на этапе 1 проверяет описание (п.3), а не вызов.

Форматы: `text, number, money, percent, date, datetime, due, duration,
principal, status, link`. Без `format` консоль показывает значение по его
типу.

`Component` — описание (TAI-ADR-0066 п.7.1): `{description?, params?,
layout}` из блоков того же набора, без вложенных компонентов. Параметр —
`{type, required?}`, как у вида, или **`{schema, required?}`**: JSON Schema,
написанная на месте или ссылкой на схему пакета `{$ref: <файл>#<указатель>}`
(`../schemas/tender.yaml#/properties/procurement`). Ссылку читает разбор
пакета: файл — относительно файла компонента и внутри пакета, указатель — JSON
Pointer, к части добавляются `$defs`/`definitions` её файла (её локальные `$ref`
остаются в силе); не нашлась — `unresolved_schema_ref`, ссылка внутри документа
или во внешний мир — `invalid_component`. Тип `param.<name>` в CEL — из этой
схемы: `param.procurement.customer.shortName` разбирается, необъявленное поле —
`expression_type_error`. В выражениях блоков компонента `param.<name>` —
**его** параметры, а не параметры вида; значения даёт вид в `with` блока
`component` (выражения CEL в контексте вида; тип значения — по типу параметра,
у параметра со схемой — по её JSON-типу: объект, список, строка, число,
логическое). Ядро **встраивает** компонент в каждый вид, который его называет:
в форме вида блок `component` несёт `with` и `layout` компонента, и правка
компонента — новая ревизия каждого такого вида. Отдельным объектом каталога
компонент не хранится и в `outside` плана не попадает. Поле `code` у вида и
компонента отвергается (`component_code_not_supported`): изолированных
компонентов с кодом (п.7.2) нет решением владельца.

### 2. Языки и словари пакета

`package.yaml` объявляет `locales: [en, ru]` (тег вида `en`, `pt-BR`) и
`defaultLocale` из них; словари — `i18n/<locale>.yaml`, плоское
отображение ключ → текст. Ключ — `^[A-Za-z0-9][A-Za-z0-9_.-]{0,199}$`
(префикс пакета — соглашение автора, ядро его не требует), текст — строка до
2000 символов с подстановками ICU (`{n}`, `{count, plural, …}`): ядро
проверяет, что фигурные скобки аргументов парные (`'` экранирует, как в ICU),
а форматирует консоль. Файлы `i18n/` не объекты каталога.

Находки (с файлом и строкой): `locales_required` — у пакета есть виды,
компоненты или словари, а языков нет; `invalid_locales`;
`invalid_default_locale`; `missing_dictionary` — у объявленного языка нет
файла; `undeclared_locale` — словарь необъявленного языка;
`invalid_dictionary` — не `i18n/<locale>.yaml`, не отображение, второй файл
того же языка; `invalid_message` — ключ, не строка, непарные скобки;
`unused_message` — предупреждение: ключ не показывает ни один вид и
компонент пакета.

Словари хранятся с пакетом: `package_dictionaries` — ревизия на изменение
(хэш языков, языка по умолчанию и текстов), с версией пакета.

### 3. Проверка вида

Вид проверяется в `POST /packages:plan` и заново в `POST /packages:apply`;
вид с ошибкой не попадает в `changes`, а установка такого пакета —
`422 invalid_package`. Находки — в форме находок плана (`code`, `path` от
`/spec`, `file`, `line`):

| Код | Когда |
|---|---|
| `invalid_view`, `invalid_component` | форма не по схеме (в том числе `nav.group` не из списка групп меню, `header` без `title`, `fields` без `items`, показатель `metrics` без `title`) |
| `unknown_block`, `unknown_format` | блока или формата нет в наборе версии 1 |
| `component_code_not_supported` | поле `code` |
| `invalid_source` | не ровно один источник; `filter`/`instance` не у процесса; `filter` у вида одного экземпляра; параметр `instance` объявлен не `uuid`/`string` |
| `unknown_source` | процесса или типа задачи нет ни в пакете, ни в каталоге tenant |
| `undeclared_path` | путь `data.*` не объявлен в JSON Schema данных процесса (`properties`, локальные `$ref`, `allOf/anyOf/oneOf`); у процесса пути — `data.*`, `instance.{id,key,version,startedAt,clock}`, `stage`, `status`, `slaState`, `id` |
| `expression_syntax_error`, `expression_type_error` | выражение не компилируется в профиле `cp/1` (ADR-0075) в контексте источника (§1); `filter` — не `bool`; `open.id` — не `string` |
| `format_type_mismatch` | тип значения не подходит формату (таблица ниже) |
| `aggregate_outside_metrics` | вызов `count/sum/avg/min/max(` вне `metrics` и `chart`; имя внутри строкового литерала CEL (`data.note == "max(x)"`) — не вызов |
| `invalid_aggregate` | значение `metrics`/`chart` — не один агрегат: `count()`, `count(<bool>)`, `sum/avg(<число>)`, `min/max(<число, время, длительность>)` |
| `block_source_mismatch` | `table/list/board` у вида одного экземпляра; `header/fields/timeline/steps` без `instance`; `timeline/steps/board` не у процесса (у доски колонки — этапы процесса) |
| `missing_label` | у колонки нет подписи, а `value` читает не одно поле — подписи по умолчанию не из чего взять |
| `duplicate_key` | две колонки (или два показателя) одного блока с одним ключом — по нему приходят значения (§9); ключ даёт `key` |
| `unknown_view` | `open.view` — не вид пакета и не вид в обороте пакета из его `requires` |
| `unknown_component` | `component` — не компонент пакета |
| `nested_component` | компонент из компонентов |
| `unresolved_schema_ref` | `$ref` схемы параметра компонента не ведёт к объекту JSON Schema файла пакета |
| `unknown_param`, `missing_param` | `with` называет параметр, которого компонент не объявил; не даёт обязательного |
| `expression_type_error` (у `with`) | тип выражения не подходит типу параметра компонента |
| `unknown_skill` | скилла `invoke` нет ни в пакете (`Skill`), ни в каталоге tenant, или он `disabled` |
| `skill_output_missing` | у скилла нет схемы выхода (`contract.outputs`, `outputSchema`) — результат не по чему показать |
| `unknown_skill_input`, `skill_input_missing` | `input` называет вход, которого нет в схеме входа скилла; не даёт обязательного входа |
| `unknown_role` | роли `audience.roles` нет ни в организации (slug, tenant-wide или в любом workspace), ни среди `Role` пакета |
| `missing_message` | ключа строки нет в словаре хотя бы одного объявленного языка (в сообщении — какого); это и подпись по умолчанию `<пакет>.fields.<путь>` у колонки, фильтра и сортировки, которые консоль показывает с подписью |

Пути и выражения блоков компонента проверяются в контексте источника
каждого вида, который его встраивает; находка — в файле компонента.

Формат → типы CEL (`dyn` подходит любому): `text`, `principal`, `status`,
`link` — `string`; `number`, `percent` — `int`, `uint`, `double`; `money` —
числа и `string` (десятичная запись); `date`, `datetime`, `due` — `timestamp`
и `string`; `duration` — `duration` и `string`. Агрегат даёт `int` у
`count`, `double` у `avg`, тип аргумента у `sum/min/max`.

Пути и выражения источников `tasks` и `knowledge` на этапе 1 проверяются
только синтаксисом: их поля (`customFields.*` по `fieldSchema` типа,
атрибуты записей) сверит этап 6 вместе с их запросом. Существование видов
онтологии — `source.knowledge.kinds`, `related.knowledge.kind` и
`related.include` — на этапе 1 **не проверяется**: онтологии живут в
memory-service, их сверит этап 6 вместе с запросом базы знаний; ядро
проверяет только форму ключа вида (`^[a-z][a-z0-9_.-]{0,63}$`) и имени
связи (`^[a-z][a-z0-9_]{0,62}$`, как в ADR-0060 С1).

Этап 6 это сделал (амендмент Б3): пути `fields.*`/`customFields.*` вида задач
сверяются с полями задачи и `fieldSchema` типа — ошибкой; виды, атрибуты и
связи онтологии — предупреждениями плана по онтологии дерева `workspaceId`.

### 4. План и установка

`View` — вид, который планирует ядро (`PLANNED_KINDS`), последним: он
называет процессы и типы задач. Сравнивается **форма** вида: `spec` со
встроенными компонентами и `blocks` (её читает запрос под вид, этап 2), плюс
`display` — отображение для консоли (§9) с ключами словаря на местах строк,
`messages` (тексты его ключей на каждом языке), `locales`, `defaultLocale`;
хэш формы — `sha256` канонического JSON. Поэтому изменённый текст словаря —
тоже новая ревизия вида: консоль сбрасывает кэш по событию, а не по сверке
словарей.

Действия плана для вида: `create`, `update` (ревизия +1), `unchanged`,
`restore` — выведенный вид пакет приносит без изменений, он снова в обороте
на прежней ревизии; `retire` — вид, который этот пакет ставил
(`package_objects`), а новая версия пакета его не приносит. Ключи вида и
выводимых видов входят в `catalogEtag` и `planHash`. Виды пишет только
`packages:apply` под блокировкой установок tenant'а
(`package_links.lock_applies`): вторая установка того же плана ждёт и
получает `409 plan_stale`. Связь вида с пакетом — `package_objects`
(вид `View` связывает только apply, как `Process` и `Calendar`;
`packages:record` его не принимает); выведенный вид связь сохраняет.

Хранение: `views` (ключ, текущая ревизия, `active|retired`, кто и когда
вывел) и `view_revisions` (неизменяемые ревизии: форма, хэш, источник,
роли аудитории, пакет и его версия).

### 5. Чтение: `GET /views`, `GET /views/{key}`

- `GET /api/v1/views?locale=&package=&limit=&cursor=` — виды в обороте,
  которые видит вызывающий, по ключу, **сводкой без `layout`** (§9); курсор
  по ключу, `?package=<key>` — как у прочих видов каталога.
- `GET /api/v1/views/{view_key}?locale=` — один вид целиком (имя параметра
  пути — `view_key`: BFF консоли открывает этот шаблон). Выведенный,
  невидимый и несуществующий — один и тот же `404 not_found`.

Ответ — **отображение** вида (§9), которое ядро строит при проверке и хранит в
форме ревизии (§4) с ключами словаря на местах строк; при чтении каждый ключ
заменяется текстом. Язык — запрошенный, иначе его базовый язык (`ru-RU` →
`ru`, без учёта регистра), иначе `defaultLocale` пакета. Ключ, которого нет в
словаре выбранного языка, берёт текст языка по умолчанию, затем сам ключ
(возможно только для формы, сохранённой прежней проверкой); подпись значения
фильтра, которой нет ни в одном словаре, — само значение.

### 6. Права: отдельного `views.read` нет

Решение (TAI-ADR-0066 п.4 оставил выбор ядру): вид не вводит своего права.
Вид — описание экрана над источником; он **сужает** то, что показывает
источник, и не может расширить. Вызывающий видит вид в обороте, когда:

1. **аудитория** — `audience` нет, или он держит одну из её ролей
   организации (`principal_roles`, tenant-wide или в любом workspace);
2. **источник** — он может его читать: `processes.read` (и на workspace
   процесса, если версия процесса к нему привязана), `tasks.read` для задач,
   `events.read` для базы знаний — те же права, что у маршрутов источника.

Почему не `views.read`: право читать описание экрана без права читать его
данные ничего не даёт, а право на данные без описания — уже есть; новое право
пришлось бы раздать всем людям консоли одновременно с выкладкой, иначе экраны
пропадут. Роль — организационная (ADR о модели организации), не право API:
администратор с `admin`, но без роли аудитории вида не видит — это экран
другой работы, а не запрет на данные. Данные под вид (этап 2) решаются правами
источника на каждую запись.

### 7. События журнала

- `view.published` (`entityType: view`): `{key, revision, hash,
  previousRevision, packageKey, packageVersion}` — новая ревизия или
  возвращённый в оборот вид (`restore`: `revision` прежняя).
- `view.retired`: `{key, revision, reason, packageKey, packageVersion}`;
  `reason` — `no longer in package <key>`.

Консоль сбрасывает кэш описания ключа по любому из них.

### 8. Отступления от TAI-ADR-0066

Форма пакета — по разделам 1, 2 и 7.1 решения: оба вида раздела 1 и компонент
п.7.1 ставятся как есть (`spec` дословно; тест
`tests/unit/test_views_blocks.py` и интеграционный
`tests/integration/test_package_views.py`). Единственная правка примеров в
фикстуре — нейтральный каталог в `apiVersion` (white-label,
[ADR-0022](0022-white-label-naming.md)); форма `spec` от неё не зависит. Чего
этап 1 не делает:

1. **Виды онтологии не сверяются** (`source.knowledge.kinds`,
   `related.knowledge.kind`, `related.include`) — §3: онтологии в
   memory-service, сверка — этап 6 вместе с запросом базы знаний.
2. **Пути и выражения источников `tasks` и `knowledge` — только синтаксис**,
   их фильтры в ответе — `type: text` без вариантов (§3, §9): поля задачи и
   записи знаний сверит этап 6 вместе с их запросом.
3. **Вызов `invoke` ядро не исполняет и не проверяет права на него при
   выдаче вида** — §1: вызов идёт существующим маршрутом скилла с правом
   вызывающего; этап 1 проверяет описание (скилл, вход, схема выхода).
4. **Значения под вид не вычисляются** — ни колонок, ни `open.id`, ни
   заголовка и состояния `header`: это `POST /views/{key}:query`, этап 2
   (TASK-001299). Этап 1 проверяет выражения и отдаёт ключи, по которым
   значения придут.

`decimal()` сделан в профиле CEL (амендмент ADR-0075), а не отложен:
выражения видов идут через профиль процессов.

### 9. Форма ответа — контракт с консолью

Согласовано с консолью 2026-10-03 (решение владельца: согласовать); сторона
потребителя — `docs/views.md` репозитория консоли. Ответ — описание пакета с
подставленными строками, **обогащённое тем, что знает только ядро**; консоль не
разбирает ни JSON Schema данных, ни CEL. Сырой `source` пакета (CEL `filter`,
`param.<name>`), пути (`field`) и выражения (`value`, `with`, `open.id`) в ответ
не попадают; исключение — `invoke` (ниже).

- `GET /views` → `{items: [ViewSummary], nextCursor}`;
  `ViewSummary = {key, title, revision, hash, package {key, version}, nav?,
  source}` — без `layout`. `GET /views/{view_key}` — то же плюс `layout`.
- `source` — `{kind: process | tasks | knowledge, process?, instance: bool}`:
  `process` — ключ процесса источника, `instance` — вид показывает один
  экземпляр (карточка открывается по id записи).
- `nav` — `{group: work | knowledge | packages, icon?, order?}`; `group` —
  закрытый список групп меню консоли, у вида без `group` — `packages`; вид
  без `nav` — только по ссылке.
- Колонка, поле и показатель — стабильный `key` (по нему значения приходят в
  `:query`), готовая подпись (`title`, у `fields` — `label`; написанная или
  по умолчанию `<пакет>.fields.<путь>`) и `format?`.
- Блоки (дискриминатор `block`):
  - `metrics` — `items: [{key, title, format?}]`;
  - `table`, `list` — `columns: [{key, title, format?}]`,
    `filters?: [{field, title, type: text | enum | number | date, options?:
    [{value, title}]}]`, `sort?: [{field, title}]`, `open?: {view}`. Тип и
    варианты фильтра ядро выводит из схемы данных: `enum` — у `enum` схемы,
    `boolean`, `stage` (этапы процесса), `status` и `slaState`; `number` — у
    `integer`/`number`; `date` — у строки `date`/`date-time` и
    `instance.startedAt/clock`; иначе `text`. Подпись варианта — ключ
    `<пакет>.fields.<путь>.<значение>`, если он есть в словаре, иначе само
    значение. `field` фильтра и сортировки — тот же путь без `data.`.
    `id` открываемой записи — `id` строки ответа `:query`: если в пакете
    `open {view, id}`, ядро вычислит id в строку ответа, в описании — только
    `view`;
  - `board` — `card: {fields: [{key, format?}]}`, `open?: {view}`,
    `filters?`; колонки — этапы процесса; заголовок, подзаголовок и метка
    карточки приходят в `:query`;
  - `chart` — `type: bar | line | donut`, `title?` (`title` блока или его
    `label`), `format?`;
  - `fields` — `section?`, `items: [{key, label, format?}]`;
  - `header` — `actions` как в пакете (контракта действия ещё нет, консоль
    их пропускает); title, status и lead приходят в `:query`;
  - `steps`, `timeline`, `artifacts` — без полей описания;
  - `related` — `{title?, relations?: [имя связи]}` (`relations: "*"` —
    без поля);
  - `invoke` — как в пакете, строки подставлены; `component` — `{component,
    layout}`, блоки компонента в том же отображении. Консоль показывает на
    их месте «нужна более новая консоль».
- `revision`, `hash`, `package`, `title` — как есть; `blocks: 1`.

Что ядро добавляет к согласованной форме (консоль может не читать):
`locale` — язык, на котором пришли строки (кэш — по `(key, revision,
locale)`); `description?` вида; `title?` любого блока, кроме `header` и
`component` (подпись блока, ключ словаря); `installHash`, `installedAt`
пакета. Форма закреплена contract-тестом
`tests/unit/test_views_console_contract.py`: независимая JSON Schema
согласованной формы, примеры — виды TAI-ADR-0066 в отображении, модели
openapi маршрутов; интеграционный тест проверяет ею ответы маршрутов.

## Последствия

- Описания экранов проходят тот же путь, что процессы: план показывает
  изменения и находки с местом в файле, установка — ровно план по хэшу.
- Ядро не знает имён видов, блоков пакетов и полей: проверка — общая для
  любого пакета (страж нейтральности `tests/unit/test_process_neutrality.py`,
  интеграционный тест на двух пакетах не из разработки).
- Нет маршрута ручного вывода вида (`:retire`) — вид выводит только пакет,
  который его ставил; вид, созданный не пакетом, невозможен.
- Не сделано на этапе 1: запрос данных под вид (этап 2), проверка путей
  `tasks`/`knowledge` и видов онтологии (этап 6), отдача словаря пакета
  целиком через API (сейчас только тексты ключей вида в его ревизии); см. §8.
- Форма ответа — контракт с консолью (§9), а не форма пакета: пакет может
  менять пути и выражения, не трогая консоль; новое поле ответа — добавление,
  смена смысла поля — согласование с консолью и новая версия набора блоков.

## Амендмент 2026-10-03 (TAI-ADR-0066 п.4, этап 2, TASK-001299): данные под вид — `POST /views/{key}:query`

Этап 2 решения суперпроекта: консоль рисует блок вида и спрашивает у ядра
**ровно то, что нужно блоку** — значения его колонок, карточек и агрегатов, а
не сырые экземпляры. Источник — `process` (список экземпляров и один экземпляр
`instance: param.<name>`); `tasks` и `knowledge` — этап 6. Форма ответа
согласована с консолью 2026-10-03 и консоль уже рисует по ней: сторона
потребителя — `docs/views.md` репозитория консоли, раздел
`POST /api/v1/views/{key}:query` (коммит консоли 54f7b58). Код —
`application/queries/view_data.py` (запрос), `application/queries/view_sql.py`
(CEL и пути в SQL), `domain/view_query.py` (разбор запроса и значения по
форматам).

### А1. Маршрут и тело

`POST /api/v1/views/{view_key}:query?locale=` — тело (`ViewQueryRequest`,
лишнее поле — `400`, ADR-0058):

```json
{"block": 1, "params": {"id": "…"},
 "filter": [{"field": "kind", "op": "eq", "value": "goods"}],
 "sort": [{"field": "amount", "dir": "desc"}], "limit": 50, "cursor": null}
```

- `block` — индекс блока в `layout` вида (как в `GET /views/{key}`); блок
  вне раскладки — `422 unknown_block`; `invoke` и `component` своих данных не
  имеют — `422 block_without_data` (консоль показывает на их месте «нужна более
  новая консоль», §9).
- `params` — параметры вида по их типам (§1): необъявленный — `422
  unknown_param`, обязательный не дан — `422 missing_param`, другого типа —
  `422 invalid_param`. Параметр `instance` (`uuid`), который не UUID, ничего не
  называет: ответ — `404`, как у отсутствующего экземпляра.
- `filter`, `sort` — по ключу `field` из описания блока (`filters[].field`,
  `sort[].field` §9: путь без `data.`). Клиент не присылает выражений: CEL
  пишет автор пакета. Поле, которого блок не объявил, — `422
  undeclared_filter` / `422 undeclared_sort` (консоль показывает ошибку
  блока); сортируются только `table` и `list`.
- `limit` — 1…200; нет — `pageSize` блока, иначе 50. У доски — карточек в
  колонке, у графика — точек, у журнала и артефактов — записей.
- `cursor` — только у `table` и `list`, из `nextCursor` того же запроса;
  курсор другой ревизии вида, блока, параметров, фильтров или порядка —
  `422 invalid_cursor`.

### А2. Права: по человеку, вид сужает

- Вид — как `GET /views/{key}` (§6): роль аудитории и право читать процесс;
  невидимый, выведенный и несуществующий — один и тот же `404 not_found`.
- Экземпляры — те, что показывает `GET /process-instances`: в workspace, где
  у вызывающего есть `processes.read` (в режиме policy — по PDP, список
  workspace — `list_objects`), и без workspace при праве на tenant.
- Экземпляр карточки другого процесса, чужого workspace или несуществующий —
  `404` «Process instance not found», неразличимо.
- `source.filter` вида действует на **каждый** блок: страницы, доску,
  агрегаты, графики. Вид сужает источник, расширить не может.
- Блок `steps` показывает задачу шага (`task`), только если вызывающий может
  её читать (`tasks.read` на задаче); `artifacts` — артефакты, которые он может
  читать (`artifacts.read`, CP-ADR-0072 §5); `related` — связи с видимым
  концом (`events.read` на workspace экземпляра, видимость памяти, ADR-0060
  С1); без права — пустой список, не ошибка.
- В ответ уходят только значения, которые блок показывает, по ключам описания;
  поля `data`, которых вид не показывает, ядро не отдаёт.

### А3. Ответ по блоку

Форма согласована с консолью и закреплена contract-тестом
`tests/unit/test_view_query_contract.py` (независимая JSON Schema формы,
примеры, модели openapi маршрута); интеграционные тесты проверяют ею ответы
каждого блока. Ключи значений — `key` колонок, полей и показателей из ответа
`GET /views/{key}`.

| `block` | Ответ |
|---|---|
| `metrics` | `{values: [v, …]}` — по порядку `items` |
| `table`, `list` | `{items: [{id, title, values: {key: v}}], nextCursor}` |
| `board` | `{columns: [{key, title, items: [{id, title, subtitle?, values, badge?}]}]}` |
| `chart` | `{points: [{label, value}]}` |
| `header` | `{title, status: {title, category}, lead?}` |
| `fields` | `{values: {key: v}}` |
| `steps` | `{items: [{key, title, task?: {ref, title}, assignee?, since?}]}` |
| `timeline` | `{items: [{at, title, actor?}]}` |
| `artifacts` | `{items: [{id, name, type, createdAt}]}` |
| `related` | `{items: [{relation, title?, kind, key, entityTitle, direction}]}` |

Как ядро заполняет поля, которых форма не определяет сама:

- `id` строки и карточки — `open.id` пакета, вычисленный над записью
  (`string`), иначе id экземпляра; `title` строки — ключ экземпляра
  (`instanceKey`).
- `board` — колонка на этап процесса в его порядке (последняя версия
  процесса); `key` — id этапа, `title` — текст ключа
  `<пакет>.fields.stage.<id>`, иначе `displayName` этапа, иначе id. Экземпляр
  стоит в колонке своего **этапа**: первого активного, иначе последнего
  завершённого; без этапа — ни в одной. В колонке — новые первыми, не больше
  `limit`. `title`, `subtitle` карточки — значения путей `card.title`,
  `card.subtitle`; `badge` — `{title, category}` значения пути `card.badge`.
- `header` — `title` — значение пути `title` (нет — ключ экземпляра);
  `status` — `{title, category}` значения пути `status` (нет — состояния
  экземпляра); `lead` описание блока не задаёт — ядро его не отдаёт.
- `steps` — открытые шаги экземпляра (`openElements`): `key` — id шага,
  `title` — его `displayName`, `task` — `{ref: publicId, title}` задачи шага,
  `assignee` — исполнитель задачи, `since` — когда шаг открылся.
- `timeline` — журнал решений экземпляра (`/journal`), новые первыми: `at`,
  `title` — причина записи журнала, `actor` — principal.
- `artifacts` — артефакты задач, которые экземпляр открыл, типов `types`
  блока (нет — всех), новые первыми.
- `related` — связи записи базы знаний `{kind, key}` блока (ключ — выражение
  CEL над экземпляром) по `include` блока, чтением памяти как
  `entities:query include` (ADR-0060 С1); экземпляр без workspace — пустой
  список. Подписи связи (`title`) в словарях пока нет — поле не отдаётся.

Значения по `format`:

| Формат | Значение |
|---|---|
| `money` | `{amount, currency}`: `amount` — строка десятичной записи, как в данных (`decimal(data.x.amount)` над `"184500.00"` — `"184500.00"`), иначе число; `currency` — строка `currency` рядом с единственным полем `….amount`, которое читает выражение, иначе `null` |
| `date` | ISO 8601 дата (`YYYY-MM-DD`; у времени — день по UTC); строка данных — как есть |
| `datetime`, `due` | ISO 8601 (RFC 3339, `Z`); строка данных — как есть |
| `duration` | ISO 8601 (`PT…S`) |
| `principal` | id участника |
| `status` | `{title, category}`: `title` — текст `<пакет>.fields.<поле>.<значение>`, у этапа — ещё `displayName`, иначе само значение |
| `link` | `{href, title}`, оба — значение |
| `number`, `percent`, `text`, без формата | как есть (время — ISO 8601, объект — объект) |
| нет значения, ошибка выражения | `null` |

`category` — категория **состояния экземпляра**, которому принадлежит
значение, как `ProcessInstanceOut.status` (§1): `running | suspended |
completed | failed | cancelled`; так же их принимает фильтр `status`.

### А4. Фильтры и сортировка

Операции — закрытый список по типу фильтра (§9; так консоль их и шлёт):

| Тип | Операции | Смысл |
|---|---|---|
| `enum` | `eq`, `in` | равенство значения JSON (`boolean` — `true`/`false`) |
| `text` | `eq`, `in`, `prefix` | `prefix` — начало строки без учёта регистра; `%` и `_` — буквы, не шаблон |
| `number` | `eq`, `in`, `gte`, `lte` | число или строка десятичной записи |
| `date` | `eq`, `gte`, `lte` | день `YYYY-MM-DD`: у строки данных — её первые 10 символов (`date` и `date-time`), у `instance.startedAt` — день по UTC |

Другая операция — `422 invalid_filter`, как и значение не того типа, `in` не
из 1…100 значений, строка длиннее 500. Фильтры одного запроса — через «и»,
значения `in` — через «или». `stage` — этап экземпляра (А3), `status` —
состояние, `slaState` — состояние сроков на сейчас, как его показывает
экземпляр (CP-ADR-0078 §6).

Сортировка — по полям `sort` блока; нет в запросе — порядок, который написал
пакет; затем новые первыми и id — порядок полный, курсор — по значениям
ключей (keyset). Нет значения — в конце при любом направлении. `stage`
сортируется по порядку этапов процесса, `slaState` — по ближайшему
идущему сроку (`sla_due_at`).

### А5. Агрегаты `metrics` и `chart`

Над всеми экземплярами источника, которые видит вызывающий, после
`source.filter` (фильтров у этих блоков нет). `count()` — число записей,
`count(<условие>)` — записей, где условие `true`; `sum/avg/min/max` — по
записям, где выражение дало число (у `min/max` — ещё время и
длительность); запись, где выражение не вычислилось (нет поля, `decimal()`
не числа), пропускается. Пустое множество: `count` и `sum` — `0`, `avg`,
`min`, `max` — `null`. Суммы ЕИС — строки десятичной записи:
`sum(decimal(data.price.amount))` в SQL считается в `numeric` без потери
копеек (`"21003.00"`). `chart` группирует по пути `groupBy` (`label` — текст
значения, как у `status`), записи без значения пути не входят; точки — в
порядке этапов, состояний, иначе значений; не больше `limit`.

### А6. Исполнение и скорость

Ядро не вычисляет вид в Python запись за записью, когда этого можно не
делать: `source.filter`, фильтры и порядок запроса и агрегаты становятся
условиями, ключами и агрегатами **одного SQL-запроса** (`view_sql.py`).
Переводится часть CEL, смысл которой SQL держит точно: чтения `data.<путь>`
по типизированным полям схемы данных (строка, число, логическое; профиль
`cp/1` типизирует так же — `typed_leaf`), `status`, `id`,
`instance.{id,key,version,startedAt,clock}`, `stage.<id>.{active,completed}`,
`param.<name>`, литералы; `==`, `!=`, `<`, `<=`, `>`, `>=`, `&&`, `||`, `!`,
`in` списка литералов, `? :`, `+`, `-`, `*`, `has()`, `decimal()`,
`startsWith`, `endsWith`, `contains`. Отсутствующее поле — `null` в CEL и
`NULL` в SQL, ошибка CEL — `NULL`, который `&&`, `||` и `!` несут, как CEL
несёт ошибку; равенство двузначно в обоих (`data.x == "a"` — `data @> {"x":
"a"}`, его отвечает GIN-индекс). Выражение вне этой части (`size()`,
`timestamp()`, деление, `slaState`) вычисляется в Python запись за записью с
тем же результатом: страница — пока не наберётся `limit`, агрегаты — по id
подошедших записей снова в SQL. Совпадение проверяет тест
`tests/integration/test_view_sql.py`: 43 выражения на одном наборе (пропуски,
`null`, суммы не числом, `%` и `_`, регистр) выбирают в SQL ровно то, что
CEL вычисляет в `true`; непереводимые — отказ, а не приближение.

Вычисление запись за записью ограничено: один запрос читает для него не
больше **20 000** экземпляров (`MAX_EVALUATED` в `view_data.py`; все проходы
запроса вместе — страница, доска, отбор `source.filter` и агрегаты). Дальше —
`409 view_too_costly` с `details {key, limit}`: ответ по части экземпляров
выдал бы неверные агрегаты и страницу без признака неполноты, а места для
такого признака в форме ответа консоли нет. Вид, у которого `source.filter`
и значения целиком в переводимой части CEL, потолка не касается: SQL читает
только нужное.

Индексы (миграция `a7d3e9c1f5b2`): GIN `jsonb_path_ops` по
`process_instances.data` (`ix_process_instances_data`) — равенства фильтров и
`source.filter`; `(tenant_id, definition_key, started_at, id)`
(`ix_process_instances_tenant_definition_started`) — экземпляры процесса
новыми первыми и курсор. Вычисляемые колонки и индексы-выражения под фильтры
пакета не заводятся: замер их не требует (TAI-ADR-0066 п.4 оставил их
решением реализации).

Замер (`tests/integration/test_view_query_speed.py`, 10 000 экземпляров
процесса в tenant, 30 запросов через API после прогрева, тестовая
PostgreSQL 16 раннера, 2026-10-03), p95 / медиана, мс:

| Запрос | p95 | медиана |
|---|---|---|
| `table`, 50 записей, порядок пакета | 38,5 | 26,3 |
| `table`, сортировка запроса по двум полям | 65,0 | 25,1 |
| `table`, `eq` + диапазон `gte`/`lte` | 35,5 | 27,7 |
| `table`, `prefix` | 25,2 | 22,3 |
| `table`, вторая страница по курсору | 37,7 | 31,1 |
| `metrics`, 5 агрегатов по всем | 31,2 | 29,3 |
| `board`, до 50 карточек в колонке | 89,0 | 77,4 |
| `table` вида с непереводимым `source.filter` | 53,1 | 48,6 |
| `metrics` вида с непереводимым `source.filter` | 1606,8 | 1526,5 |

Цель TAI-ADR-0066 — p95 < 150 мс на страницу 50 записей при 10⁴ экземпляров —
выполнена; тест держит её для страниц. Непереводимый `source.filter` стоит
одного вычисления CEL на экземпляр: страница остаётся быстрой, пока
подходящие записи часты, агрегаты — линейны по числу экземпляров. Автору
пакета — писать фильтр источника в переводимой части CEL.

### А8. Чего этап 2 не делает

2. `open.params` вида не вычисляются: форма ответа консоли места для них не

5. Блоки внутри `component` и `invoke` данных не получают (консоль их не

Пример доски TAI-ADR-0066 п.1 (`filter: "status == 'active'"`) над
экземплярами не покажет ни одного: состояния экземпляра — `running |
suspended | completed | failed | cancelled` (§1). Это пример решения, не
ошибка ядра; пакету тендеров — `status == 'running'`.


## Амендмент 2026-10-04 (TAI-ADR-0066 п.1 `source`, план п.6, TASK-001302): источники `tasks` и `knowledge`

Этап 6 решения суперпроекта: тот же запрос `POST /views/{key}:query` и те же
ответы блоков (А1, А3–А5), ещё два источника вида. Код —
`application/queries/view_records.py` (запрос), `domain/views.py` (пути,
типы фильтров, окружение CEL, сверка с онтологией),
`application/commands/views.py` (контекст проверки и онтология дерева для
плана). Форма ответов консоли не меняется; в теле запроса добавлено
необязательное `workspaceId` (Б2).

### Б1. Источник `{tasks: {type}}`

- **Записи** — задачи типа `type` (любой версии типа) из тех, что вызывающему
  показывает `GET /tasks`: то же условие видимости
  (`queries/lists.readable_tasks` — его теперь читают оба), `tasks.read`.
  Вид сужает, не расширяет.
- **Пути** — `id`; `fields.<поле>` — поля `TaskOut`: `publicId`, `title`,
  `description`, `status`, `systemStatusCategory`, `priority`, `ownerId`,
  `assigneeId`, `workspaceId`, `createdBy`, `startDate`, `dueDate`,
  `createdAt`, `updatedAt`, `completedAt`; `customFields.<путь>` — по
  `fieldSchema` последней активной версии типа (`properties`, локальные
  `$ref`, `allOf/anyOf/oneOf`, как у `data.*` процесса). Те же имена — в CEL:
  `fields` — объект полей задачи (время — `timestamp`, отсутствующее —
  `null`), `customFields` — по `fieldSchema`, `id`, `param`, `settings`.
- **Ключ и подпись** — путь как есть: `field` фильтра и сортировки, ключ
  колонки и подпись по умолчанию `<пакет>.fields.<путь>`
  (`ledger.fields.customFields.total`), как решил этап 1.
- **Типы фильтров** (§9): `fields.status` — `enum` статусов жизненного цикла
  типа; `fields.systemStatusCategory` — `enum` категорий; `fields.priority` —
  `enum` приоритетов; даты задачи — `date`; `customFields.*` — по схеме, как
  `data.*`; прочее — `text`.
- **Строка** — `id` — `open.id` пакета, иначе id задачи; `title` — заголовок
  задачи. Значение формата `status` у пути `fields.status`: `title` — текст
  `<пакет>.fields.fields.status.<ключ>`, иначе `displayName` статуса типа,
  иначе ключ; `category` — по категории задачи в словаре А3:
  `backlog`, `blocked` → `suspended`, `active` → `running`,
  `terminal_success` → `completed`, `terminal_cancelled` → `cancelled`.
- **Фильтры, порядок, страница** — SQL по колонкам задачи и `custom_fields`
  (операции А4; день даты задачи — по UTC). Порядок пакета или запроса, затем
  новые первыми и id; `fields.status` сортируется по порядку статусов типа,
  `fields.priority` — `critical, high, medium, low`; курсор — по ключам
  (keyset), как у процесса.
- **Агрегаты** `metrics` и `chart` — над всеми видимыми задачами типа,
  выражения — в Python по записям (Б4); `chart` по `fields.status` — в порядке
  статусов, по `fields.priority` — в порядке приоритетов.

### Б2. Источник `{knowledge: {kinds}}`

- **Где** — база знаний корня дерева пространств: `workspaceId` тела запроса,
  иначе единственное дерево вызывающего (корни видимых пространств в режиме
  `members`, корни tenant иначе); деревьев больше одного —
  `422 workspace_required`; ни одного — пустой ответ блока. Корень дерева в
  режиме `members` сам часто невидим (член отдела под корнем компании):
  тогда права и namespace решаются по видимому пространству этого дерева с
  наименьшим id — память читается та же, база знаний корня. Другие источники
  `workspaceId` не читают.
- **Права** — как у `POST /knowledge/entities:query` (ADR-0060): `events.read`
  на пространстве, namespace корня его дерева, видимость вызывающего в памяти.
  Невидимое и несуществующее пространство — тот же `404`, без права читать
  знания дерева — тот же `403`; запись, которую память вызывающему не
  показывает, — ни в одном ответе, связь с ней — тоже. Транзакция только
  решает, где и можно ли; записи читаются из памяти после неё.
- **Пути** — `id` (`<kind>:<key>`), `kind`, `key`, `title`, `validFrom`,
  `validTo`, `attributes.<путь>`; колонка `table`/`list` — ещё
  `relations.<имя связи>`: заголовки противоположных концов связи через
  запятую, прочтённые обходом `include.relations` (ADR-0060 С1) для строк
  страницы. В фильтре, порядке, группе и CEL связей нет (`undeclared_path`,
  у CEL — ошибка выражения). В CEL `attributes` — отображение (`dyn`): схемы
  атрибутов живут в памяти, не в ядре.
- **Типы фильтров** — `kind` — `enum` видов источника, `validFrom`/`validTo` —
  `date`, прочее — `text`. Равенство — значений JSON (логическое не число,
  `1` и `1.0` — одно число); атрибут-список подходит, если подходит элемент.
- **Строка** — `id` — `open.id`, иначе `<kind>:<key>`; `title` — заголовок
  записи, иначе ключ; `category` значения `status` — `running` (своего
  состояния у записи нет).
- **Порядок** — пакета или запроса, отсутствующее значение последним, затем
  `(kind, key)`, как перечень памяти. Курсор — по месту последней записи
  страницы: продолжает после неё; исчезла из перечня — с того же номера.
- **Агрегаты** — над всеми записями видов, `chart` — в порядке видов
  источника.
- Блок `related` вида задач и вида знаний: ключ записи — выражение над
  `param` (записи у блока нет), база знаний — по `workspaceId`, как у
  источника `knowledge`; без права — пустой список, как в А2.

### Б3. Проверка при публикации

Ошибки (`POST /packages:plan` и `:apply`, §3):

- `undeclared_path` — путь вида задач не `id`, не `fields.<поле TaskOut>` и
  не `customFields.<путь>`, объявленный в `fieldSchema` типа (у типа без
  `fieldSchema` — ни один); путь вида знаний не той формы (`relations.*` —
  только колонкой `table`/`list`);
- `format_type_mismatch`, `expression_type_error` — как у процесса, по типам
  Б1 и Б2.

Предупреждения (только план, `planHash` их не включает): виды
`source.knowledge.kinds` и `related.knowledge.kind` (`unknown_kind`),
атрибуты `attributes.*` колонок, фильтров, порядка, группы и чтений CEL
(`undeclared_path`, предупреждение: объявлен хотя бы у одного вида источника;
вид без схемы атрибутов принимает любой), связи `relations.*` и
`related.include.relations` (`unknown_relation`) — по онтологии дерева
`workspaceId` плана (каталог видов namespace корня и схемы атрибутов из пакетов
знаний памяти, первый пакет, объявивший вид, побеждает — как в памяти). Плана
без `workspaceId`, без права читать знания дерева или при недоступной памяти —
одно предупреждение `knowledge_unchecked`.

Почему предупреждения, а не ошибки: онтология принадлежит дереву пространств
(пакеты знаний включают на корне), пакет — tenant; один вид читают в
деревьях с разными онтологиями, а `:apply` память не читает. Ошибка по
дереву, которое назвал план, отвергала бы вид, верный для другого дерева.
Путь, которого онтология дерева не объявляет, при запросе даёт `null`.

### Б4. Исполнение и потолок

Выражения CEL источников `tasks` и `knowledge` вычисляются в Python по
записям тем же профилем `cp/1`; в SQL у задач — только фильтры, порядок и
страница (они — пути, а не выражения). Поэтому у обоих — потолок А6:
агрегаты задач читают не больше `MAX_EVALUATED` (20 000) задач, вид знаний —
не больше `MAX_KNOWLEDGE` (5 000) записей из памяти (страницами по 500);
дальше — `409 view_too_costly` с `details {key, limit}`, а не ответ по части
записей. Страница `table`/`list` задач потолка не касается.

### Б5. Ошибки

К таблице А7:

| Код | Когда |
|---|---|
| `422 block_source_mismatch` | блок записи процесса (`header`, `fields`, `steps`, `timeline`, `artifacts`) у вида задач или знаний |
| `422 workspace_required` | вид знаний (или `related`) без `workspaceId`, а у вызывающего несколько деревьев |
| `404 not_found` | `workspaceId` невидимого или несуществующего пространства |
| `403` | нет права читать знания дерева (как `entities:query`) |
| `409 view_stale` | выражение вида больше не компилируется по `fieldSchema` последней версии типа |
| `502`/`503` | память ответила ошибкой / не ответила или не настроена (как `entities:query`) |

`501 not_implemented` маршрут больше не отвечает.

### Б6. Чего этап 6 не делает

1. Выражения CEL задач и знаний в SQL не переводятся (Б4): вид с большими
   источниками упирается в потолок, а не замедляется без предела.
2. Условия фильтров вида знаний не передаются в `where` памяти: у памяти
   свой смысл `prefix` (по сегментам) и сравнений; фильтр считается в ядре по
   А4.
3. Блок `artifacts` у вида задач и знаний проверка публикации не отвергает
   (этап 1), запрос отвечает `422 block_source_mismatch`.
4. Подписи значений `kind` и связей — из словаря пакета по общему правилу
   (`<пакет>.fields.kind.<вид>`), словарей онтологии нет.
