# Execution workspace: рабочая копия на задачу

Реализация п. 5 [ADR-0016](../../docs/adr/ADR-0016-agent-runtime-and-execution-workspace.md)
для reference-демона `control-plane-agent`. Модуль —
`src/control_plane_agent/workspace.py`.

## Зачем

Адаптер, работающий в `os.getcwd()`, сериализует процесс до одной задачи и
делает коммит непригодным как evidence: изменения разных задач смешиваются.
Здесь каждая задача исполняется в собственном git worktree на ветке
`task/<publicId>`, а коммит регистрируется Artifact'ом **ссылкой**
`git:<sha>` — Control Plane не файловое хранилище (harness-protocol §8).

## Включение

Пул создаётся, только если заданы обе переменные:

| Переменная | Смысл |
|---|---|
| `CONTROL_PLANE_AGENT_REPO` | репозиторий-источник копий (bare-клон на runner) |
| `CONTROL_PLANE_AGENT_WORKTREE_ROOT` | каталог, где живут рабочие копии |
| `CONTROL_PLANE_AGENT_BASE_REF` | от чего ветвиться, по умолчанию `HEAD` |
| `CONTROL_PLANE_AGENT_KEEP_WORKSPACES` | `1` — не убирать копию после успеха |
| `CONTROL_PLANE_AGENT_MAX_WORKSPACES` | потолок числа простаивающих копий (8) |
| `CONTROL_PLANE_AGENT_REPO_DIR` | каталог рабочей копии внутри контейнера: имя или путь из сегментов (`services/control-plane`); по умолчанию имя репозитория |
| `CONTROL_PLANE_AGENT_NEIGHBOURS` | соседние репозитории: `путь=/путь/к/зеркалу.git`, через запятую; путь — имя или сегменты (`sdk/platform-auth-sdk`), он же путь сабмодуля в суперпроекте |
| `CONTROL_PLANE_AGENT_SUPERPROJECT` | репозиторий, чьи сабмодули закрепляют ревизии соседей |
| `CONTROL_PLANE_AGENT_SUPERPROJECT_REF` | ревизия суперпроекта, из которой читаются закрепления (`HEAD`) |
| `CONTROL_PLANE_AGENT_SUPERPROJECT_REMOTE` | remote для обновления суперпроекта; пусто — зеркало обновляет деплой |

Осторожно с именами: `CONTROL_PLANE_AGENT_WORKSPACE` — это **Workspace
Control Plane**, из которого берутся задачи, а не локальная рабочая копия.

Без этих переменных адаптер получает `workspace=None`, и демон ведёт себя
ровно как раньше — протокольные тесты, не трогающие файлы, продолжают
работать.

## Каталог репозиториев (universal-runner U005)

Агент с каталогом в `workingCopy` (`repositories`, `repositoryField`;
TAI-ADR-0063 п.3, CP-ADR-0073 амендмент 2026-09-30, Е4) исполняет задачи
любого репозитория каталога. Репозиторий задачи — ключ или псевдоним в
`customFields.<repositoryField>`, без учёта регистра; адрес — только из
каталога. Задача без ключа или с незнакомым ключом не исполняется в
репозитории по умолчанию: прогон проваливается с `repository_unknown`, задача
уходит в `blocked`. Пул на ключ создаётся при первой задаче репозитория
(`control_plane_agent/catalog.py`); пулы делят корень копий, поэтому раскладка
та же:

```
<worktree-root>/TASK-000123/control-plane/       копия задачи control-plane
<worktree-root>/TASK-000124/memory-service/      копия задачи memory-service
```

Каталог копии — `directory` записи, по умолчанию ключ; `directory` —
имя или путь из сегментов (`services/control-plane`, раскладка TAI-ADR-0064,
см. «Раскладка с сегментами» ниже). В чекпоинт
`execution.workspace` добавляются `repositoryKey` и `baseRevision` (коммит,
от которого отведена ветка задачи). Если у задачи сменился ключ, копия
прежнего репозитория без правок и собственных коммитов (в том числе на
отсоединённом HEAD) удаляется вместе с веткой в зеркале, иначе —
`repository_changed` и `blocked`, работа остаётся на месте.

Ограничения каталога:

- Адрес — https без учётных данных, запроса и фрагмента; для отладки
  принимаются `file://` и абсолютный путь хоста. Два адреса одного репозитория
  (регистр, `/`, `.git`) — ошибка каталога.
- Ядро ищет секреты по подстроке имени ключа (`reject_secret_material`,
  CP-ADR-0073 Е1), и ключ каталога — не исключение: репозиторий с ключом вроде
  `token-service` или `secrets-manager` ревизия не примет (`422
  secret_material_rejected`). Такой репозиторий заводится под другим ключом, а
  прежнее имя — в `aliases`.
- `CONTROL_PLANE_AGENT_MAX_WORKSPACES` — потолок на репозиторий, а не на
  реплику.
- Прежний ключ задачи демон ищет в 50 новейших чекпоинтах задачи; не нашёл —
  копия прежнего репозитория остаётся на месте.
- Адрес с неразбираемым хостом (`https://[abc/x`) или портом вне 1–65535 —
  ошибка каталога (выход 2), а не трейсбек; у прежней формы — тоже выход 2.

### Соседи, суперпроект и `runner.yaml` (universal-runner U006)

Что готовить для задачи, репозиторий каталога говорит сам — в
[`.agents/runner.yaml`](../src/control_plane_agent/runner_config.md)
(`control_plane_agent/conventions.py`):

- **Базовая ревизия.** Файл читается из зеркала через
  `git show <база>:.agents/runner.yaml`, где база — коммит, от которого
  отведена ветка задачи (записанный; у ветки без записи — общая точка с базовой
  веткой; у новой ветки — сама база). С ветки задачи — никогда: правка файла на
  ветке начинает действовать после ревью и вливания. Файла нет — соседей нет.
  Файл неверен (схема, лишнее поле, больше 256 КиБ), сосед не из каталога или
  сам репозиторий, сосед не сабмодуль суперпроекта — прогон проваливается с
  `runner_config_invalid`, задача уходит в `blocked` с ошибками по путям полей.
- **Соседи.** `neighbours` — ключи (или псевдонимы) каталога. Адрес — из
  каталога. Ревизия — gitlink сабмодуля в дереве суперпроекта (`superproject`
  каталога) на его базовой ревизии: `baseRef` записи суперпроекта, свежий fetch.
  Сабмодуль ищется по пути `directory` записи (по умолчанию ключ), затем по
  имени репозитория в URL `.gitmodules`. Соседи есть, а суперпроекта в каталоге
  нет — ошибка прогона. Сосед кладётся рядом с копией, в каталог `directory`
  записи, — то, что называет путь `../<сосед>` (на раскладке с сегментами —
`../../sdk/<сосед>`).
- **Раздельные зеркала.** Соседей режут из `<зеркала>/neighbours/<ключ>.git`,
  а не из зеркала пула. Это bare-репозиторий с `origin` = адрес каталога, fetch
  идёт только в `refs/remotes/origin/*`, веток у него нет. Задача
  memory-service с соседом control-plane не двигает ветки задач пула
  control-plane той же реплики. Закреплённый коммит, которого нет ни в одной
  ветке forge, берётся fetch по id в `refs/remotes/pins/<sha>`; туда же
  записывается каждая ревизия, на которую поставлен сосед, — после force-push
  у соседа его копия не считается «своими коммитами». Закрепление, на котором
  не стоит ни одна живая копия этого зеркала (`git worktree list` после
  `worktree prune`), удаляется при каждой постановке соседа и при снятии его
  копии: закрепления не копятся. `worktree prune` снимает записи о копиях,
  каталогов которых не видно по записанному пути, — поэтому это безопасно,
  пока все реплики видят корень копий (`CONTROL_PLANE_AGENT_WORKTREE_ROOT`)
  по одному и тому же пути. Если вынести зеркала на общий том
  (`CONTROL_PLANE_AGENT_MIRRORS`), а копии оставить у каждой реплики своими
  (или смонтировать корень копий по разным путям),
  `prune` одной реплики сотрёт записи о живых копиях другой, а следом за ними
  уйдут и их закрепления; такой вынос требует сначала развести записи копий
  по репликам. Своего в зеркале соседа
  нет, поэтому новый адрес в каталоге переписывает `origin` зеркала и
  сбрасывает ветки прежнего адреса (закрепления остаются). Замок зеркала,
  занятый дольше таймаута, при подтягивании закрепления — ошибка «занято», а
  не «ревизии нет в forge». Forge ответил на fetch веток и отказал в коммите
  по id (`not our ref`, `unadvertised object`) — ревизии нет; forge не ответил
  на любой из двух fetch (сетевой сбой, таймаут) — ошибка прогона, повтор
  может пройти, но не `blocked`. Каждый fetch зеркала соседа и суперпроекта
  ограничен тем же сроком, что fetch базы пула (`BASE_FETCH_TIMEOUT`), и по
  истечении убивается вместе с транспортом: зависший forge соседа не держит
  взятие копии и замок зеркала.
  Зеркало суперпроекта для чтения закреплений — тоже здесь.
- **Задача суперпроекта.** Закрепления читаются из головы ветки задачи (у
  новой ветки это база; влила задача базу со сдвинутым указателем — уже её),
  соседи кладутся **внутрь** копии, на пути своих сабмодулей: копия
  суперпроекта с сабмодулями-соседями. Указатель на ветке задачи, отличный от
  базового и названный коммитом, которого нет в forge соседа (не запушен или
  стёрт), при взятии копии — `neighbour_modified`, задача уходит в `blocked` с
  причиной «ветка задачи указывает сабмодулем <путь> на <sha>, которого нет в
  forge; верните указатель на <базовый sha> или запушьте коммит». Если
  указатель пришёл вливанием новой базы — он тот же, что у базовой ветки в
  точке, где ветка задачи сошлась с ней последний раз (`merge-base` головы и
  ссылки базы; слиянием или fast-forward), — причина называет этот коммит базы
  и советует чинить базу: запушить коммит в соседа или поправить указатель в
  базе и влить её снова, а не откатывать указатель на ветке. Базовый
  указатель на отсутствующий коммит — по-прежнему ошибка прогона: чинить базу,
  а не задачу. `git status` копии видит их чистыми.
  Коммит демона пути вложенных соседей не индексирует
  (`git add -A -- . ':(exclude,literal)<путь>'`): указатель в коммите — тот,
  что на ветке, и вливание базы посреди прогона не откатывается. Указатели
  соседей задача не трогает: указатель в индексе, отличный от HEAD копии, или
  указатель на ветке, отличный от указателя в последней общей точке с
  базовой веткой (точка отвода; позже — общая точка с
  `refs/remotes/<remote>/<база>` или `refs/heads/<база>`), —
  `neighbour_modified`. Ссылку отслеживания базы демон обновляет при взятии
  копии и ещё раз, best-effort, перед проверкой соседей (fetch не дольше
  `base_fetch_timeout` пула, по умолчанию 120 с; дольше — процесс git вместе с
  транспортом снимается, в журнал — предупреждение, проверка идёт по ссылке,
  что уже есть): база, влитая через
  `git pull origin <база>` или `git merge FETCH_HEAD`, — не изменение задачи,
  а откат указателя к значению до вливания — изменение. Указатель головы
  базы на момент сдачи — тоже базовый: базу, сдвинутую во время прогона,
  задача может не вливать, а чекаут вложенного соседа (`git submodule
  update`) может стоять на любом базовом указателе — это не изменение
  соседа (ADR-0073, Н1–Н3). Указатель на ветке или в индексе, старше
  ожидаемого указателя базы (после вливания — её головы, без вливания — точки
  отвода), — откат: `neighbour_pointer_regressed` с ожидаемой и фактической
  ревизиями и подсказкой `git checkout <remote>/<база> -- <путь>` (ADR-0073,
  О3). Так проверяется каждый gitlink суперпроекта, и сабмодуль не из
  `neighbours` (О2); коммит демона не записывает ни одного указателя (О1).
  Сдвиг указателя — отдельное действие (скилл сдвига сабмодуля). Перед удалением копии вложенные соседи снимаются первыми.
- **Сосед только для чтения** (`neighbour_modified`). После работы исполнителя
  демон проверяет каждого соседа: изменённые или новые неигнорируемые файлы,
  HEAD не на закреплённой ревизии (у вложенного соседа — и не на указателе
  базы), каталог удалён или подменён. Нашёл — ничего не коммитится и не публикуется, прогон проваливается с
  `neighbour_modified`, задача уходит в `blocked`, копия и сосед остаются как
  есть. Сосед, оставленный изменённым прежним прогоном (правки или коммиты,
  которых нет ни в одной ссылке его зеркала), при взятии копии не сдвигается —
  тот же `neighbour_modified` до решения человека. Чистый сосед на старом
  закреплении переводится на новое; чистая копия соседа из другого зеркала
  (прежняя форма) пересоздаётся. Каталог на месте соседа с чужими файлами —
  `neighbour_modified`. Публикуется только репозиторий задачи.
- **След.** В чекпоинт `execution.workspace` добавляются `conventionsRevision`
  (коммит, с которого прочитаны соглашения), `agentsMdBase` (sha блоба
  `AGENTS.md` там, `null` — файла нет) и `neighbours` (ключ → ревизия); после
  коммита — `agentsMdHead`, sha блоба `AGENTS.md` в сданном коммите.
- **Зеркала при старте.** Зеркало пула и зеркало соседа создаются и
  обновляются под файловым замком рядом с ними. Замок ждёт не дольше 600 с:
  клон, зависший в соседней реплике, даёт ошибку с причиной, а не вечное
  ожидание. Пул на ключ создаётся под замком своего ключа: первый клон одного
  репозитория не задерживает задачи других. Временные каталоги
  `.<имя>.git.<pid>.tmp`, оставленные упавшими клонами, демон убирает при
  старте — если их процесс не жив и замок репозитория свободен.

### Установка `setup` (TASK-001273)

`setup` из `runner.yaml` базовой ревизии демон выполняет сам, в каждом
прогоне с рабочей копией: после копии, соседей и тестовых сервисов, до
исполнителя (`control_plane_agent/setup_command.py`). Запуск — как у одной
проверки ниже (`sh -c` в корне копии, то же окружение вместе с `env`
сервисов, предел 1800 с, группа процессов снимается), действие `setup.run`
прогона; вывод — только в журнал демона, со скрытыми секретами и путями.
Ненулевой код или предел — `setup_failed`, задача в `blocked`, исполнитель
не запускается. Пропуска по хэшу нет: команда должна быть идемпотентной и не
менять отслеживаемые файлы. База неизвестна — установка пропускается.
Подробно — [runner_config.md](../src/control_plane_agent/runner_config.md),
«Как исполняются `setup` и `checks`», решение — CP-ADR-0073, амендмент Е7
2026-10-01.

### Проверки перед сдачей (universal-runner U014)

Включаются `workingCopy.checks: true` описания агента (в env-режиме —
`CONTROL_PLANE_AGENT_CHECKS=1`; `control_plane_agent/checks.py`). Без
включения демон `checks` не читает и не прогоняет.

1. **До исполнителя** демон читает `checks` из `runner.yaml` базовой ревизии
   (те же правила, что выше): неверный файл — `runner_config_invalid`, задача
   в `blocked`, модель не запускалась. База — как у соглашений каталога:
   записанная точка ответвления ветки задачи, без записи — её `merge-base` с
   базовой веткой, никогда не голова ветки задачи (FR-009). Базу узнать не
   удалось — `checks_base_unknown`, тоже `blocked` до работы модели.
2. **После хода исполнителя** — и после проверки соседей и `blocked` —
   каждая проверка идёт `sh -c '<run>'` в корне копии, все по порядку файла,
   даже после упавшей. Окружение — демона без зарезервированных имён
   `runner.yaml` (`RESERVED_ENV_NAMES`: учётки и настройки демона,
   исполнителя, forge — `CLAUDE_*`, `ANTHROPIC_*`, `GH_*`, `GIT_*`, `SSH_*`,
   `XDG_*`, `CONTROL_PLANE_*`…), кроме `PATH`, `HOME`, `SHELL`, хранилища
   сертификатов (`SSL_CERT_*`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`,
   `NODE_EXTRA_CA_CERTS`) и прокси (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`,
   `ALL_PROXY` в любом регистре; прочие `*_PROXY`, например
   `GITHUB_TOKEN_PROXY`, отбрасываются), и без переменных с именами
   секретов (`GITHUB_TOKEN`, `NPM_TOKEN`, `AWS_SECRET_ACCESS_KEY`, `DB_PASS`,
   `MYSQL_PWD`, `GITLAB_PAT`, `DOCKER_AUTH_CONFIG`, `SENTRY_DSN`…: код
   исполнителя мог бы их прочитать и отправить); имена сравниваются в верхнем
   регистре (`gh_token`, `Claude_Code_OAuth_Token` тоже отбрасываются). Имя
   говорит не всё, поэтому отбрасываются и переменные, чьё значение несёт
   секрет (`is_secret_value`): URL с паролем (`scheme://user:pass@…` —
   `DATABASE_URL=postgresql://u:pw@db/app`; без пароля, `user@` или `user:@`,
   — нет) и строка подключения с непустым `Password=`, `Pwd=`, `AccountKey=`
   или `SharedAccessKey=` в начале значения или после `;`
   (`AZURE_STORAGE_CONNECTION_STRING`; регистр ключа любой,
   `SharedAccessKeyName=` — не секрет). Маскировки пароля в выводе мало:
   сам процесс проверки видел бы значение целиком. Исключение — оставленные
   зарезервированные имена (`KEPT_RESERVED_ENTRIES` и прокси выше): без них
   проверка не работает, а `user:pass@` прокси скрывается в выводе. Плюс
   `env` сервисов прогона — его строки подключения с паролем проверка
   получает: это её база.
   **Фильтр окружения — не граница безопасности.** Проверка работает под тем
   же uid, что и демон, и может прочитать его окружение из
   `/proc/$PPID/environ` (как и любого процесса того же uid). Фильтр и
   маскировка убирают случайные утечки в вывод и промпт, но не защищают от
   кода, который ищет секреты намеренно: для этого нужен отдельный uid или
   sandbox, их нет (см. «Границы»).
   Проверка — действие `checks.run` прогона (временная ошибка ядра при его
   записи прогон не роняет); дольше 1800 с — останавливается вместе со своими
   процессами (`timed_out`). Когда оболочка проверки вышла, её группа
   процессов снимается всегда: фоновый процесс не держит результат и не
   переживает проверку.
3. **Бюджет.** Все проверки одной сдачи, оба раунда, делят общий бюджет —
   3600 с (параметр `checks_budget` демона). Проверка, которую он обрезал, —
   `timed_out`, та, на которую времени не осталось, — `not_run`; бюджет
   исчерпан — попытки исправления нет, сдача с тем, что показали проверки.
4. **Упала хотя бы одна** — исполнитель получает ровно один ход ещё, в том же
   прогоне (Claude Code продолжает свою сессию), с разделом промпта «Проверки
   перед сдачей не прошли»: команда, код выхода, хвост вывода. В выводе и
   команде скрыты пароли сервисов прогона и значения их `env`, в которые
   подставлены `{password}` или `{user}` (прочие — хост, порт, имя базы — не
   секрет и не скрываются; значение из одного `{user}` — тоже: имя
   пользователя шаблона, `postgres`, иначе пропадало бы по всему выводу),
   значения переменных демона с именами секретов (`*TOKEN*`, `*KEY*`,
   `*SECRET*`, `*PASSWORD*`, `*PASS`, `*PASSPHRASE*`, `*PWD*`, `*_PAT`,
   `*AUTH*`, `*DSN*`…,
   кроме путей `*_FILE`, `*_DIR`, `*_ASKPASS`, каталога `PWD`/`OLDPWD` и
   `*AUTHOR*`) — даже если проверка их не получала — вместе с user-частью URL
   в них, если за ней нет пароля (ключ `SENTRY_DSN=https://<key>@host`; у
   `postgresql://postgres:<пароль>@db` скрыт только пароль), пароль из URL в любой
   переменной демона и часть `user:pass@` любого URL в выводе (`https_proxy`,
   `DATABASE_URL`). Маскировка best-effort: секрет, разрезанный переносом
   строки или закодированный (base64), не распознаётся. Затем снова соседи
   и `blocked`, затем все проверки заново.
5. **Что оставили проверки.** Перед проверками демон снимает дерево копии
   (своим индексом, индекс копии не трогается), после — возвращает файлы к
   нему: добавленное проверками удаляется, изменённое и удалённое
   восстанавливается; игнорируемые файлы и вложенные соседи не трогаются.
   Сначала возвращаются файлы `.gitignore`, остальное сравнивается уже по
   ним: проверка, дописавшая свои артефакты в `.gitignore`, не протащит их в
   коммит. Проверки сдвинули HEAD (commit, checkout) — `checks_moved_head`,
   копию вернуть не удалось — `checks_restore_failed`; в обоих случаях задача
   в `blocked`, ничего не сдаётся. Ошибка возврата копии после упавшего хода
   проверок (отмена, отказ ядра) идёт в журнал и не подменяет исходную ошибку.
   Ход исправления начинается с работы исполнителя, в коммит идёт только она.
6. **Сдача** — какой бы ни был итог: `metadata.checks` артефакта `commit`
   (прежние поля не меняются) и `output.checks` прогона — `status` (`passed`,
   `failed`, `none`), `revision`, `fixAttempted`, `durationSeconds`, `results`
   (`name`, `run`, `status` — `passed`, `failed`, `timed_out`, `not_run`,
   `exitCode`, `durationSeconds`), после попытки — `firstResults`. Красные —
   ещё и комментарий в задаче. Вывод проверок в метаданные не попадает.

## Публикация, WIP и реплики (universal-runner U007)

Подробности и контракт хука — CP-ADR-0073, Е8; код — `control_plane_agent/publish.py`.

- **Перед каждым push** каждый push-адрес remote сверяется с адресом
  конфигурации (запись каталога или `workingCopy.repository`), затем спрашивается хук хоста
  `CONTROL_PLANE_AGENT_PUBLISH_HOOK`: JSON `{url, branch, commit, repositoryKey}`
  на stdin, код 0 — можно, иначе отказ с причиной из первой строки stdout.
  Отказ — `publish_target_rejected`: ничего не отправлено, задача уходит в
  `blocked`. Пушится только ветка задачи, ровно проверенный коммит и ровно на
  проверенные адреса (не по имени remote).
- **WIP.** Перед `blocked` и перед закрытием по `restart_recovery` правки копии
  коммитятся в ветку задачи (трейлер `Control-Plane-WIP: true`) и публикуются;
  запись с `wip: true` — в чекпоинте `execution.workspace` (у
  `restart_recovery` — в `output.workspace` прогона), артефакта `commit` нет.
  Указатели сабмодулей в WIP не входят. Продолжение WIP сдаёт свой коммит
  поверх него (без правок — пустой), а не сам WIP.
- **Неопубликованное.** Push, не прошедший из-за сети или forge, попадает в
  `<worktree-root>/.unpublished.json` и повторяется в следующем цикле, затем с
  растущей паузой (30 с … 30 мин); ветка, переписанная в forge, снимается.
  Повторяются только задачи, чья копия есть на реплике (сданная с
  неопубликованной веткой копия не удаляется). После 12 неудач или 6 ч с
  первой запись снимается: warning в журнале и комментарий в задаче с
  причиной.
- **Диск, пока forge недоступен.** Копии задач из списка лимит
  `MAX_WORKSPACES` не вытесняет и не считает (CP-ADR-0073, Е8), поэтому пока
  forge недоступен, диск реплики растёт сверх лимита — до тех пор, пока
  записи не исчерпают повторы (12 неудач или 6 ч) и не снимутся. Это
  осознанно: потерять неопубликованную работу хуже, чем временно превысить
  лимит. Следите за свободным местом тома при долгом сбое forge. Список,
  который есть, но не разбирается (битый JSON, нет `items`), вытеснение
  останавливает целиком: какие копии ждут — неизвестно; отсутствующий файл
  значит «ничего не ждёт». Битый файл перезапишется при следующем сбое push
  (или удалите его руками, если повторять нечего).
- **Другая реплика** берёт опубликованную ветку, а отставшую локальную ветку
  сдвигает вперёд до опубликованной (без правок в копии и без расхождения).
- **Выбор работы.** До 50 кандидатов; внутри приоритета — перемешивание, свои
  копии первыми; проигранный claim — следующий кандидат, `403` на claim —
  конец цикла; неназначенные задачи агент с каталогом не берёт.

## Соседи: копия, которую можно собрать

Репозиторий с path-зависимостью нельзя собрать из копии его одного:
`control-plane` подключает `platform-auth-sdk` как `../platform-auth-sdk`, то
есть ждёт его **соседней папкой**. Поэтому копия — не один каталог, а
контейнер:

```
<worktree-root>/TASK-000123/control-plane/       рабочая копия, ветка task/TASK-000123
<worktree-root>/TASK-000123/platform-auth-sdk/   сосед на закреплённой ревизии
```

Ревизия соседа берётся **из суперпроекта** — из gitlink его сабмодуля, — а не
из `main` самого соседа. Разница принципиальная: «последний main» это
сочетание ревизий, которого нет ни в одном коммите, и зелёный прогон против
него ничего не говорит о ветке, которую отдают на ревью.

Недостающий закреплённый коммит подтягивается fetch в `refs/remotes/origin/*`
зеркала соседа, а не поверх его веток: зеркало может быть и зеркалом пула с
ветками задач.

Соседи создаются на задачу, а не на весь пул: две одновременные задачи не
двигают общий каталог под ногами друг у друга. Если в соседе есть локальные
изменения (агент или человек что-то правил при отладке), пул их не трогает и
оставляет соседа как есть — молча уничтожать работу этот модуль не умеет.
Ревизии соседей уезжают в checkpoint (`neighbours`): evidence — это коммит
**вместе** с тем, против чего он проверялся.

Копии, созданные до появления контейнеров, при первом обращении переносятся
внутрь контейнера вместе с незакоммиченными изменениями: на runner они
означают незавершённую работу, с которой продолжит следующая попытка.

### Раскладка с сегментами

Суперпроект переезжает в `services/`, `sdk/`, `apps/` (TAI-ADR-0064). Каталог
копии (`directory` записи каталога, `CONTROL_PLANE_AGENT_REPO_DIR`) и путь
соседа могут быть путями из сегментов. Контейнер тогда повторяет раскладку
суперпроекта, и путь между компонентами в нём тот же, что в суперпроекте:

```
<worktree-root>/TASK-000123/services/control-plane/   рабочая копия
<worktree-root>/TASK-000123/sdk/platform-auth-sdk/    сосед: ../../sdk/platform-auth-sdk
<worktree-root>/TASK-000123/services/memory-service/  сосед: ../memory-service
```

Правило пути — `$defs.workingCopyPath` схемы package-sdk: сегменты через `/`,
сегмент начинается с буквы или цифры (`.` и `..` не проходят), без пустых
сегментов, обратного слэша, ведущего и завершающего `/`, сегмент до 100
символов, путь до 200. Каталог записи каталога — только строчные (как в
схеме); прежняя форма допускает и заглавные: её каталог по умолчанию — имя
репозитория-источника. Копия и сосед не лежат один в другом — отказ при старте.
Уборка снимает копию, соседей и опустевшие промежуточные каталоги (`services/`,
`sdk/`). Плоская раскладка — частный случай: путь из одного сегмента.

## Контракт адаптера

```python
async def execute(self, task, run, client, workspace) -> list[ArtifactSpec]
```

Адаптер, меняющий файлы, обязан работать **внутри `workspace.path`** и нигде
больше: именно это не даёт двум одновременным задачам писать в одну копию.

## Жизненный цикл

1. `acquire(publicId)` — эксклюзивная блокировка (lock-файл), `git worktree
   add` на ветку `task/<publicId>`; если копия уже есть — переиспользуется
   вместе с незакоммиченными изменениями.
   База по умолчанию fetch'ится так же — в
   `refs/remotes/<remote>/<база>` зеркала, от неё и режется копия; ветки
   зеркала fetch не двигает.
   Если у задачи есть `customFields.baseBranch` (ветка фичи, TAI-ADR-0047),
   ветка задачи отводится от неё: ветка fetch'ится из push-remote в
   `refs/remotes/<remote>/<baseBranch>` зеркала (не в общий `FETCH_HEAD` —
   задачи разных фич берут копии одновременно). Ветки нет в forge — отказ
   `base branch … does not exist`, а не копия от ветки по умолчанию; forge
   недоступен — копия от ветки, уже лежащей в зеркале. База, от которой
   отведена ветка задачи, записывается в `branch.task/<id>.controlPlaneBase`
   (и коммит — в `…controlPlaneBaseCommit`); если задача теперь просит другую
   базу, ветка без работы пересоздаётся (с записью в лог), а с незакоммиченными
   правками или собственными коммитами — отказ с причиной. Ветки, созданные
   до этой записи, считаются отведёнными от базы по умолчанию.
2. Checkpoint `execution.workspace` — `workspaceKey`, `branch`, `baseBranch`, `baseCommit`
   (у каталога ещё `repositoryKey`, `baseRevision`, `conventionsRevision`,
   `agentsMdBase`); после коммита добавляется `head` (у каталога и `agentsMdHead`). Это то, по чему следующий Run находит
   работу предыдущего.
3. `commit()` — сообщение всегда содержит publicId; Artifact типа `commit` с
   `uri = git:<sha>`.
4. `release(outcome)` — успех убирает рабочую копию, **ветку не трогает
   никогда**; `failed` и `suspended` оставляют копию как есть: это состояние,
   с которого продолжит следующая попытка.

Уборка не разрушает работу: копия с незакоммиченными изменениями не
удаляется, `git worktree remove` вызывается без `--force`, а ветки не
удаляются вовсе — кроме ветки задачи без единого собственного коммита,
пересоздаваемой от новой `baseBranch` (см. выше). Потолок `MAX_WORKSPACES` убирает только простаивающие
чистые копии; диск при этом ограничен сверху, а история — нет.

## Что не уходит наружу

`assert_portable()` проверяет checkpoints и артефакты перед отправкой и
**отклоняет** абсолютные локальные пути (`/Users/`, `/home/`, `file://`,
`~/`, `C:\`) и очевидные credentials (значения по ключам `token`, `apiKey`,
`password`, …; строки с префиксами `cp_`, `sk-`, `ghp_`, PEM). Наружу уходят
только логические идентификаторы: ключ workspace, ветка, sha.

## Границы

- Push в общую ветку и PR не делаются: это внешнее действие, требующее gate
  (AR-5).
- Изоляции файловой системы и сети нет — worktree это не sandbox. Процессы
  исполнителя и проверок работают под uid демона и могут прочитать его
  окружение (`/proc/$PPID/environ`): фильтр окружения проверок — не граница
  безопасности.
- Ветка задачи — в одном репозитории. Соседи раскладываются detached на
  закреплённой ревизии: они нужны, чтобы копию можно было собрать, а не чтобы
  вести в них работу. Задача, которой нужно менять сам SDK, — это отдельная
  задача в его репозитории.
- Зеркало суперпроекта обновляет деплой, если не задан
  `CONTROL_PLANE_AGENT_SUPERPROJECT_REMOTE`: пул не угадывает, какому remote
  принадлежит суперпроект.
- Занятая другим процессом копия сейчас даёт честный `fail_run` с причиной
  `workspace_busy`; после AR-5 это станет `checkpoint → suspend`.
- **Известное ограничение: force-push базы суперпроекта.** Указатель,
  принесённый вливанием базы, признаётся базовым по общей точке ветки задачи
  с `refs/remotes/<remote>/<база>`. Если базу перезаписали force-push'ем после
  того, как задача её влила, влитый коммит больше не предок ссылки
  отслеживания, общая точка уходит назад, и указатель из стёртой базы читается
  как изменение задачи — ложный `neighbour_modified`. Разбирает человек:
  влить в ветку задачи новую базу (или сбросить ветку на неё) и вернуть
  задачу.
